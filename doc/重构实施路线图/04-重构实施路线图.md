## 二、Phase 1：快速见效（Week 1-2）

> 目标：**花最少时间，获得最大优化效果**，零风险，零接口变更。

### 2.1 任务分解

| 任务 | 工作内容 | 预估工时 | 产出 |
|------|---------|---------|------|
| **1.1 Fallback 统一降级** | 编写 `SentinelFallbackFactory`，替换所有手写 FallbackFactory/Fallback | **1 人天** | 消除 ~15,000 行模板代码 |
| **1.2 gm-agg 纯代理消除** | 引入 `@FeignDelegate` 注解或网关路由，消除纯透传的 Service 方法 | **2 人天** | 消除 ~8,000 行代理代码 |
| **1.3 DTO 合并清扫** | 合并冗余 DTO（如 V1/V2 完全相同的 DTO），删除死代码 | **2 人天** | 减少 ~5,000 行 |
| **1.4 静态代码检查** | 配置 SonarQube/Checkstyle 规则，阻塞未来新增反模式代码 | **0.5 人天** | 质量门禁 |

### 2.2 Phase 1 详细实施步骤

#### 任务 1.1：Fallback 统一降级

```yaml
步骤:
  1. 引入 Sentinel（如果尚未引入）或使用动态代理
  2. 编写 UnifiedFallbackFactory.java（~50行）
  3. 逐个模块替换 @FeignClient 的 fallbackFactory 属性
     - cwhs: CwhsFeignClient → UnifiedFallbackFactory
           CwhsV2FeignClient → UnifiedFallbackFactory
           CwhsCwbbFeignClient → UnifiedFallbackFactory
           ...
     - ywgl: YwglFeignClient → UnifiedFallbackFactory
           YwglV2FeignClient → UnifiedFallbackFactory
           ZbkhFeignClient → UnifiedFallbackFactory
           ...
     - zhgl: ZhglFeignClient → UnifiedFallbackFactory
           ZhglV2FeignClient → UnifiedFallbackFactory
  4. 删除已不再使用的 FallbackFactory 和 Fallback 文件（约 10+ 个文件）
  5. 编译 + 全量回归测试
```

#### 任务 1.2：gm-agg 代理消除

```yaml
步骤:
  1. 在 gm-agg 中识别"纯透传"方法（无地区逻辑、无数据转换、无聚合处理）
  2. 引入 @FeignDelegate 注解 + Spring AOP
  3. 对纯透传方法添加 @FeignDelegate，指定目标 FeignClient 和方法
  4. 为有真实业务逻辑的方法（如涉及地区策略分派）保留在 gm-agg 中
  5. 编译 + 回归测试
```

### 2.3 Phase 1 风险与应对

| 风险 | 概率 | 应对 |
|------|------|------|
| Sentinel 与现有 Feign 不兼容 | 低 | 先在小模块试点（如 sp/lcgl） |
| AOP 代理链路性能影响 | 低 | 仅对纯透传方法使用，不影响链路 |
| 遗漏有业务逻辑的方法 | 中 | 代码审查 + 人工确认每个被标记的方法 |

## 三、Phase 2：核心重构（Week 3-6）

> 目标：拆分上帝类、解除循环依赖，这是架构优化的**核心攻坚战**。

### 3.1 任务分解

| 任务 | 工作内容 | 预估工时 | 产出 |
|------|---------|---------|------|
| **2.1 YwglServiceImpl 拆分** | 拆分为 6 个领域 Service（Fkyw/Skyw/Transfer/Account/Recon/Settlement） | **5 人天** | 消除 God Class |
| **2.2 CwhsServiceImpl 拆分** | 拆分为 6 个领域 Service（Pz/Km/Zt/Hz/Bb/Rzcl） | **5 人天** | 消除 God Class |
| **2.3 YwglController 拆分** | 按领域拆分为 3-4 个小 Controller | **2 人天** | Controller < 500 行/个 |
| **2.4 CwhsController 拆分** | 按领域拆分为 3-4 个小 Controller | **2 人天** | Controller < 500 行/个 |
| **2.5 循环依赖解除** | 引入防腐层/内部 SPI，解除 ywgl↔cwhs↔zhgl 循环 | **3 人天** | 依赖方向一致 |
| **2.6 回归测试 + BUG 修复** | 全面回归、修复兼容性问题 | **3 人天** | 稳定版本 |

### 3.2 Phase 2 实施策略

#### 上帝类拆分策略（以 YwglServiceImpl 为例）

```
Day 1-2: 静态分析
  - 在原文件中标记每个方法所属的领域（@Fkyw / @Skyw / @Transfer ...）
  - 识别跨领域调用的方法依赖关系图

Day 3-4: 创建领域 Service 骨架
  - 创建 6 个领域 Service 接口 + 实现类
  - 将原方法按领域复制到对应实现类
  - 注意：跨领域方法引用（如 addFkywDbfk 调用 createVoucher）需要建立领域 Service 间的依赖

Day 5: 旧 Service 瘦身 + 回归
  - 原 YwglServiceImpl 改为：所有方法委托给领域 Service
  - @Service("ywglService") 名称保留
  - 全量编译 + 回归测试
```

#### 循环依赖解除方案

```
现状: ywgl-busi ──→ cwhs-api ──→ zhgl-api ──→ ywgl-api (循环)

Step 1: 识别跨模块调用点
  - ywgl-busi 调用了 cwhs 的哪些方法？
  - cwhs-busi 调用了 ywgl 的哪些方法？
  - zhgl-busi 调用了 ywgl/cwhs 的哪些方法？

Step 2: 在调用方模块的 API 层定义 Facade 接口（依赖倒置）
  Example: ywgl-api 中定义 YwglCwhsFacade，由 cwhs-busi 实现

Step 3: 逐个替换直接依赖为 Facade 调用

Step 4: 解除原来 pom.xml 中的直接模块依赖
```

### 3.3 Phase 2 风险与应对

| 风险 | 概率 | 应对 |
|------|------|------|
| 跨领域方法拆分后事务边界问题 | 中 | 保持原 @Transactional 粒度，必要时使用编程式事务 |
| 字段/方法遗漏 | 中 | 编写单元测试对照原方法输入输出 |
| 领域 Service 间循环引用 | 低 | 提取公共逻辑到 shared 层 |

## 四、Phase 3：多地区多渠道策略化（Week 7-10）

> 目标：将 HSDWDM 判断从 55 个文件收敛到策略层，引入渠道策略。

### 4.1 任务分解

| 任务 | 工作内容 | 预估工时 | 产出 |
|------|---------|---------|------|
| **3.1 地区策略拆分** | 将 RegionBusinessStrategy 拆为 3-4 个领域特定策略接口 | **2 人天** | 细粒度策略 |
| **3.2 策略扩散覆盖** | 将 55 个文件中散落的 HSDWDM 判断迁移到策略实现中 | **4 人天** | HSDWDM 收敛 |
| **3.3 新增地区策略** | 评估枣庄/临沂/嘉兴是否需要独立策略，如有则创建 | **2 人天** | 新增策略 |
| **3.4 渠道策略引入** | 创建 SettlementChannel 策略层 + 实现 Yqzl/Zjb/Yht | **3 人天** | 渠道层 |
| **3.5 地区+渠道联动** | 地区策略决定使用什么结算渠道 | **2 人天** | 组合策略 |

### 4.2 Phase 3 实施策略

#### HSDWDM 收敛路径

```yaml
Step 1: 枚举所有 HSDWDM 引用点
  - 基于审计结果当前有 55 个文件包含 HSDWDM
  - 分类：哪些可以迁移到策略，哪些是业务必需的

Step 2: 先迁移"if (xxxHSDWDM)"条件分支
  - 如业务记账中的地区差异 → 迁移到 PaymentRegionStrategy
  - 如凭证生成中的科目差异 → 迁移到 VoucherRegionStrategy

Step 3: 再迁移"if (HSDWDM) header.set... "类代码
  - 如 ZJBWL 报头字段的地区差异 → 迁移到 ProtocolStrategy

Step 4: 最后迁移 Controller/JobHandler 中的 HSDWDM 引用
  - 如 YwglController 中直接引用 Constants.HSDWDM → 通过 @RequestHeader 传递
```

#### 渠道策略渐进式引入

```yaml
Step 1: 创建 SettlementChannel 接口 + YqzlSettlementChannel 实现
  - Yqzl 渠道已有 Socket 通信代码，直接包装

Step 2: 创建 ZjbSettlementChannel 实现
  - ZJB 渠道已有 RestTemplate 调用代码，直接包装

Step 3: 创建 YhtSettlementChannel 实现
  - 一户通已有 Feign 调用代码，直接包装

Step 4: 在 PaymentRegionStrategy 中注入 SettlementChannel
  - 地区维度和渠道维度解耦
  - 例如：WzStrategy 可以使用 ZjbChannel, DefaultStrategy 可以使用 YqzlChannel
```

### 4.3 Phase 3 风险与应对

| 风险 | 概率 | 应对 |
|------|------|------|
| 策略迁移后业务逻辑不一致 | 中 | 每个策略迁移后对比原逻辑的输入输出 |
| 渠道链路复杂影响现有功能 | 中 | 引入渠道策略后先在非核心业务验证 |

## 九、团队实施建议

### 9.1 团队分工

| 角色 | 数量 | 职责 |
|------|------|------|
| 架构师 | 1 人 | 设计方案评审、接口兼容把关 |
| 核心开发者 | 2-3 人 | Phase 2 上帝类拆分（最核心） |
| 开发者 | 2 人 | Phase 1 + Phase 3 策略迁移 |
| QA | 1 人 | 全量回归测试 |

### 9.2 编码规范（新增）

```yaml
# 禁止：
- 单个文件超过 500 行（Exception: 自动生成的代码）
- Controller 超过 20 个 @RequestMapping
- Controller 直接注入 RegionBusinessStrategy（通过 Service 层）
- 直接引用 Constants.HSDWDM（通过策略工厂）

# 强制：
- 新领域代码放在对应的 domain 包下，不允许放入 God Service
- 跨模块调用仅依赖 API 层（禁止 busi→busi）
- 新增策略时使用已存在的策略工厂模式
- 涉及地区差异的代码必须在策略实现中
```
