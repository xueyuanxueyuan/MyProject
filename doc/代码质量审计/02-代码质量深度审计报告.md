## 一、耦合度分析

### 1.1 模块间依赖拓扑 — 循环依赖警告

```
┌──────────────────────────────────────────────────────────────┐
│                   模块间循环依赖环                           │
│                                                              │
│    ywgl-busi ◄─────────────────────────────── cwhs-busi     │
│       │                                                     │
│       │ 依赖 zhgl-api + cwhs-api            │ 依赖 ywgl-api │
│       │ 还直接依赖 zbkh-busi (违反分层)      │ + zhgl-api    │
│       ▼                                                     │
│    zhgl-busi ──── 依赖 ywgl-api + cwhs-api ──►              │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

| 违反类型 | 具体表现 | 严重程度 |
|---------|---------|---------|
| **busi→busi 直接依赖** | `ywgl-busi` 直接依赖 `zbkh-busi`（非 API 层） | 🔴 严重 |
| **循环引用** | `ywgl-busi ←→ cwhs-busi ←→ zhgl-busi` 三者互为依赖 | 🔴 严重 |
| **单向过度耦合** | `ywgl-busi` 依赖 6+ 个其他模块的 API 层 | 🟡 中等 |
| **gm-agg 代理层脆弱** | gm-agg 对每个业务模块的 FeignClient 做 1:1 代理转发，业务层 API 变更直接波及聚合层 | 🟡 中等 |

### 1.2 上帝类反模式

| 文件 | 行数 | 注入的 Service/DAO | 方法数 | 评级 |
|------|------|-------------------|--------|------|
| `CwhsServiceImpl.java` | **21,633 行** | ~50+ 个 | ~200+| 🔴 上帝类 |
| `YwglServiceImpl.java` | **13,218 行** | ~60 个 | 394+| 🔴 上帝类 |
| `ZhglServiceImpl.java` | **4,884 行** | ~30 个 | ~100+| 🟡 大泥球 |
| `CwhsController.java` | **3,852 行** | 直接调用 Service | ~80+| 🟡 胖控制层 |

**典型症状（以 YwglServiceImpl 为例）**：
- 单一文件 `@Resource` 注入 **60+** 个 Service/DAO 依赖
- 同时承担：收付款处理、转账、一户通、网银、报表、日终处理、对账、凭证生成等全部职责
- 方法声明达 **394 个**（含私有方法），单一方法的平均行数难以控制
- 同时操作 **14 个数据表**（Fkyw, Skyw, YwJg, ZjLhhcx, Cwzjzf 等）

### 1.3 控制层过胖

| Controller | 行数 | @RequestMapping 数量 | 职责范围 |
|-----------|------|---------------------|---------|
| `YwglController` (V1) | **3,164 行** | **140+** 个 | 收/付款、转账、凭证、报表、黑名单、参数、渠道配置 |
| `CwhsController` (V1) | **3,852 行** | ~80+ 个 | 科目、凭证、模板、报表、审核、汇率 |
| `gm-agg/CwhsController` | **3,121 行** | ~70 个 | 代理原始CwhsController |
| `gm-agg/YwglController` | **2,251 行** | ~50 个 | 代理原始YwglController |

> **每个 Controller 违反单一职责原则**，一个 Controller 处理了 6+ 个业务领域。

## 二、代码冗余分析

### 2.1 V1 / V2 API 双版本冗余

| 模块 | V1 API 文件 | V2 API 文件 | 功能重叠度 |
|------|------------|------------|-----------|
| ywgl | `YwglController` (3,164行) | `YwglV2Controller` (671行) | **~70% 重复** |
| ywgl | `YwglFeignClient` (2,091行) | `YwglV2FeignClient` | **~60% 重复** |
| zhgl | `ZhglController` | `ZhglV2Controller` | **~80% 重复** |
| zhgl | `ZhglFeignClient` | `ZhglV2FeignClient` | **~70% 重复** |
| cwhs | `CwhsController` (3,852行) | `CwhsV2Controller` | **~60% 重复** |
| cwhs | `CwhsFeignClient` (2,604行) | `CwhsV2FeignClient` | **~60% 重复** |

**V1 vs V2 典型重复模式**（以 ywgl 为例）：
```
V1: /api/v1/ywgl/addFkywDbfk  →  YwglService.addFkywDbfk(...)
V2: /api/v2/ywgl/addFkywDbfk  →  YwglService.addFkywDbfk(...)
// ↑ 底层调用的 Service 方法完全一样，只是路由不同
```

**核心问题**：V2 并未引入新的业务逻辑实现，而是仅仅为了不同前端版本或地区提供不同路由路径。**如果改为统一的 API 网关路由映射，这 6 个文件可以完全合并。**

### 2.2 聚合层（gm-agg）代理冗余

gm-agg 模块的核心模式是为每个业务模块的 FeignClient 做 1:1 方法代理转发：
```java
// gm-agg YwglServiceImpl 典型代码
public R<Page<...>> queryYwlxSfgx(ReqDTO dto) {
    return ywglFeignClient.queryYwlxSfgx(dto); // 纯代理！
}
```

| gm-agg 文件 | 行数 | 纯代理转发占比 |
|------------|------|--------------|
| `YwglServiceImpl` (gm-agg) | 2,292 行 | ~95% |
| `CwhsServiceImpl` (gm-agg) | 2,964 行 | ~90% |
| `ZhglServiceImpl` (gm-agg) | 1,137 行 | ~95% |

> **结论**：gm-agg 模块 90%+ 的代码是"透传代理"，没有真实的业务逻辑。这部分代码可以用 AOP/统一网关路由方案替代。

### 2.3 FallbackFactory / Fallback 重复

每个 FeignClient 都附带一个 FallbackFactory + Fallback 类：
```
CwhsFeignClient (2,604行) + CwhsFallbackFactory (2,939行) + CwhsFeignClientFallback (2,932行) ≈ 8,475行
YwglFeignClient (2,091行) + YwglFallbackFactory (2,438行) + YwglFeignClientFallback (2,477行) ≈ 7,006行
```

**问题**：Fallback 代码占用了 **15,000+ 行**，几乎与主逻辑代码 1:1 体积比。且 Fallback 是模板化的（基本是 return R.fail()），完全可以通过统一降级策略或 sentinel 规则替代。

## 三、多地区适配成熟度评估

### 3.1 现有策略模式

系统已有 **`RegionBusinessStrategy`** 策略模式雏形：

| 组件 | 说明 | 成熟度 |
|------|------|-------|
| `RegionBusinessStrategy` 接口 | 定义了 processBusinessAccounting / tzYwjz / fkywJssbCl / skywJssbCl | ✅ 好 |
| `RegionBusinessStrategyFactory` | 基于 HSDWDM 注册和获取策略 | ✅ 好 |
| `WzStrategy` | 温州地区特有逻辑（HSDWDM=330300000000000） | ✅ 好 |
| `DefaultRegionStrategy` | 默认城市通用逻辑（北京、临沂等） | ✅ 可用 |
| `WzApiConfig` | 温州地区 API 配置 | ✅ 可用 |

### 3.2 不足之处

| 问题 | 详情 | 影响面 |
|------|------|-------|
| **策略粒度太粗** | 一个策略接口覆盖所有业务方法，没有按业务域拆分（收付款策略、账户策略、转账策略） | 策略实现类会膨胀成小上帝类 |
| **HSDWDM 判断散落** | **55 个文件**中散布了 HSDWDM 地区判断，包括 Controller、ServiceImpl、JobHandler、Validator | 改一个地区的逻辑需涉及多个模块 |
| **策略覆盖不全** | 仅对"业务记账"类方法使用策略模式，财务模块(Cwhs-Jzgl)完全没有使用策略模式 | 财务模块直接用 if-else 区分地区 |
| **多渠道未建模** | 结算渠道(Jsqd枚举)定义了银企直联/住建部平台/一户通，但没有对应的渠道策略模式 | 渠道差异化逻辑散落在各个 ServiceImpl 中 |
| **移动端渠道特殊** | `YdchdOpenController` 单独开了一个 `/open/api/loan` 路径 | 渠道入口混乱 |

## 六、审计结论

### 核心问题排序（按 ROI 优先）

1. **🔴 上帝类拆分**（CwhsServiceImpl + YwglServiceImpl → 按领域拆分为 6~8 个领域服务）—— 最大收益
2. **🔴 解除循环依赖**（引入防腐层/API 网关）—— 架构安全
3. **🟡 V1/V2 合并**（路由归一化，消除双版本）—— 快速见效
4. **🟡 策略模式推广**（将 HSDWDM 判断从 55 个文件收敛到策略实现中）—— 持续增益
5. **🟡 渠道层引入**（Jsqd 枚举 → 渠道策略模式 + 渠道 SPI）—— 架构前瞻
6. **🟢 聚合层消除**（gm-agg 代理层 → 统一网关）—— 立竿见影
7. **🟢 Fallback 统一降级**（消除 15,000 行模板代码）—— 立竿见影
