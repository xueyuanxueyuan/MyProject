## 2. 已确认漏洞

### 2.1 高危：未鉴权回调接口可被外部用户利用为 SSRF，并可回读内部响应

| 项 | 内容 |
|---|---|
| 影响等级 | 高危 |
| 攻击者画像 | 可访问 `yht-mock-server` 网络端口的外部用户 |
| 输入向量 | `POST /yht-mock/api/trigger-callback` 中的 `targetUrl`；或 `POST /yht-mock/api/callback-config` 中的 `defaultTargetUrl` |
| 关键位置 | `yht-mock-server/src/main/java/cn/capinfo/gjj/yhtmock/controller/YhtMockApiController.java`；`yht-mock-server/src/main/java/cn/capinfo/gjj/yhtmock/service/MockCallbackService.java`；`yht-mock-server/src/main/java/cn/capinfo/gjj/yhtmock/service/MockStoreService.java` |
| 结果影响 | 可向任意 URL 发起服务器端 POST 请求，探测/访问内网服务，并通过开放日志接口读取返回内容 |

**端到端利用路径**

1. 攻击者向 `POST /yht-mock/api/trigger-callback` 提交自定义 `targetUrl`。
2. `YhtMockApiController.triggerCallback()` 直接将 `request.targetUrl` 传入 `MockCallbackService.triggerManualCallback()`。
3. `MockCallbackService.triggerManualCallback()` 在未做白名单、协议限制、地址过滤的情况下调用 `push(...)`。
4. `MockCallbackService.push()` 使用 `HttpRequest.newBuilder(URI.create(targetUrl))` 向攻击者指定地址发起 POST 请求。
5. 请求结果被写入 `MockRecord.responseBody`，再经 `MockStoreService.addRecord()` 持久化。
6. 攻击者随后调用 `GET /yht-mock/api/logs`，即可读取对应 `CALLBACK` 记录中的 `status`、`target`、`responseBody`。

**证据点**

- `YhtMockApiController.triggerCallback()` 直接接收并转发 `targetUrl`。
- `MockCallbackService.triggerManualCallback()` 直接信任 `targetUrl` 或配置中的 `defaultTargetUrl`。
- `MockCallbackService.push()` 直接使用 `URI.create(targetUrl)` 组装并发送 HTTP 请求。
- `YhtMockApiController.logs()` 公开返回 `storeService.listRecords(limit)`。

**可验证利用示例**

```http
POST /yht-mock/api/trigger-callback
Content-Type: application/json

{
  "callbackMesgType": "caps.205.001.01",
  "targetUrl": "http://127.0.0.1:8080/actuator/health"
}
```

随后访问：

```http
GET /yht-mock/api/logs?limit=10
```

即可在最新 `CALLBACK` 记录中读取对内网目标的访问结果。

**修复建议**

1. 为 `yht-mock/api/**` 增加强制认证和最小权限控制，至少将管理接口限定为受信用户访问。
2. 对回调目标实施严格白名单，仅允许预配置的业务域名或固定主机。
3. 拒绝 `localhost`、环回地址、链路本地地址、RFC1918 私网地址及非常规协议。
4. 不要通过公开日志接口暴露下游响应体；如确需留痕，应脱敏并限制仅管理员可读。

### 2.2 高危：未鉴权管理接口泄露敏感配置与完整交互报文

| 项 | 内容 |
|---|---|
| 影响等级 | 高危 |
| 攻击者画像 | 可访问 `yht-mock-server` 网络端口的外部用户 |
| 输入向量 | `GET /yht-mock/api/callback-config`、`GET /yht-mock/api/logs`、`GET /yht-mock/api/protocols`、`GET /yht-mock/api/trades`、`GET /yht-mock/api/batches` |
| 关键位置 | `yht-mock-server/src/main/java/cn/capinfo/gjj/yhtmock/controller/YhtMockApiController.java`；`yht-mock-server/src/main/java/cn/capinfo/gjj/yhtmock/model/MockSettings.java`；`yht-mock-server/src/main/java/cn/capinfo/gjj/yhtmock/model/MockRecord.java` |
| 结果影响 | 泄露 HSM 模拟密钥、默认回调目标、交易报文、签名/验签输入输出、回调响应内容等敏感数据 |

**端到端利用路径**

1. 攻击者直接访问 `GET /yht-mock/api/callback-config`。
2. `YhtMockApiController.callbackConfig()` 直接返回 `storeService.getSettings()`。
3. `MockSettings` 包含 `hsmMockKey`、`defaultTargetUrl` 等敏感配置字段。
4. 攻击者再访问 `GET /yht-mock/api/logs`。
5. `YhtMockApiController.logs()` 直接返回 `MockStoreService.listRecords(limit)` 的完整记录。
6. `MockRecord` 中包含 `requestBody`、`responseBody`、`target`、`reqId`、`sysSeqNo` 等敏感字段，可直接泄露交互细节。

**证据点**

- `MockSettings.hsmMockKey` 明确作为公开接口返回字段存在。
- `MockRecord` 结构公开暴露请求体和响应体。
- `MockStoreService.addRecord()` 会持久化 HSM/GATEWAY/CALLBACK 全量记录到 `data/mock-state.json`。
- 当前仓库中的 `data/mock-state.json` 已存在历史签名、交易、回调记录样例。

**影响说明**

- 攻击者可获取 `hsmMockKey` 与历史 HSM 输出，降低伪造测试签名、复现业务报文的门槛。
- 攻击者可读取批量交易、协议、回调报文及返回内容，造成测试环境业务数据与联调数据外泄。
- 这些信息还能作为上一个 SSRF 漏洞的响应回显通道，进一步扩大影响面。

**修复建议**

1. 将管理接口整体置于认证保护之后，按只读/写入操作区分权限。
2. `MockSettings` 不应直接序列化返回全部字段，至少移除 `hsmMockKey` 等敏感项。
3. `MockRecord` 输出时应默认脱敏 `requestBody`、`responseBody`、账号、流水号等字段。
4. 对历史持久化文件增加访问控制和定期清理策略，避免长期保留明文敏感数据。

### 2.3 中危：未鉴权 HSM 模拟接口提供签名与解密 Oracle

| 项 | 内容 |
|---|---|
| 影响等级 | 中危 |
| 攻击者画像 | 可访问 `yht-mock-server` 网络端口的外部用户 |
| 输入向量 | `POST /yht-mock/api/hsm/sign`、`/verify`、`/encrypt`、`/decrypt` |
| 关键位置 | `yht-mock-server/src/main/java/cn/capinfo/gjj/yhtmock/controller/HsmMockController.java`；`yht-mock-server/src/main/java/cn/capinfo/gjj/yhtmock/service/HsmMockService.java` |
| 结果影响 | 未授权用户可直接获取签名结果、解密任意提交密文，破坏该模拟 HSM 所提供的保密性与完整性边界 |

**端到端利用路径**

1. 攻击者直接向 `POST /yht-mock/api/hsm/sign` 提交待签名数据。
2. `HsmMockController.sign()` 无鉴权地调用 `HsmMockService.sign(...)`。
3. `HsmMockService.sign()` 使用内部 `hsmMockKey` 生成签名并在响应体返回。
4. 对于解密场景，攻击者可调用 `POST /yht-mock/api/hsm/decrypt`，`HsmMockService.decrypt()` 会返回明文。

**影响说明**

- 在任何把该服务当作 HSM/签名服务使用的测试、联调或共享环境中，外部用户都能直接调用签名与解密能力。
- 即使这是“mock”实现，这类接口一旦暴露到共享网络，仍会破坏与其交互系统对签名来源和数据保密性的基本假设。

**修复建议**

1. 对 HSM 模拟接口启用认证，并限制来源网段或通过网关白名单访问。
2. 若仅供本地联调，默认绑定 `127.0.0.1` 或开发专网，不对共享网络开放。
3. 明确区分“调试接口”和“受控模拟服务”，避免在共享环境暴露签名/解密能力。

## 3. 未纳入最终结论的排查项

## 4. 审计结论

本次在 `yht-mock-server` 中确认 **2 个高危漏洞**、**1 个中危漏洞**，共同根因是：**对外暴露的挡板/管理/HSM 接口完全缺乏认证授权与最小暴露控制**。建议优先按以下顺序整改：

1. 立即为 `yht-mock-server` 全部管理与 HSM 接口加鉴权。
2. 立即限制回调目标地址白名单，封堵 SSRF。
3. 立即收紧日志与配置接口的敏感字段输出。
4. 复核该服务在测试/联调环境中的暴露范围，必要时改为仅内网或本机可访问。
