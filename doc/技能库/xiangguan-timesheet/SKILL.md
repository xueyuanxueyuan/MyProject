# 象管精灵工时填报技能

## 用途

`xiangguan-timesheet` 用于把“打开象管精灵、匹配当日项目、填写工时并提交校验”沉淀为一套可复用流程。

本技能不只是打开页面点击提交，而是把以下几个关键环节标准化：

- 浏览器桥接方式选择
- 登录/验证码的人机接管边界
- 当日代码与操作记录的项目归集
- 工时内容的精简生成
- 提交后的页面结果校验

## 适用场景

- 用户要求“打开象管精灵”“填写今天工时”“补填工时”“按今天改动填工时”
- 用户给出 `https://gs.capinfo.com.cn/pc/index.html#/index` 或要求登录象管精灵后提交工时
- 用户要求基于当日代码修改、发布记录、文档记录来匹配项目填报

## 依赖关系

执行本技能时，优先按以下顺序组合已有能力：

1. `cli-anything-local-tools`
   - 用于判定本机浏览器桥接方式是否需要先做路径/版本/帮助探测
2. `tencent-novnc-chromium-cdp`
   - 当用户明确要求“本机浏览器 + CDP 接管”时优先参考
3. `integrated_browser` MCP
   - 当前工作区下最直接的网页自动化执行通道

## 核心原则

### 1. 先判定，再提交

在真正写工时前，必须先判断：

- 是否已登录
- 是否存在验证码
- 当日修改是否能明确映射到单一项目
- 用户是否已经给出总工时和拆分方式

### 2. 不猜测验证码

- 账号、密码、验证码登录场景，允许自动打开页面与识别状态
- 一旦遇到验证码或必须人工确认的登录动作，必须暂停自动化并交由用户接管
- 严禁伪造“已自动登录”或尝试自动识别验证码

### 3. 不在项目拆分不明确时擅自提交

若存在以下任一情形，必须先向用户确认：

- 当日工作同时覆盖多个项目，且无法根据记录唯一归集
- 总工时未明确
- 需要区分项目工时与内管工时
- 工作类型不是默认的“系统开发”

### 4. 默认记录风格要简洁

若用户未给出特殊要求，工时日志默认采用：

- `3` 到 `5` 行
- 每行一句
- 简洁明了
- 既覆盖主要工作，又不过度堆砌细节

## 标准流程

### 1. 浏览器与页面准备

- 打开 `https://gs.capinfo.com.cn/pc/index.html#/index`
- 若当前落在登录页，则识别是否需要用户手动完成登录
- 操作前先获取页面快照，确认当前页签、菜单和按钮状态

### 2. 登录接管

若页面要求：

- 账号/密码
- 验证码
- 其他人工识别或人工确认动作

则必须：

1. 自动化停在登录节点
2. 明确提示用户接管浏览器完成登录
3. 用户确认“已登录”后，再继续工时填报流程

### 3. 当日工作归集

优先从以下来源归集今天的实际工作：

1. 当前仓库 `git status` / `git diff`
2. 当日 `doc/操作记录/` 下的 Markdown 记录
3. 当日新增或修改的配置、脚本、代码文件
4. 必要时参考最近会话记忆中的当日任务摘要

归集时重点提取：

- 项目名称
- 模块/服务名称
- 工作类型倾向
- 构建、发布、联调、修复等动作

### 4. 项目匹配规则

优先按“记录事实”而不是“主观印象”匹配工时项目。

建议按以下优先级判断：

1. 用户明确指定的项目
2. 当日修改记录中最集中、最明确的业务项目
3. 工时弹窗中可选项目名称与当日记录的语义匹配结果
4. 若仍有歧义，则暂停并向用户确认

### 5. 工作类型选择

若用户未明确指定，默认优先使用：

- `系统开发`

仅在有明确依据时再改为：

- `文档编写`
- `实施/部署/交付`
- `系统运维`
- 其他类型

### 6. 日志生成

日志内容应根据当日记录提炼成 3 到 5 行摘要，优先覆盖：

- 核心代码修复或开发点
- 前后端联调或参数修复
- 脚本/配置/自动化能力增强
- 构建、发布、重启、验收等闭环动作

### 7. 页面填写

进入“我的工时”后，按以下步骤执行：

1. 定位当日日期行
2. 打开“提交工时”弹窗
3. 只填写与本次匹配项目对应的那一行
4. 录入工作类型、小时数和日志内容
5. 其余项目行保持未填写或 `0`
6. 确认表单校验通过后再提交

### 8. 提交后校验

提交后必须回到周视图或列表视图做二次验证。

至少确认以下字段：

- 工时是否显示为目标值，例如 `12H`
- 填报状态是否为 `已填报`
- 审核状态是否出现，例如 `待审核`

若页面未显示这些结果，不得直接声称成功。

## 推荐交互策略

### 可以直接执行

- 用户已明确总工时
- 项目归属单一且清晰
- 工作类型明确或可按默认 `系统开发`

### 必须先追问

- 用户只说“帮我填工时”，但没说总时长
- 当日工作明显分属多个项目
- 同时存在业务项目与内管项目
- 页面项目列表与当日记录无法可靠对应

## 风险边界

- 不自动识别验证码
- 不在项目归属不清时强行提交
- 不在用户未明确总工时的情况下猜测数值
- 不把“页面打开成功”当作“工时提交成功”
- 不覆盖用户已明确给出的项目拆分方案

## 结果回报要求

执行完成后，至少汇报：

- 已填报的项目
- 工时数
- 工作类型
- 页面校验结果
- 留痕文档路径
