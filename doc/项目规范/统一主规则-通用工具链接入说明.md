# 统一主规则通用工具链接入说明

## 1. 目标
- 本文件是当前仓库面向其他 AI 工具的唯一通用接入说明。
- 目标是让其他工具在读取本文件后，优先参考 `doc/入口文件样例/` 中的已验证样例，生成自己的项目入口文件，并尽量复现当前工作区的默认调用方式。
- 若目标工具不支持自动生成入口文件，也应把本文件直接作为项目级主规则使用。

## 2. 标准源与样例
- **唯一标准源**：`doc/项目规范/统一主规则-通用工具链接入说明.md`
- **入口文件样例目录**：`doc/入口文件样例/`
- **通用技能入口模板**：`doc/通用模板/技能入口统一模板.md`
- **当前样例文件**：
  - `doc/入口文件样例/CLAUDE.md`
  - `doc/入口文件样例/.trae/rules/edict-workflow.md`
  - `doc/入口文件样例/.trae/rules/anti-laziness-anti-hallucination.md`
  - `doc/入口文件样例/.trae/rules/workspace-common.md`

## 3. 接入方式

### 3.1 支持自动或半自动生成入口文件的工具
- 请先读取本文件，再读取 `doc/入口文件样例/` 中的对应样例文件。
- 生成本工具自己的入口文件时，优先复用样例的结构、字段和职责边界，而不是自行重新发明一套入口格式。
- 生成后应做防遗漏自检，确认默认工作流、三省六部、交付门禁、项目主源关系和结果复核都没有缺失。

### 3.2 只支持加载单文档规则的工具
- 直接加载本文件，并将本文件视为项目级主规则。
- 若工具无法写入口文件，应在行为上模拟本文件所要求的默认流程和门禁。

### 3.3 支持多入口结构的工具
- 本文件负责声明完整规则。
- 具体入口文件应尽量参考样例目录中的同类文件生成，不要在多个入口里重复展开整套长正文。
- 若目标工具还支持“技能入口”“子能力入口”或“桥接技能文档”，应优先参考 `doc/通用模板/技能入口统一模板.md` 生成对应入口。

## 4. 工具必须接入的默认调用方式

### 4.1 默认工作流
- 实质性任务默认先进入 `Edict` 工作流，再并行启用防偷懒/防撒谎门禁；临近交付时默认联动最终验证闭环。
- `Edict` 已吸收 `using-superpowers` 的总控能力：先判技能后行动、先流程技能再实现技能再基础工具、checklist 必须转为可验证任务。
- 实质性任务包括：开发、缺陷修复、重构、规则或脚本编写、影响面分析、代码评审、文档落地、多步骤分析，以及任何准备宣告“已完成”“已修复”“已通过”“已验证”的回复。

### 4.2 三省六部执行语义
- **太子**：先判定闲聊或正式任务；正式任务先给出流程技能路由建议，禁止绕过技能判定直接开工。
- **中书省**：先拆任务，再执行；默认拆为 3 步以上可验证子任务，并把流程技能、checklist、阶段门禁、执行模式写入计划。
- **门下省**：在执行前审查规则、记忆、技能完备性与执行模式；高风险操作必须请求用户批准；发现缺少验证闭环或明显跳流程时必须驳回。
- **尚书省**：先调度流程技能，再调度实现技能和基础工具；只在任务相互独立时并行派发；负责监督检查点真正落地。
- **六部**：技能与记忆、资源与工具链、文档留痕、部署、质控、编码分工必须保留。
- 调用 `edict-triage`、`edict-planning`、`edict-review` 等三省流程技能后，必须在紧随其后的对用户可见回复中，显式按该技能 `输出规范` 回显对应 Markdown 规范块；仅调用技能工具而未回显，不算完成该环节。
- 若已调用流程技能却仍使用自然语言进度更新替代规范块，视为未按三省六部规范执行；可在规范块之后追加简短说明，但不得省略规范块本身。

### 4.3 默认流程路由
- 新需求、行为调整、方案讨论：优先 `brainstorming`
- Bug、测试失败、异常行为：优先 `systematic-debugging`
- 新功能或缺陷修复进入编码：优先 `test-driven-development`
- 需要隔离环境或新分支执行：优先 `using-git-worktrees`
- 已有成文计划：优先 `executing-plans`
- 当前会话内按计划拆块开发：优先 `subagent-driven-development`
- 2 个以上独立子任务：优先 `dispatching-parallel-agents`
- 关键阶段完成或合并前：优先 `requesting-code-review`
- 收到评审意见：优先 `receiving-code-review`
- 准备宣告完成：优先 `verification-before-completion`

## 5. 项目通用规范
- 所有任务必须优先阅读 `doc` 目录下相关文档。
- `doc/项目规范` 是项目规范主源；`doc/提示词` 是任务模板与输出模板；`doc/技能库` 是技能主源。
- 若项目中存在多个技能入口副本，应以 `doc/技能库` 为归档和理解主源。
- 涉及编译、打包、发布或工具链切换时，必须同时遵守项目规范和对应技能说明。
- 代码必须符合对应语言与框架规范，包括 Java、Vue、TypeScript、JavaScript。
- Git 提交规范属于跨项目通用规范，统一以 `doc/通用模板/Git提交描述模板.md` 为模板主源，不能作为某个具体项目专属约束单独维护。
- 提交前必须先同步远端主线并处理冲突，再执行本地提交，避免把冲突遗留到后续环节。
- 提交标题必须使用 `feat|fix|docs: 具体标题（AI生成提交）` 格式；若属于其他类型提交，可将 `feat|fix|docs` 替换为实际类型，但 `（AI生成提交）` 后缀必须保留。
- 提交描述必须固定包含 `AI辅助：true`、`AI工具：Trae`、`1. 改了什么`、`2. 为了解决什么问题`，且顺序不得调整。
- 提交标题与描述必须具体、可审计，禁止使用“修复问题”“优化代码”“调整一下”等空泛表述。

## 6. 交付门禁
- 先查证：先读相关文档、规则、技能、目标文件和现状实现，禁止凭记忆下结论。
- 先拆解：先明确验证方式，再实施；技能中的 checklist 和检查点必须落入可验证任务。
- 禁占位：禁止 `TODO`、`...`、空实现、伪代码占位和把应完成工作转嫁给用户。
- 无验证不报喜：任何成功表述前必须完成最新验证并核对结果；测试、构建、修复、子代理成功均不得口头认定。
- 真实兜底：无法确认时只能明确写“未验证”“仅完成局部验证”“无此数据”等真实状态。

## 7. 最终验证与结果复核
- 任何“已完成”表述前，至少执行一次等价于 `scripts/guardrails/agent-delivery-guardrail.sh --scan-only` 的守卫扫描。
- 需要声称测试、构建或检查通过时，必须执行真实验证命令，并核对输出、退出码与失败数。
- 子代理、自动化工具、脚本或外部执行器的“成功”只是线索，不是事实；对外汇报前必须复核实际改动、diff、输出与结果证据。

## 8. 防遗漏检查清单
- 是否保留了 `Edict + anti-laziness + verification` 的联动关系。
- 是否保留了三省六部角色分工。
- 是否明确要求并实际回显了 `edict-triage`、`edict-planning`、`edict-review` 的规范输出块。
- 是否保留了流程技能路由优先级。
- 是否保留了 `doc/项目规范` / `doc/提示词` / `doc/技能库` 的主源关系。
- 是否保留了交付门禁、真实验证和结果复核要求。
- 是否明确用户指令优先级最高。
- 是否避免在多个入口重复展开整套长正文。

## 9. 可直接交给其他工具的生成指令

```md
请将《统一主规则通用工具链接入说明》视为当前仓库的唯一标准源。

执行要求：
1. 先读取本文件，再读取 `doc/入口文件样例/` 中与当前工具最接近的样例文件。
2. 基于样例生成当前工具自己的项目入口文件，而不是自行重新设计入口结构。
3. 生成的入口文件必须保留当前工作区的默认调用方式：
   - 实质性任务默认先走 Edict
   - 再并行执行交付门禁
   - 交付前必须最终验证
4. 调用 `edict-triage`、`edict-planning`、`edict-review` 等流程技能后，必须在对用户可见的回复中显式输出该技能规定的 Markdown 规范块；不得只调用技能而不回显。
5. 不得遗漏三省六部、流程技能路由、项目通用规范、交付门禁、结果复核、优先级。
6. 若工具无法写入口文件，则直接把本文件作为项目级主规则执行。
7. 生成或接入完成后，按“防遗漏检查清单”逐项自检并汇报。
```

## 10. 真实性说明
- 本文件解决的是“如何以标准源 + 样例目录的方式稳定迁移规则体系”，不是保证所有工具都具备真正的自动写文件能力。
- 如果某工具可以读文档但不能写入口文件，它仍然可以直接把本文件当作项目主规则使用。
- 如果某工具既能读文档又能写项目入口，则应优先按本文件和样例目录派生入口文件，避免人工重写漏规则。
