# 版本管理策略说明_枣庄项目_凭证汇总_V1.0

## 1. 目标
- 为枣庄“凭证汇总改造”建立可审计、可灰度、可回退的版本管理机制。
- 保证功能分支与主线隔离，避免将环境脏改动、其他模块改动混入本次交付。

## 2. 分支策略

### 2.1 分支角色
| 分支 | 作用 | 说明 |
| --- | --- | --- |
| `zaozhuang/dev` | 区域开发主线 | 日常功能集成主线，不直接承载未验证的大改 |
| `zaozhuang/dev-凭证汇总修改` | 功能隔离分支 | 本次凭证汇总改造专用分支，按原子提交推进 |
| `backup/*` | 回退前备份分支 | 回退操作前临时创建，用于保底 |

### 2.2 分支隔离要求
- 所有凭证汇总改造代码必须先进入 `zaozhuang/dev-凭证汇总修改`，不得直接在 `zaozhuang/dev` 上裸改。
- 原始脏仓中与本功能无关的环境配置、其他系统模块改动，不得带入本功能分支。
- 合并回主线前，必须先完成：
  - 提交粒度检查
  - 编译验证
  - 回退方案准备
  - 文档留痕

## 3. 提交策略

### 3.1 原子提交要求
- 每笔提交只覆盖一个清晰职责：
  - 字段与落库映射
  - 生成链路注入
  - 汇总口径改造
  - 区域灰度配置
- 同一提交内应包含该职责需要的最小闭环内容。
- 不允许把“功能代码 + 无关环境配置 + 其他模块改动”混成一笔。

### 3.2 提交模板
- 提交标题使用：
  - `feat|fix|docs: 具体标题（AI生成提交）`
- 提交描述必须包含：
  - `AI辅助：true`
  - `AI工具：Trae`
  - `1. 改了什么`
  - `2. 为了解决什么问题`

## 4. 发布与灰度策略

### 4.1 灰度顺序
1. 先发布代码，但控制区域配置开关。
2. 再启用 `voucher.summary.byYwfl` 等灰度配置。
3. 观察回退率、空值归并率、汇总结果一致性。
4. 稳定后再合入主线或扩大范围。

### 4.2 配置策略
- 与业务功能强绑定的灰度配置，应作为独立原子提交维护。
- 默认区分：
  - 通用默认配置：`application.yml`
  - 区域启用配置：`application-city-zaozhuang.yml`
- 若区域配置文件中混有无关环境地址变更，必须拆分，只提交本功能直接相关的键。

## 5. 回退触发条件
- 测试发现严重缺陷，且无法在短时间热修复。
- 汇总口径错误，导致金额或附件数统计不可信。
- 新配置开启后，业务失败率明显上升。
- 映射回退率、空值归并率超过业务允许阈值。
- 业务需求发生变化，需要临时恢复旧版行为。

## 6. 回退审批流程

### 6.1 审批分级
| 回退范围 | 审批要求 |
| --- | --- |
| 仅回退灰度配置 | 项目开发负责人审批 |
| 回退汇总口径代码 | 技术负责人审批 |
| 回退生成链路/字段映射 | 技术负责人审批 |
| 数据库结构回滚 | 技术负责人 + DBA + 业务负责人联合审批 |

### 6.2 标准流程
1. 提出回退申请，说明问题现象、影响范围、目标回退点。
2. 技术负责人判断是“配置回退”还是“代码回退”。
3. 回退前创建备份分支。
4. 执行 `git revert` 或配置回滚。
5. 执行最小验证并留痕。
6. 通知业务方与相关开发确认结果。

## 7. 操作日志要求
- 每次回退必须记录：
  - 操作人
  - 操作时间
  - 回退原因
  - 目标提交
  - 审批人
  - 执行命令
  - 验证结果
- 建议统一落到 `doc/操作记录`，命名应包含日期、项目、动作主题。

## 8. 验证门禁
- 任何“已回退成功”“已恢复正常”结论前，必须有最新验证证据。
- 至少执行：
  - `scripts/guardrails/agent-delivery-guardrail.sh --scan-only`
  - 必要的编译命令或功能验证命令
- 若验证受已有历史问题阻塞，必须明确写“验证受阻”与真实阻塞点，不得伪装通过。

## 9. 本次功能建议执行模型
- 开发阶段：`zaozhuang/dev-凭证汇总修改`
- 提交阶段：按 4 笔原子提交推进
- 上线阶段：先代码、后区域配置
- 故障阶段：优先配置回退，再考虑代码回退，最后才评估数据库回滚
