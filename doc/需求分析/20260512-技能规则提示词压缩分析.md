# 技能、规则、提示词压缩分析

## 1. 目标
- 在不降低现有能力、不改变触发效果、不破坏主从关系的前提下，压缩当前工作区中 `技能`、`规则`、`提示词` 的重复描述，减少智能体会话中的 token 消耗。
- 本文仅基于当前仓库现状进行分析，优先识别“高收益、低风险”的压缩点。

## 2. 当前结构判断

### 2.1 主源与入口
- `doc/技能库/`：完整技能主源，适合作为能力正文归档。
- `.trae/skills/`：Trae 发现入口，适合保留轻量镜像，不适合维护大段正文。
- `doc/项目规范/`：项目规范正文主源。
- `.trae/rules/`：会话级硬规则入口，越短越划算，因为更容易被频繁注入上下文。
- `doc/提示词/`：任务模板与专项提示词，适合保留“场景差异”，不适合重复抄写规范正文。
- `CLAUDE.md`：仓库级入口规则，属于高价值压缩对象。

### 2.2 token 消耗类型
- 高常驻成本：
  - `CLAUDE.md`
  - `.trae/rules/*.md`
  - 长期记忆
  - 用户级规则
- 中等按需成本：
  - `doc/提示词/*.md`
  - `doc/项目规范/*.md`
- 低频按需成本：
  - `doc/技能库/` 下的长技能正文与参考资料

结论：
- 真正优先压缩的不是所有文档，而是“每次更容易被注入的入口规则”与“重复蒸馏的提示词”。

- 对 token 成本影响最大的，是其中被系统规则、习惯流程或默认读取路径高频命中的那部分。

### 3.2 重复最严重的主题

- `doc/技能库` 与 `.trae/skills` 的同名双副本

## 4. 重复源分析

### 4.1 防偷懒链路重复
同一组约束同时出现在以下位置：
- `CLAUDE.md`
- `.trae/rules/anti-laziness-anti-hallucination.md`
- `.trae/rules/workspace-common.md`
- `doc/技能库/anti-laziness-anti-hallucination/SKILL.md`
- `doc/技能库/verification-before-completion/SKILL.md`
- `doc/项目规范/AI-Agent-防偷懒防撒谎-跨工具接入说明.md`

重复内容主要包括：
- 实质性任务默认启用
- 先查证再动手
- 先拆解再实施
- 禁止占位交付
- 无验证不报喜
- 无法确认必须如实说明
- guardrail 脚本使用要求

判断：
- 这组内容确实重要，但现在的重复方式属于“多处全文重写”，不是“入口引用主源”。
- 这是压缩收益最高的一组。

### 4.2 Edict 流程重复
重复位置：
- `.trae/rules/edict-workflow.md`
- `doc/技能库/edict-triage/SKILL.md`
- `doc/技能库/edict-planning/SKILL.md`
- `doc/技能库/edict-review/SKILL.md`
- `doc/技能库/edict-dispatch/SKILL.md`

问题：
- 总规则写了一遍流程，分技能又分别把流程再写一遍。
- 若未来维护，极易产生“总规则更新了，分技能忘记更新”的漂移。

### 4.3 前端规范重复
重复位置：
- `doc/项目规范/Gjj项目组开发规范.md`
- `doc/项目规范/项目开发规范.md`
- `doc/提示词/capinfo-gjj-frontend-jshs-gm前端开发提示词.md`
- `doc/提示词/Gjj项目组前后端项目开发提示词.md`

问题：
- `项目开发规范.md` 已声明正文并入总规范，但仍保留较长摘要。
- 前端专项提示词与前后端总提示词都重复了大量目录分层、HTTP 约束、组件复用、自检要求。

### 4.4 提示词重复
重复位置：
- `doc/提示词/Gjj项目组开发提示词.md`
- `doc/提示词/Gjj项目组前后端项目开发提示词.md`
- `doc/提示词/capinfo-gjj-frontend-jshs-gm前端开发提示词.md`

问题：
- 三份提示词都在重复写“先分析模块/目录/分层/SDD/验证/输出格式”。
- 这些本应由项目规范和入口规则负责，提示词只需要保留“场景差异”和“输出模板”。

## 5. 压缩原则

### 5.1 单一正文原则
- 同一组规则只能有一个正文主源。
- 其余文件只保留：
  - 触发条件
  - 必守硬约束
  - 主源路径
  - 当前工具环境差异

### 5.2 入口最短原则
- `CLAUDE.md`
- `.trae/rules/*.md`
- `.trae/skills/*/SKILL.md`

以上文件优先短化，因为它们更接近“系统入口”。

### 5.3 提示词只保留差异
- 提示词不再重复解释完整规范。
- 提示词应只保留：
  - 任务场景
  - 当前任务的特殊约束
  - 输出模板
  - 必要引用入口

### 5.4 主源保留完整
- `doc/技能库/`
- `doc/项目规范/`

这两类目录可以保留完整说明，因为它们承担归档、评审、沉淀职责。

## 6. 建议压缩方案

### 6.1 第一优先级：压缩会话入口规则
建议处理：
- `CLAUDE.md`
- `.trae/rules/anti-laziness-anti-hallucination.md`
- `.trae/rules/workspace-common.md`

建议方式：
- 保留“何时触发 + 必守底线 + 主源路径”。
- 删除长段解释性正文。
- 把五道门禁的详细说明下沉到 `doc/技能库/anti-laziness-anti-hallucination/SKILL.md`。

预期收益：
- 这是最直接减少常驻 token 的改法。

### 6.2 第二优先级：压缩提示词层
建议处理：
- `doc/提示词/Gjj项目组开发提示词.md`
- `doc/提示词/Gjj项目组前后端项目开发提示词.md`
- `doc/提示词/capinfo-gjj-frontend-jshs-gm前端开发提示词.md`

建议方式：
- 保留一份“主提示词”作为总入口。
- 其余提示词改成：
  - 场景差异补充
  - 特殊输出模板
  - 项目特异约束
- 删除与总规范重复的分层、命名、验证长列表。

预期收益：
- 降低每次手工读取提示词时的上下文占用。
- 降低维护成本。

### 6.3 第三优先级：完成前端规范去重
建议处理：
- `doc/项目规范/项目开发规范.md`

建议方式：
- 只保留：
  - 适用项目
  - 统一入口
  - 当前项目特有差异
- 删除已并入总规范的重复章节摘要。

### 6.4 第四优先级：统一技能镜像策略
建议处理：
- `.trae/skills/*/SKILL.md`

建议方式：
- 统一成“轻量镜像模板”：
  - 一句能力说明
  - 触发场景
  - 主源位置
- 不在 `.trae/skills` 维护长正文。

说明：
- 你当前的 `anti-laziness-anti-hallucination` 已经基本采用这个策略。
- 可以把其他同名技能也统一成同一模式。

## 7. 不建议优先压缩的部分
- `doc/技能库/writing-skills/anthropic-best-practices.md`
- `doc/技能库/brainstorming/visual-companion.md`
- `doc/技能库/systematic-debugging/*`
- `doc/技能库/test-driven-development/*`

原因：
- 这些大文件虽然长，但通常按需读取，不是每次会话都强制注入。
- 直接压缩正文可能损失参考价值，收益不一定高于风险。

## 8. 风险控制

### 8.1 不能删掉的东西
- 默认触发语义
- 成功表述前必须验证
- 主源优先级
- `doc/技能库` 与 `.trae/skills` 的主从关系
- 设计、分析、评审文档的落盘要求
- 提交规范中的 `AI辅助：true`、`AI工具：Trae`、`（AI生成提交）`

### 8.2 适合删掉的东西
- 相同规则的解释性重复段落
- 多份提示词里重复出现的分层清单
- 已声明并入总规范后的摘要性正文
- `.trae/skills` 中与主源完全重复的长描述

## 9. 推荐实施顺序
1. 先压 `CLAUDE.md` 与 `.trae/rules/*.md`
2. 再压三份高重复提示词
3. 再收缩 `doc/项目规范/项目开发规范.md`
4. 最后统一 `.trae/skills` 的轻量镜像模板

## 10. 结论
- 当前最值得压缩的不是所有资料，而是“入口层重复”。
- 只要坚持“正文单一主源 + 入口短化 + 提示词只保留差异”，基本可以在不明显损失效果的前提下减少 token 消耗。
- 若进入实施阶段，建议先做低风险第一阶段：压缩 `CLAUDE.md`、`.trae/rules/anti-laziness-anti-hallucination.md`、`.trae/rules/workspace-common.md`，这一步收益最大。
