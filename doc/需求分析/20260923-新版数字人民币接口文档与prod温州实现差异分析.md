## 4. 总体结论

### 3.1 两个项目的共同结论

两边当前数字人民币主实现仍以 `WbjkServiceImpl` 为核心，请求封装口径大体一致；针对最新版文档，`prod` 与温州都存在以下共同缺口：

1. `ECS419` 尚未按最新版补齐 `MerchantNo / MerchantName / SubMerchantNo / SubMerchantName`
2. `ECS419` 仍继续上送已废弃字段 `BusinessSummary`
3. `ECS419`、`ECS441` 对 `ProxyCollPartyId` 仍允许空串兜底，和新版“必输/条件必输”口径不完全一致
4. 多个钱包编号相关 DTO 仍保留 `35` 位长度约束，未完全收敛到最新版 `34` 位

### 3.2 prod 与温州的差异

温州项目对 `ECS453` 新口径的适配明显比 prod 更靠前，已经看到对以下字段的显式处理：

- `ActualAmount`
- `TxRejectCode`
- `TxRejectInformation`

而 prod 仍存在旧口径处理残留，至少在抽查到的单笔付款结果处理中，仍沿用：

- `RejectCode`
- `RejectInformation`
- 原始 `TranResult` 分支判断

结论上可以认为：

- `温州`：在 `V1.10 / V1.12` 之后的结果处理口径上更接近新版
- `prod`：存在“部分已升级、部分仍旧口径”的混用风险

## 5. 逐项差异

## 5.1 ECS419 对公扣款账户签约

### 文档要求

最新版要求请求体新增：

- `MerchantNo`（必输）
- `MerchantName`（必输）
- `SubMerchantNo`（可选）
- `SubMerchantName`（可选）

并要求：

- `ProxyCollPartyId` 条件必输
- `BusinessSummary` 废弃

### 当前实现

核对位置：

- `...capinfo-gjj-busi-zjjs-ywgl...WbjkServiceImpl.java`
- `...api\dto\req\CorpWalletSignReqDTO.java`

两个项目当前 `corpWalletSign` 请求封装中仍然只有：

- `ProxyCollPartyId`
- `BusinessSummary`
- `Remark`
- `Postscript`

未见：

- `MerchantNo`
- `MerchantName`
- `SubMerchantNo`
- `SubMerchantName`

同时 `ProxyCollPartyId` 仍按以下方式处理：

- `StrUtil.isNotBlank(...)? ... : ""`

这说明：

1. 商户字段未适配
2. `ProxyCollPartyId` 仍可为空，不满足最新版必输口径
3. 已废弃字段 `BusinessSummary` 仍在继续上送

### 影响判断

- 若对接方已按 `V1.18` 严格校验，`ECS419` 存在报文拒绝风险
- 即使暂未拦截，也属于协议口径落后，后续联调/切换环境时容易暴露

## 5.2 ECS431 对公扣款账户签约结果查询

### 文档要求

最新版把请求体里的 `ProxyCollPartyId` 调整为必输。

### 当前实现

抽查两边 `ECS431` 查询请求构造逻辑时，已看到请求中会写入：

- `ProxyCollPartyId = dbqyReqDTO.getYhdm()`

因此从“是否上送该字段”的角度看，`ECS431` 请求侧风险相对较低。

### 风险提示

虽然 `ECS431` 请求侧较接近文档，但当前结果解析仍主要围绕：

- `QueryResult`
- `SigningResult`
- `ProtocolNo`
- `DeAcctName`
- `CrAcctName`

未见围绕新版扩展口径做额外结构化沉淀。当前看不是 `V1.18` 的主缺口，但后续若接口继续扩展，仍建议统一收口到协议解析工具层。

## 5.3 ECS441 对公扣款账户解约

### 文档要求

最新版把请求体里的 `ProxyCollPartyId` 调整为必输。

### 当前实现

核对 `corpWalletCancel` 请求封装，两个项目当前都是：

- `reqMapArgs.put("ProxyCollPartyId", StrUtil.isNotBlank(...)? ... : "")`
- 同时仍继续上送 `BusinessSummary`

### 差异结论

1. `ProxyCollPartyId` 仍允许空串，不满足最新版必输约束
2. `BusinessSummary` 仍在继续上送，存在和新版口径不一致的问题

## 5.4 钱包编号长度 35 -> 34

### 文档要求

最新版将钱包编号字段长度从 `35` 调整回 `34`。

### 当前实现

两个项目中仍能检到多个 `35` 位限制，典型包括：

- `CorpWalletSignReqDTO`
- `CorpWalletCancelReqDTO`
- `YhtProtocolQueryReqDTO`
- `YhtBatchTradeReqDTO`
- `YhtBatchTradeDetailReqDTO`
- `Caps305Message`

其中典型写法为：

- `@Size(max = 35, ...)`

### 差异结论

这说明两个项目尚未完成钱包编号长度回收。虽然“34 位值”仍能通过“max=35”校验，但：

1. 本地校验规则与协议口径不一致
2. 后续若存在长度格式校验、脱敏、拼报文或外围系统校验，容易留下边界问题

## 5.5 ECS453 交易结果查询

### 文档演进要求

文档较新版本已陆续新增/调整：

- `ActualAmount`
- `TxRejectCode`
- `TxRejectInformation`
- 查询频次间隔不低于 `20` 秒

### prod 当前情况

抽查 `SysDbfkServiceImpl` 可见，prod 在单笔付款结果处理中仍主要使用：

- `RejectCode`
- `RejectInformation`
- `TranResult`

未在该处看到对：

- `TxRejectCode`
- `TxRejectInformation`
- `ActualAmount`

的同等处理。

说明 prod 至少在部分结果处理链路上仍是旧口径。

### 温州当前情况

抽查温州 `SysDbfkServiceImpl`，已看到：

- `DigitalCurrencyProtocolUtils.getString(map, "TxRejectCode")`
- `DigitalCurrencyProtocolUtils.getString(map, "TxRejectInformation")`
- `DigitalCurrencyProtocolUtils.parseAmount(map.get("ActualAmount"))`

说明温州在该链路上已按新版结果字段处理。

### 两边共同问题

本次检索未看到对“同一交易 `ECS453` 查询间隔不低于 20 秒”的显式节流控制。

因此这里仍有一个共同风险：

- 业务定时查询或重复查询若过于频繁，可能不符合文档约束

## 5.6 ECS415 单位钱包绑定账户管理

- `yhssjg`

## 5.7 ECS435 钱包交易明细查询

### 文档要求

文档正文要求 `ECS435`：

1. `TxDateBegin/TxDateEnd` 使用 `yyyyMMddHHmmss`
2. 开始日期不能早于一年前
3. 请求支持：
   - `QueryNumber`
   - `PageNumber`
   - `LastTransactionFlowId`

### prod 当前情况

抽查 `prod` 的 `WbjkServiceImpl`：

- 已传 `QueryNumber`
- 已传 `PageNumber`
- 将 `TxDateBegin/TxDateEnd` 拼成当日 `000000/235959`
- **未看到**“不能早于一年前”的显式校验
- **未看到** `LastTransactionFlowId` 上送

### 温州当前情况

温州同一位置已看到：

- 一年前边界校验
- `LastTransactionFlowId` 上送
- 返回文件按更严格的列数与时间格式解析

### 差异结论

这是一项不止靠修订记录才能发现的正文差异：

1. `prod` 的 `ECS435` 仍缺少文档要求的一年前校验
2. `prod` 的 `ECS435` 仍缺少 `LastTransactionFlowId`
3. 温州在 `ECS435` 上明显比 prod 更贴近文档正文

## 5.8 ECS683 电子回单列表查询

### 文档要求

文档正文要求 `ECS683`：

1. 开始日期不能晚于结束日期
2. 开始日期不能晚于当前营业日期
3. 时间跨度不能超过 90 天
4. `AmtBegin/AmtEnd` 为正值
5. 填 `AmtBegin` 时必须同步填 `AmtEnd`
6. 请求支持分页参数 `QueryNumber/PageNumber`
7. 返回文件要支持末尾字段扩展，不影响前面字段解析

### prod 当前情况

抽查 `prod` 的 `WbjkServiceImpl`：

- 已上送 `QueryNumber/PageNumber`
- 已拼装 `TxDateBegin/TxDateEnd`
- **未看到** 90 天跨度、金额正值、起止金额联动等显式校验
- 返回文件仍以较直接的 `split(Pattern.quote("@|$"), -1)` 解析，未见明显的“列数保护/格式保护”

### 温州当前情况

温州同一实现中已看到：

- 开始/结束日期顺序校验
- 不得晚于当前日期校验
- 90 天跨度校验
- `AmtBegin/AmtEnd` 正值与联动校验
- 解析时使用更严格的列数/时间格式校验工具

### 差异结论

`ECS683` 是本次新增发现的另一类差异：

1. 两边都实现了接口
2. 但温州已经补了正文要求的行为校验
3. prod 仍偏旧，存在“报文构造能发出，但入参未按文档前置约束收口”的问题

## 8. 优先整改建议

建议优先级如下：

1. 优先整改 `ECS419`
   - 补齐 `MerchantNo / MerchantName / SubMerchantNo / SubMerchantName`
   - 收紧 `ProxyCollPartyId`
   - 下线 `BusinessSummary`
2. 同步整改 `ECS441`
   - 将 `ProxyCollPartyId` 改为真正必输
   - 清理继续上送的 `BusinessSummary`
3. 统一收口钱包编号长度
   - 将相关 DTO / 协议模型中的 `35` 位约束回收到 `34`
4. 统一 `ECS453` 结果解析
   - prod 对齐温州的 `DigitalCurrencyProtocolUtils` 口径
   - 统一使用 `TxRejectCode / TxRejectInformation / ActualAmount`
5. 增加 `ECS453` 查询节流
   - 至少在定时任务或重试任务层保证单交易查询间隔不低于 20 秒

## 9. 结论摘要

本次对比后可以明确：

- `温州` 并不是完全跟上最新版文档，只是比 `prod` 更接近正文要求
- 两个项目当前最大的共同缺口集中在 `ECS419 / ECS441 / 钱包编号长度`
- `prod` 还额外存在 `ECS453 / ECS435 / ECS683` 等接口的行为校验或结果解析口径偏旧问题
- 文档里的 31 个接口大多数都已有实现，当前工作的重点应从“补接口”转为“补字段、补校验、补解析、统一口径”

如果下一步要做改造，建议按“先协议报文必输项，再结果解析统一化，最后做长度/节流收口”的顺序推进。
