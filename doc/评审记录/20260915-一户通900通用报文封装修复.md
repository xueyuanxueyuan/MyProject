# 一户通900通用确认报文封装修复

日期：2026-09-15
适用范围：prod、嘉兴结算业务模块、一户通独立挡板。

## 依据与根因

用户提供的厂商样例使用 Document / Message / Head 三层结构，Document 默认命名空间为 urn:cbcc:std:caps:2020:tech:xsd:caps.900.001.01，并声明 xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"。

两地 Caps900Builder 原先直接输出 Message 根节点，默认命名空间错误地使用 urn:caps:msg:caps.900.001.01。挡板正常处理和异常兜底两个生成入口都调用 CapsCodecService.buildXml，因此存在相同问题。此外挡板按请求是否加签/加密决定响应处理，没有排除900，可能将本应明文的确认报文再次加签、加密。

协议来源：prod/IdeaProject/capinfo-gjj-busi-jshs/document/一户通相关文档/0.原始文档/上海集中代收付系统报文交换规范V1.2.7.7.md 第5.24节。该节描述 Message 内部业务结构；外层封装以本次厂商样例为准。

## 修改范围

- prod、jiaxing 两个结算业务模块的 Caps900Builder：增加 Document 外层及标准默认命名空间、xsi声明，Message和Head继承同一命名空间；同步原有说明样例。
- yht-mock-server 的 CapsCodecService.buildXml：仅对 caps.900.001.01 使用标准Document封装，覆盖正常和异常兜底入口；其他报文生成格式不变。
- yht-mock-server 的 MockGatewayService.dispatch：900响应始终不加签、不加密；其他响应继续遵循原规则。
- 两地分别新增 Caps900BuilderTest；挡板新增 Caps900EnvelopeTest。
- 未修改数据库、环境配置、凭证、发布制品；未提交或发布。
- 保留工作区原有未提交修改，尤其 MockGatewayService 原有的回调处理器注册、Remark补充等改动。

## 字段口径

2026-09-16按用户补充要求，以第7.1节作为ProcCode和ProcMsg的唯一取值来源，纠正上一版仅核对第5.24节的结论。CorpNo仍为实际机构编号；成功统一为I000 / 平台校验成功。

第7.1节共168组编码和描述，在prod、嘉兴和挡板分别维护Caps900CodeCatalog。失败响应使用合法失败码，并从码表取标准描述；不透传自定义描述、不截断拼造处理码。未知、空值或误用于失败响应的I000统一使用E999 / 其他错误请联系中心解决。挡板异常出口按解析异常E401、未知业务E012、其他系统异常S999返回码表描述。

Remark在协议中为[0..1]，普通成功回执允许不输出；自动化验证回执继续保留既有检测序号处理。XML字符转义保留。900无Body。
