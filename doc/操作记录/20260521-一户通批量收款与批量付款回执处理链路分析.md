# 一户通批量收款与批量付款回执处理链路分析

## 1. 结论先行

当前一户通批量收款和批量付款在结算系统中的回执处理，走的不是单笔实时 `caps.205` 链路，而是批量 `caps.107` 链路。

两条链路的共同点：

1. 都通过 `caps.101` 发起批量交易；
2. 都通过 `caps.107` 接收批量处理结果回执；
3. 回执到达后，当前代码首先更新的是一户通任务表、批次表、批次明细表；
4. 结果文件解析后，当前直接落的是 `zjjs_zj_yht_batch_task` / `zjjs_zj_yht_batch_detail` 这套一户通台账；
5. 本轮排查未发现像单笔 `20601/20602` 那样，直接在 `caps.107` 回调里继续调用 `YwglService` 去推进 `Skyw/Fkyw/YwJg` 主业务表。

也就是说，当前批量回执处理更像“批量任务收敛 + 结果文件明细落账”，而不是“回执到达即直接联动主业务结果处理”。

## 2. 交易码与报文映射

根据测试文档与控制器注释：

1. 批量付款：`bizType=PAY`，交易码 `40501`
2. 批量收款：`bizType=COLLECT`，交易码 `40502`
3. 批量申请：`caps.101.001.01`
4. 批量应答：`caps.102.001.01`
5. 批量状态查询：`caps.103.001.01 / caps.104.001.01`
6. 批量结果提回：`caps.105.001.01 / caps.106.001.01`
7. 批量结果回执：`caps.107.001.01`

## 3. 批量付款发送链路

### 3.1 结算业务入口

`YwglServiceImpl.addFkywPlfkjy(Fkyw fkyw, List<FkywPlmx> list)`

在 `Jsqd=YHT` 时：

1. 不再走原本地批量接口；
2. 直接调用 `yhtYwService.addFkywPlfkjy(fkyw, list)`；
3. 然后立即 `return`。

### 3.2 一户通发送入口

`YhtYwServiceImpl.addFkywPlfkjy(Fkyw fkyw, List<FkywPlmx> list)`

主要行为：

1. `batchNo = fkyw.getJslsh()`
2. `bizType = PAY`
3. 组装 `YhtBatchTradeReqDTO`
4. 调用 `yhtService.submitBatchTrade(reqDTO)`

说明：

这里是批量付款走一户通的真正发送入口。

## 4. 批量收款发送链路

### 4.1 结算业务入口

`YwglServiceImpl.addSkywPlskjy(Skyw skyw, List<SkywPlmx> list)`

在 `Jsqd=YHT` 时：

1. 直接调用 `yhtYwService.addSkywPlskjy(skyw, list)`
2. 然后立即 `return`

### 4.2 一户通发送入口

`YhtYwServiceImpl.addSkywPlskjy(Skyw skyw, List<SkywPlmx> list)`

主要行为：

1. 先按付款银行分组；
2. 每个分组生成一个子批次；
3. `batchNo = skyw.getJslsh() + "-" + groupIndex`
4. `bizType = COLLECT`
5. 明细里把 `serialNum` 设置为 `SkywPlmx.mxlsh`
6. 调用 `yhtService.submitBatchTrade(reqDTO)`

说明：

批量收款为了兼容不同付款银行，会拆成多个子批次。

## 5. 批量回执入口链路

### 5.1 HTTP 接收入口

`YhtController.receive(...)`

统一接收 CAPS 异步回执，路径：

`POST /api/v1/ywgl/yht/yht/receive`

### 5.2 回调分发链路

收到报文后的处理链：

1. `YhtController.receive(...)`
2. `YhtServiceImpl.receiveCallback(...)`
3. `YhtInboundCallbackFacade.handle(...)`
4. 按报文类型分发

其中：

1. `caps.205` 走实时回执处理器
2. `caps.107` 走批量回执处理器

### 5.3 批量回执处理器

`YhtBatchCallbackProcessor.handle(String body)`

主要处理步骤：

1. 解析 `caps.107`
2. 取 `BatchNo`
3. 通过 `batchNo` 找本地 `YhtBatchTaskDO`
4. 再通过 `reqId` 找 `YhtProtocolTaskDO`
5. 更新协议任务状态、批次状态
6. 如果 `fileData` 不为空，解析结果文件并更新批量明细
7. 最后刷新批次聚合统计

## 6. `caps.107` 回执具体更新了什么

### 6.1 更新协议任务表

更新对象：

- `YhtProtocolTaskDO`

更新内容：

1. `receiveTime`
2. `respBody`
3. `bizStatus`
4. `errorCode`
5. `errorMsg`

### 6.2 更新批次主表

更新对象：

- `YhtBatchTaskDO`

更新内容：

1. `batchStatus`
2. `checkDate`
3. `platformBatchNo`
4. `errorCode`
5. `errorMsg`
6. `successCount`
7. `failCount`
8. `processingCount`

### 6.3 更新批次明细表

更新对象：

- `YhtBatchDetailDO`

更新方式：

`YhtBatchResultFileProcessor.parseAndUpdateDetails(...)`

匹配键：

1. 优先 `reqId + serialNum`
2. 不命中再退到 `reqId + detailSeq`

更新字段：

1. `bizStatus`
2. `retCode`
3. `retMsg`

说明：

这一层更新的是一户通批量明细台账，不是本地批量业务明细表 `ZjPlskmx / ZjPlfkmx`。

## 7. 当前“没做什么”

本轮排查到的关键事实是：

在 `YhtBatchCallbackProcessor` 和 `YhtBatchResultFileProcessor` 中，当前没有发现以下动作：

1. 没有调用 `YwglService`
2. 没有直接调用批量收款/付款主业务结果处理方法
3. 没有直接更新 `Skyw/Fkyw/YwJg`
4. 没有直接更新 `ZjPlskmx/ZjPlfkmx`

因此当前批量回执的落点是：

1. 一户通协议任务
2. 一户通批次任务
3. 一户通批次明细

而不是结算业务主表和原始批量明细表。

## 8. 与单笔回执的差异

单笔实时业务现在已经补齐了业务联动：

1. `20601` 单笔付款回执会调用 `fkywJfJgCl(...)`
2. `20602` 单笔收款回执会调用 `skywJfJgCl(...)`

但批量业务当前并没有看到同等级的：

1. 批量付款回执 -> `批量付款业务结果处理`
2. 批量收款回执 -> `批量收款业务结果处理`

这正是批量与单笔目前最核心的结构差异。

## 9. 现场联调时该怎么看

如果现场测试“批量收款/批量付款收到回执后业务没处理”，优先按下面顺序核对：

1. 是否收到 `caps.107`
2. `YhtBatchTaskDO.batchStatus` 是否更新
3. `YhtBatchDetailDO` 是否已按 `serialNum/detailSeq` 回写 `retCode/retMsg/bizStatus`
4. `ZjPlskmx / ZjPlfkmx` 是否完全没变化
5. `Skyw/Fkyw/YwJg` 是否仍停留在交易中

如果出现：

1. `YhtBatchDetailDO` 已成功更新；
2. 但 `ZjPlskmx/ZjPlfkmx/YwJg` 没变；

那么基本可以判定：

当前批量回执链路只收敛了一户通批量台账，还没有继续联动结算主业务处理。

## 10. 下一步建议

如果后续要继续修复，建议分两步做：

### 10.1 先补“批量回执 -> 本地批量业务明细”的映射层

建议建立：

1. `YhtBatchDetailDO.serialNum` 对应 `ZjPlskmx.refseqno1` / `ZjPlfkmx.refseqno1`
2. `YhtBatchDetailDO.batchNo` 对应本地主批次 `jslsh`

先把结果同步到本地批量明细表。

### 10.2 再补“本地批量明细汇总 -> 主业务状态推进”

当本地批量明细全部成功/失败/部分成功后，再统一决定：

1. 主业务 `YwJg` 是否置成功
2. 是否部分成功
3. 是否走失败链
4. 是否通知业务侧

这样比直接在 `caps.107` 里硬改主表更稳。
