## 2. 总体结论

### 2.1 可以确认的结论

1. `yht` 不是“只写了接口壳子”，而是已经具备较完整的通道内能力：
   - 报文构建
   - 同步应答处理
   - 回调接收
   - 幂等控制
   - 任务落库
   - 补查与人工介入

2. 当前最大问题不是“模块完全不可用”，而是：
   - 一部分实现与原始规范存在偏差
   - 模块尚未正式接入现有业务主链路

3. 与现有业务对接时，不能只让前端直接访问 `/yht/**` 新接口，而必须像 `yqzl` 一样，把通道能力接入到：
   - 业务总入口分流
   - 主业务状态回写
   - 查询/补查/回调闭环

### 2.2 需要纠正的旧判断

之前仅从控制层语义看，容易把“协议查询校验过严”判为代码问题；本次对照原始规范后确认：

- `caps.303` 规范本身就要求 `ProtocolNo`、`AcctNo`、`FeeNo` 为必填
- `ReqId` 只是可选附加条件，用于指定某次申请号查询

因此真正的问题不是服务层校验违背协议，而是：

- 控制层注释和对外描述把查询说成了“至少一个条件即可”
- 旧接口参数表达方式与底层报文真实要求不一致

## 3. 审计结果

以下按严重级别给出审计结论。

## 3.1 高优先级问题

### 问题 1：`caps.203` 实时状态查询报文结构与原始规范不一致

规范依据：

- 原始规范 `5.10 实时业务查询报文<caps.203.001.01>`
- 规范中 `BizDate`、`TranCode`、`FeeNo`、`QueryType`、`SerialNum`、`SysSeqNo` 均定义在 `<Head>` 下

当前实现：

- `YhtRealtimeTradeMessageBuilder.buildCaps203()`
- `YhtRealtimeStatusQueryOrchestrator.buildCaps203Xml()`

当前代码把：

- `CorpNo/BizDate/TranCode/FeeNo/QueryType` 放在 `Head`
- `SerialNum/SysSeqNo` 放在 `Body`

这与原始规范不一致，属于报文结构级偏差。

影响：

1. 平台可能直接按格式错拒绝。
2. 即便网关放行，也可能导致签名原文与平台解析结构不一致。
3. 后续查询失败会被业务层误判成“交易不存在”或“平台拒绝”。

结论：

- 这是明确的协议实现错误，优先级 `P0`。

### 问题 2：`caps.201` 实时业务签名原文拼接字段明显少于规范要求

规范依据：

- 原始规范 `5.8.3 实时业务申请报文<caps.201.001.01>`
- 大量字段被标记为加签要素，包括：
  - `CorpNo`
  - `Version`
  - `TranCode`
  - `FeeNo`
  - `SerialNum`
  - `DbtrProtocol`
  - `DbtrActName`
  - `DbtrActId`
  - `DbtrCardType`
  - `DbtrBankId`
  - `DbtrBankType`
  - `CdtrActName`
  - `CdtrActId`
  - `CdtrCardType`
  - `CdtrBankId`
  - `CdtrBankType`
  - `PayAmt`

当前实现：

- `YhtRealtimeTradeMessageBuilder.buildCaps201SignElement()`

当前仅拼了：

- 企业号
- 交易类型
- 费项代码
- 企业流水号
- 付款账号
- 收款账号
- 金额

影响：

1. 若平台按规范验签，极易出现验签失败。
2. 即使当前联调环境容忍，也存在正式环境切换后失败风险。

结论：

- 这是明确的协议实现错误，优先级 `P0`。

### 问题 3：实时交易请求校验规则与 `caps.201` 规范不一致

规范依据：

- 原始规范 `5.8.3`

规范要求中关键约束包括：

1. `FeeNo` 在 `caps.201` 中是 `Max5Text`
2. `Remark` 是 `Max60Text`
3. `DbtrBankType`、`CdtrBankType` 为必填
4. `TranCode=20601/20602` 时，收付双方账户类型组合有限制

当前实现：

- `YhtRealtimeTradeRequestValidator`

发现的问题：

1. 只校验 `FeeNo` 最大长度为 `14`，与 `caps.201` 的 `5` 不一致
2. 没有强制 `FeeNo` 必填，而是允许后续默认补 `00000`
3. `Remark` 允许到 `128`，超出规范 `60`
4. 未校验 `DbtrBankType`、`CdtrBankType` 必填
5. 未按 `TranCode` 校验账户类型组合，只宽松允许 `01/02/03`

影响：

1. 请求可能在本地通过，但被 CAPS 拒绝。
2. 交易参数不合法时，错误暴露在远端，不利于本地定位。

结论：

- 这是明确的协议实现偏差，优先级 `P0`。

### 问题 4：`caps.201` 可选字段在代码中被强行输出空标签，存在报文格式风险

规范依据：

- 原始规范 `5.8.3`
- `Remark`、`Use`、`DbtrPhone`、`CdtrPhone`、`ExtraData` 都是可选项

当前实现：

- `YhtRealtimeTradeMessageBuilder`

其中：

- `Remark` 使用 `appendTag()`
- `Use` 使用 `appendTag()`

这意味着即使为空，也会输出空 XML 标签。

影响：

1. 如果平台 schema 或业务校验要求“可选项缺省时不出现”，空标签会带来格式风险。
2. 这与当前代码自己对可选项的公共封装 `appendOptionalTag()` 设计也不一致。

结论：

- 这是高风险实现问题，优先级 `P0/P1`。

## 3.2 中优先级问题

### 问题 5：协议查询控制层对外语义与原始规范不一致

规范依据：

- 原始规范 `5.15 协议查询报文<caps.303.001.01>`

规范要求：

- `ProtocolNo` 必填
- `AcctNo` 必填
- `FeeNo` 必填
- `ReqId` 可选，但用于查询某次申请过程状态

当前实现：

- `YhtController.queryProtocol()` 对外说明为“协议号/账号/申请号至少一个即可”
- `YhtProtocolRequestValidator.validateQuery()` 则按协议要求校验必填字段
- `YhtProtocolRequestOrchestrator.prepareQueryRequest()` 会尝试通过历史任务补齐缺失字段

结论：

1. 服务层本身没有明显违背规范。
2. 真正的问题是控制层契约描述与底层真实报文要求不一致。
3. 这会导致外部调用方误以为 `reqId` 单独可查，但实际仍依赖本地任务上下文补齐。

### 问题 6：协议查询结果落库未按 `6.8` 文件流规范完整解析

规范依据：

- 原始规范 `6.8 协议查询文件流`

文件流字段顺序为：

1. 协议号
2. 付方账号
3. 付方户名
4. 开户行号
5. 协议开始日期
6. 协议结束日期
7. 单笔付款金额上限
8. 协议状态

当前实现：

- `Caps304FileDataParser` 已按规范正确建模
- 但 `YhtProtocolStatusSyncProcessor.syncFromQuery()` 没有复用该解析器，而是直接对整段文本 `split("\\|")`

问题包括：

1. 没有按“多行记录”语义解析
2. 没有完整写入开始日期、结束日期、开户行号、单笔限额
3. 返回对象里虽然预留了 `effectDate/dueDate`，但查询同步时并未真正填充

影响：

1. 协议查询返回后的本地主表信息不完整。
2. 多条协议结果时解析风险更高。

结论：

- 这是状态同步不完整问题，优先级 `P1`。

### 问题 7：`caps.306` 回调状态处理对 `RE00/RE01` 的利用仍偏弱，存在业务态粗化风险

规范依据：

- 原始规范 `5.18 协议签约管理应答报文<caps.306.001.01>`

规范说明：

- `RE00` 表示协议变更回执
- `RE01` 表示协议授权结果回执
- 一次申请可能对应两次回执

当前实现：

- `YhtProtocolCallbackProcessor.resolveBizStatusByCallback()`

当前策略：

- `RE00` 直接返回 `ACCEPTED`
- 否则再尝试用 `protocolProcessCode/errorCode` 推断状态

问题在于：

1. 规范仅说明回执类型，并未等同于固定业务状态。
2. 代码把 `RE00` 直接固化成中间态，容易把本应可落终态的结果延后。
3. `Caps306Message` 模型有 `protocolProcessCode` 字段，但 `parseCaps306()` 并未真正解析该字段，状态推断依据不稳定。

结论：

- 这是状态机实现风险，优先级 `P1`。
- 目前可以判定“风险较高”，但无法仅凭规范直接断言其线上必错。

## 3.3 低优先级问题

### 问题 8：存在一段未使用的 `caps.305` 查询构建逻辑，且结构不符合 `caps.305` 原始规范

位置：

- `Caps305Builder.buildQueryMessage()`

该方法构造了 `OrigMsgId/QueryTime/PyerBgNum` 等字段，而这并不是原始规范 `5.17` 中定义的 `caps.305` 结构。

但当前检索结果显示：

- 该方法未被业务链路调用

结论：

- 这是遗留/废弃代码风险，不是当前主路径故障点。

## 4. 与规范一致、可以继续沿用的实现

以下能力对照原始规范后，结论是“方向基本正确”：

1. `caps.900/999` 走免签免密逻辑
2. `caps.999` 的 `CorpNo` 固定为 `1111`
3. `caps.205` 回调先同步返回 `caps.900`，再做业务处理
4. 协议查询支持通过本地任务上下文补齐 `ProtocolNo/AcctNo/FeeNo`
5. 回调接收门面对 `MesgId` 做幂等控制

结论：

- 这部分不需要推倒重写，可以继续作为接入基础。

## 5. 与现有业务接口对接方案

## 5.1 当前未接通的位置

当前现有业务主链路仍未正式使用 `yht`：

1. `YwglController.corpWalletSign()` 仍走 `wbjkService`
2. `YwglController.corpWalletCancel()` 仍走 `wbjkService`
3. `YwglV2Controller` 同样仍走旧服务
4. `YwglServiceImpl` 付款分流只有 `ZJBJSPT`、`YQZL`
5. `YwglServiceImpl.khzhyxxCx()` 留有 `// TODO: 一户通渠道查询`
6. `YwglServiceImpl.yhzhHqyeCx()` 没有 `YHT` 分支

因此即使 `yht` 自身接口可调用，它也还不是现有业务体系里的正式通道。

## 5.2 应参考 `yqzl` 的“接入方式”，不是照搬报文发送形式

`yqzl` 的关键经验在于：

1. 业务总入口按 `Jsqd` 分流
2. 通道侧有自己的交易表/初始化表
3. 发起后会更新主业务状态为“交易中”
4. 回执和补查结果会再回写业务主表

`yht` 对接时也应保持这个原则：

- 不是让业务层直接拼 `caps.201/caps.305`
- 而是让业务层调用一层 `YhtYwService`

## 5.3 推荐对接架构

### 第一层：保留现有外部请求 DTO，不改前端协议

建议保留：

- `CorpWalletSignReqDTO`
- `CorpWalletCancelReqDTO`

原因：

1. 现有业务接口已存在大量调用方
2. 先不改前端协议，可以降低切换风险

### 第二层：新增一层业务接入门面

建议新增：

- `YhtYwService`
- `YhtYwServiceImpl`

职责：

1. 把旧业务 DTO 转换成 `YhtSignReqDTO/YhtCancelReqDTO/YhtRealtimeTradeReqDTO`
2. 把 `yht` 任务状态翻译成现有业务主状态
3. 维护主业务与 `yht` 任务表的关联关系

### 第三层：在现有入口里做通道路由

建议改造点：

1. `YwglController/YwglV2Controller`
2. `WbjkServiceImpl` 或其上层门面

思路：

- 先做“按通道路由”
- 走 `YHT` 时转发给 `YhtYwService`
- 非 `YHT` 时继续走原实现

这样可以实现：

1. 前端无感切换
2. 支持按机构/渠道灰度切换

### 第四层：在 `YwglServiceImpl` 补 `Jsqd.YHT`

这是把 `yht` 变成正式结算通道的关键步骤。

至少要补的点：

1. 付款业务分流
2. 账户有效性查询
3. 余额查询
4. 付款结果补查
5. 回调结果后的主业务状态回写

### 第五层：建立主业务和 `yht` 任务表关联键

建议至少保存以下关联维度：

1. 主业务 ID
2. `reqId`
3. `mesgId`
4. `protocolNo/sysSeqNo`
5. `jsqd`
6. 业务类型

否则会出现：

- `yht` 通道内状态更新了
- 但现有主业务表无从感知

## 5.4 推荐改造顺序

### 阶段一：先修协议偏差

优先修复：

1. `caps.203` 结构错误
2. `caps.201` 签名原文错误
3. `caps.201` 实时请求校验偏差
4. `caps.304` 查询结果同步不完整

### 阶段二：接企业钱包签约/解约旧入口

先接：

1. `corpWalletSign`
2. `corpWalletCancel`

这是最容易形成业务闭环的第一步。

### 阶段三：补 `YwglServiceImpl` 通道分流

补齐：

1. `付款`
2. `账户有效性查询`
3. `余额查询`

### 阶段四：做回调和补查的业务闭环

把：

1. `caps.306`
2. `caps.205`
3. `caps.304`
4. `caps.204`

这些通道结果翻译成主业务状态。

## 6. 本次建议结论

### 6.1 当前不建议直接接入生产业务的原因

因为还存在协议实现偏差，尤其是：

1. `caps.203` 结构不对
2. `caps.201` 签名要素不全
3. 实时请求校验与原始规范不一致

这些问题会导致：

- 联调时出现“本地看起来没问题，平台直接拒绝”的情况

### 6.2 可以作为下一步实施起点的方案

推荐执行顺序：

1. 先修 `P0` 审计问题
2. 再新增 `YhtYwService` 业务接入层
3. 接 `corpWalletSign/cancel`
4. 接 `YwglServiceImpl` 的 `Jsqd.YHT`
5. 最后补查询、补查、回调状态闭环

## 7. 一句话结论

`yht` 当前的真实状态是：

- **模块能力已基本成型，但还存在几处明确的协议实现偏差，而且尚未接进现有业务主链路。**

因此下一步应先做“协议纠偏”，再做“像 `yqzl` 一样的业务入口接入”，而不是直接把 `/yht/**` 暴露出去就算完成对接。

## 8. 最小可落地改造清单

本节将前述审计结果进一步压缩成“按类、按方法、按阶段”的执行清单，便于直接进入开发。

## 8.1 第一批必须先改的协议纠偏项

### 改造项 A：修正 `caps.203` 报文结构

目标：

- 让实时状态查询报文严格符合原始规范 `5.10`

涉及类：

- `busi/yht/message/builder/YhtRealtimeTradeMessageBuilder`
- `busi/yht/orchestrator/realtime/YhtRealtimeStatusQueryOrchestrator`

建议动作：

1. 把 `SerialNum` / `SysSeqNo` 从 `Body` 挪回 `Head`
2. 保证 `Head` 字段顺序与规范一致
3. 统一签名原文拼接逻辑，避免一个类改了、另一个类仍使用旧结构

验收标准：

1. 生成的 `caps.203` XML 结构与原始规范一致
2. 查询类单测能断言 `Head` 中出现 `SerialNum` 或 `SysSeqNo`

### 改造项 B：修正 `caps.201` 签名原文

目标：

- 让实时业务发送报文的签名要素与原始规范一致

涉及类：

- `busi/yht/message/builder/YhtRealtimeTradeMessageBuilder`

建议动作：

1. 重新按规范梳理 `caps.201` 全部加签字段
2. 补上 `Version/DbtrProtocol/DbtrActName/DbtrCardType/DbtrBankId/DbtrBankType/CdtrActName/CdtrCardType/CdtrBankId/CdtrBankType` 等缺失项
3. 明确可选字段空值是否进入签名串，严格按规范顺序输出

验收标准：

1. 签名原文顺序与规范表格一致
2. 联调日志中不再出现验签失败类错误

### 改造项 C：修正实时请求校验器

目标：

- 把本地校验收紧到与 `caps.201` 一致，避免“本地放行、平台拒绝”

涉及类：

- `busi/yht/validator/realtime/YhtRealtimeTradeRequestValidator`

建议动作：

1. `FeeNo` 长度改为 `Max5`
2. `Remark` 长度改为 `Max60`
3. 增加 `DbtrBankType/CdtrBankType` 必填校验
4. 按 `TranCode` 校验 `DbtrCardType/CdtrCardType` 合法组合
5. 评估是否应要求 `FeeNo` 必填，而不是默认补 `00000`

验收标准：

1. 不合法请求在本地直接被拒绝
2. 错误码和错误信息能明确指出字段问题

### 改造项 D：修正 `caps.304` 查询结果同步

目标：

- 让协议查询结果按 `6.8` 文件流完整落本地

涉及类：

- `busi/yht/processor/protocol/YhtProtocolStatusSyncProcessor`
- `busi/yht/caps/parser/Caps304FileDataParser`

建议动作：

1. 在 `syncFromQuery()` 中复用 `Caps304FileDataParser`
2. 正确写入：
   - 协议号
   - 账号
   - 户名
   - 开户行号
   - 开始日期
   - 结束日期
   - 单笔限额
   - 协议状态
3. 明确多行结果时的处理策略

验收标准：

1. 单条、多条查询结果都能正确解析
2. 本地协议主表字段完整更新

## 8.2 第二批业务接入改造项

### 改造项 E：新增 `YhtYwService` 业务接入层

目标：

- 避免 `YwglServiceImpl/WbjkServiceImpl` 直接承载大量一户通细节

建议新增：

- `busi/yht/service/YhtYwService.java`
- `busi/yht/service/impl/YhtYwServiceImpl.java`

建议职责：

1. `corpWalletSign` 路由到 `yhtService.sign()`
2. `corpWalletCancel` 路由到 `yhtService.cancel()`
3. 统一做旧 DTO 到 `yht` DTO 的映射
4. 统一做 `YhtRespDTO -> DbqyRespDTO` 的结果翻译
5. 后续承接账户有效性、余额查询等业务适配

建议不要做的事：

- 不要把 CAPS 报文拼接写到 `YwglServiceImpl`
- 不要让控制层直接感知 `caps.305/caps.201`

### 改造项 F：改旧签约/解约入口为“按通道路由”

当前落点：

- `busi/controller/YwglController`
- `busi/controller/YwglV2Controller`
- `busi/service/impl/WbjkServiceImpl`

建议路线：

方案 1：

- 保持控制层不变
- 在 `WbjkServiceImpl.corpWalletSign/corpWalletCancel` 内部按 `jsqd` 或机构配置路由到 `YhtYwService`

方案 2：

- 控制层改为调用新的统一门面服务
- 统一门面再决定走 `wbjk` 还是 `yht`

推荐：

- 优先方案 2，更干净
- 若希望最小改动，则先用方案 1

验收标准：

1. 前端无须改请求结构
2. 指定机构或通道可切到 `yht`
3. 其他机构仍可保留旧链路

### 改造项 G：在 `YwglServiceImpl` 增加 `Jsqd.YHT`

目标：

- 让 `YHT` 成为正式业务通道

涉及点：

1. 付款业务分流
2. `khzhyxxCx()`
3. `yhzhHqyeCx()`

建议动作：

1. 在现有 `ZJBJSPT/YQZL` 分支旁边增加 `YHT`
2. 把 `// TODO: 一户通渠道查询` 替换为真实调用
3. 对余额查询明确一户通是否支持；若原始规范或现有一户通模块暂无此能力，则应在代码中显式返回“当前通道不支持”，而不是静默走旧链路

注意：

- 若 `yht` 当前仅覆盖协议与实时交易，不覆盖账户查询或余额查询，则该能力应标记为“暂不接入”，不能伪装成已支持

## 8.3 推荐实施顺序

### 第一步：协议纠偏

先改：

1. `caps.203`
2. `caps.201` 签名
3. 实时请求校验
4. `caps.304` 查询结果同步

原因：

- 不修这些，接业务越多，联调失败面越大

### 第二步：接签约/解约旧入口

先打通：

1. `corpWalletSign`
2. `corpWalletCancel`

原因：

- 这是最清晰、最独立、最容易灰度切量的业务入口

### 第三步：补 `YwglServiceImpl` 分流

补：

1. `Jsqd.YHT`
2. 查询能力接入
3. 余额查询能力接入或显式不支持

### 第四步：做状态闭环

补：

1. `caps.306` 回写协议状态
2. `caps.205/204` 回写实时业务状态
3. 主业务状态翻译
4. 补查与人工介入联动

## 8.4 如果下一步直接开始编码，建议从这几个类下手

优先顺序如下：

1. `YhtRealtimeTradeMessageBuilder`
2. `YhtRealtimeStatusQueryOrchestrator`

6. 改 `YwglController/YwglV2Controller` 或统一门面
7. 改 `YwglServiceImpl`

## 8.5 当前最稳妥的实施策略

若按风险最小原则推进，建议使用下面的执行模式：

1. 先只修协议偏差，不改业务入口
2. 协议偏差修完后，先让旧 `corpWalletSign/cancel` 支持灰度走 `YHT`
3. 等签约/解约稳定后，再把付款查询类能力接到 `YwglServiceImpl`

这样做的好处是：

1. 回归范围最小
2. 最容易定位问题
3. 不会一次性把整个结算链路绑到仍在纠偏的通道上

## 8.6 第一批编码任务拆分（按方法）

为避免进入开发时再次把问题讨论回到“改哪个类、改哪个方法”，这里把第一批协议纠偏项进一步压缩到方法级任务。

### 任务单 1：`caps.201` 实时报文与签名统一修正

目标类：

- `busi/yht/message/builder/YhtRealtimeTradeMessageBuilder`

重点方法：

1. `buildCaps201(YhtRealtimeTradeReqDTO reqDTO, String reqId)`
2. `buildCaps201SignElement(YhtRealtimeTradeReqDTO reqDTO)`

实施要点：

1. 先按原始规范重新核对 `Head`、`Body` 字段顺序，再决定签名原文顺序，避免“XML 改了但签名串没改”
2. `Remark`、`Use` 从 `appendTag()` 改为“有值才输出”的可选节点处理，避免空标签进入报文
3. `buildCaps201()` 与 `buildCaps201SignElement()` 统一维护同一份字段顺序说明，避免后续再次偏移
4. 若 `FeeNo` 最终允许默认 `00000`，则 XML 与签名串必须保持一致；若不允许默认值，应在校验器中同步收紧

建议补充校验点：

1. 生成 XML 时，断言 `DbtrBankType/CdtrBankType` 存在
2. 生成签名串时，断言字段顺序与规范表一致
3. `Remark/Use` 为空时，断言 XML 中不出现对应空标签

### 任务单 2：`caps.203` 查询报文与签名统一修正

目标类：

- `busi/yht/message/builder/YhtRealtimeTradeMessageBuilder`
- `busi/yht/orchestrator/realtime/YhtRealtimeStatusQueryOrchestrator`

重点方法：

1. `YhtRealtimeTradeMessageBuilder.buildCaps203(...)`
2. `YhtRealtimeTradeMessageBuilder.buildCaps203SignElement(...)`
3. `YhtRealtimeStatusQueryOrchestrator.buildCaps203Xml(...)`
4. `YhtRealtimeStatusQueryOrchestrator.buildCaps203SignElement(...)`

实施要点：

1. 统一把 `SerialNum` / `SysSeqNo` 放回 `Head`
2. 两处 `caps.203` 构文逻辑必须同时改，不能只修一个入口
3. 两处签名原文逻辑必须同步调整，确保不会出现“结构已对、验签仍错”
4. 优先抽公共构文方法或直接复用 `YhtRealtimeTradeMessageBuilder`，避免并行维护两套 `caps.203` 规则

建议补充校验点：

1. `queryType=RCNO` 时，断言 `Head` 中出现 `SerialNum`
2. `queryType=RPNO` 时，断言 `Head` 中出现 `SysSeqNo`
3. `Body` 为空或仅保留规范允许的内容，不再承载查询主键

### 任务单 3：实时请求校验规则收紧

目标类：

- `busi/yht/validator/realtime/YhtRealtimeTradeRequestValidator`

重点方法：

1. `validate(YhtRealtimeTradeReqDTO reqDTO)`

实施要点：

1. `FeeNo` 长度从 `14` 收紧为 `5`
2. `Remark` 长度从 `128` 收紧为 `60`
3. 增加 `DbtrBankType`、`CdtrBankType` 必填校验
4. 梳理 `DbtrCardType`、`CdtrCardType` 与 `TranCode` 的合法组合，不再只做通用枚举判断
5. 若规范不允许实时交易默认补 `00000`，则在此处直接要求 `FeeNo` 必填

建议补充校验点：

1. 非法 `FeeNo` 长度直接抛本地异常
2. 缺失银行类别直接抛本地异常
3. 备注超长直接抛本地异常
4. 异常码与异常文案保持现有风格，避免前端或调用方无法识别

### 任务单 4：`caps.304` 查询结果按文件流完整落库

目标类：

- `busi/yht/processor/protocol/YhtProtocolStatusSyncProcessor`
- `busi/yht/caps/parser/Caps304FileDataParser`

重点方法：

1. `YhtProtocolStatusSyncProcessor.syncFromQuery(...)`
2. `YhtProtocolStatusSyncProcessor.findOrCreateProtocol(...)`
3. `Caps304FileDataParser.parse(String base64FileData)`

实施要点：

1. `syncFromQuery()` 不再直接 `split("\\|")`，而是统一复用 `Caps304FileDataParser`
2. 明确单条结果时如何直接回写 `protocol` 主表
3. 明确多条结果时如何按 `ProtocolNo/AcctNo/FeeNo` 命中或筛选
4. 除 `AcctNo/AcctName` 外，还要补齐 `BankId/StartDate/EndDate/OnceLimit/ProcessCode`
5. `result` 返回对象也应同步回填解析后的核心字段，避免外层仍拿到半成品数据

建议补充校验点：

1. 单行 `FileData` 能完整更新协议主表
2. 多行 `FileData` 不会误写到错误协议
3. Base64 解码失败或内容格式异常时，日志与返回状态可追踪

### 任务单 5：进入业务接入前的收口条件

在 `YhtYwService` 开始编码前，建议先满足以下收口条件：

1. `caps.201`、`caps.203`、实时校验、`caps.304` 四项协议纠偏至少完成本地代码修正
2. 相关新增单测或最小构文断言已补齐
3. 至少完成一次一户通模块定向回归，确认没有把现有 `caps.305/303/304/306` 链路带坏
4. 满足上述条件后，再进入 `corpWalletSign/cancel` 的旧入口路由改造
