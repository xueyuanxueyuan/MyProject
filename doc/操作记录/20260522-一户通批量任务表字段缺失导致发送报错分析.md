# 一户通批量任务表字段缺失导致发送报错分析

## 1. 现象

批量收款场景调用：

`/api/v1/ywgl/addSkywPlsk`

报错核心日志为：

1. `Unknown column 'platform_batch_no' in 'field list'`
2. 报错定位到 `YhtBatchTaskDao.java`
3. 触发 SQL：

```sql
SELECT
  id, req_id, batch_no, corp_no, biz_type, total_count, total_amt,
  success_count, fail_count, processing_count, batch_status, error_code, error_msg,
  platform_batch_no, fee_no, file_name, corp_acct_no, tran_code, success_amt,
  check_date, qdbm, created_time, del_flag, creator, revision, zxbh
FROM zjjs_zj_yht_batch_task
WHERE del_flag='0'
  AND (batch_no LIKE ?)
```

## 2. 触发位置

本次错误不是在真正发送 `caps.101` 时发生，而是在**发送前的防重发查询**就已经报错。

代码路径：

1. `YwglController.addSkywPlsk(...)`
2. `YwglServiceImpl.addSkywPlskjy(...)`
3. `YhtYwServiceImpl.addSkywPlskjy(...)`
4. 先执行：

```java
qw.likeRight(YhtBatchTaskDO::getBatchNo, skyw.getJslsh());
List<YhtBatchTaskDO> existingTasks = yhtBatchTaskDao.selectList(qw);
```

也就是：

1. 系统为了防止批量重复发起；
2. 先查 `zjjs_zj_yht_batch_task`；
3. 由于 `YhtBatchTaskDO` 实体映射了 `platform_batch_no`；
4. MyBatis-Plus 自动生成全字段 `SELECT`；
5. 数据库表里缺该字段，于是查询阶段直接失败；
6. 外层事务被标记回滚，最终抛出 `UnexpectedRollbackException`。

## 3. 根因

根因不是业务参数错误，也不是一户通接口报错，而是：

**当前运行环境中的表 `zjjs_zj_yht_batch_task` 结构落后于当前代码版本。**

代码证据：

### 3.1 实体已声明该字段

`YhtBatchTaskDO` 中明确存在：

1. `platformBatchNo -> platform_batch_no`
2. `feeNo -> fee_no`
3. `corpAcctNo -> corp_acct_no`
4. `tranCode -> tran_code`
5. `successAmt -> success_amt`
6. `checkDate -> check_date`

说明当前代码版本已经把这些字段视为表结构的一部分。

### 3.2 DAO 没有手写 SQL

`YhtBatchTaskDao` 只是 `BaseMapper<YhtBatchTaskDO>`，没有自定义 XML。

因此报错 SQL 不是手工写错，而是 MyBatis-Plus 根据 `YhtBatchTaskDO` 自动展开全字段查询。

### 3.3 当前仓库未发现对应补库脚本

本地已检索 `doc/数据库脚本`，没有发现为 `zjjs_zj_yht_batch_task` 增加：

1. `platform_batch_no`
2. `fee_no`
3. `corp_acct_no`
4. `tran_code`
5. `success_amt`
6. `check_date`

的明确升级脚本。

这进一步说明：

1. 可能代码先行了；
2. 但测试环境库表还没同步到位；
3. 或者补库脚本没有归档进当前仓库。

## 4. 影响范围

这个问题不只影响“批量收款发送”。

凡是对 `YhtBatchTaskDO` 做普通查询的地方，都可能在当前环境报同类错，例如：

1. 批量收款发起前的防重发查询
2. 批量任务分页查询
3. 批量回执处理按批次号/申请号查任务
4. 批量结果文件解析时按 `reqId` 查批次任务
5. 批量状态查询与结果提回链路

所以这不是单点接口问题，而是：

**整个一户通批量任务表访问链路都受影响。**

## 5. 修复建议

优先建议修数据库，而不是先改代码绕过去。

原因：

1. 这些字段当前代码后续本来就要使用；
2. `platform_batch_no`、`fee_no` 等字段对批量回执、结果提回、平台批次号匹配都有意义；
3. 如果把代码里的字段临时删掉或 `exist = false`，会造成后续回执/查询链路继续缺能力。

### 5.1 建议先核实现网表结构

先在报错环境执行：

```sql
DESC zjjs_zj_yht_batch_task;
```

或：

```sql
SHOW CREATE TABLE zjjs_zj_yht_batch_task;
```

重点核对是否存在以下列：

1. `platform_batch_no`
2. `fee_no`
3. `corp_acct_no`
4. `tran_code`
5. `success_amt`
6. `check_date`

### 5.2 如果确认缺失，按代码补齐字段

可参考如下 SQL 方向处理：

```sql
ALTER TABLE zjjs_zj_yht_batch_task
  ADD COLUMN platform_batch_no VARCHAR(64) NULL COMMENT '平台批次号，caps.102应答返回的BatchNo',
  ADD COLUMN fee_no VARCHAR(32) NULL COMMENT '费项代码',
  ADD COLUMN corp_acct_no VARCHAR(64) NULL COMMENT '企业账号',
  ADD COLUMN tran_code VARCHAR(16) NULL COMMENT '交易代码：40501=代付，40502=代收',
  ADD COLUMN success_amt DECIMAL(18,2) NULL COMMENT '成功金额',
  ADD COLUMN check_date VARCHAR(16) NULL COMMENT '对账日期';
```

注意：

1. 长度、注释、列顺序可按现网规范调整；
2. 如果其中部分列已存在，需要拆开逐列执行；
3. 如果现网要求保留字符集、排序规则、默认值规范，也要同步遵守。

## 6. 不推荐的临时方案

不推荐为了让当前接口先跑通，就把 `YhtBatchTaskDO` 中这些字段直接去掉或标记 `exist = false`。

原因：

1. 这会掩盖真实的库表版本不一致问题；
2. 批量回执和结果提回后续本来就依赖这些字段；
3. 临时绕过后，可能把问题从“发起前报错”变成“回执时再报错”，风险更隐蔽。

## 7. 结论

本次报错的本质是：

1. 当前代码版本中的 `YhtBatchTaskDO` 已经扩展出 `platform_batch_no` 等批量任务字段；
2. 测试环境表 `zjjs_zj_yht_batch_task` 还没有同步这些字段；
3. 批量收款发起前执行防重发查询时，MyBatis-Plus 自动查询全字段；
4. 因数据库缺列而直接失败；
5. 外层事务回滚，最终表现为结算发送报错。

一句话结论：

**这是库表结构落后于代码版本导致的批量任务查询失败，不是一户通报文发送失败。**
