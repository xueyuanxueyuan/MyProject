# 更新规范后实时与批量交易实施链路重梳理

## 1. 目的

基于更新后的原始接口文档《上海集中代收付系统报文交换规范V1.2.7.7》，重新梳理当前项目中：

1. 实时交易实施链路；
2. 批量交易实施链路；
3. 规范口径与当前实现的对应关系；
4. 仍然存在的差异点与联调关注点。

## 2. 原始规范确认后的核心口径

### 2.1 交易码

更新后的原始规范明确：

1. `20601`：实时代付
2. `20602`：实时代收
3. `40501`：批量代付
4. `40502`：批量代收

### 2.2 报文族

#### 实时交易

1. `caps.201`：实时业务申请
2. `caps.202`：实时业务应答
3. `caps.203`：实时业务查询
4. `caps.204`：实时业务查询应答
5. `caps.205`：实时业务处理结果回执

#### 批量交易

1. `caps.101`：批量业务申请
2. `caps.102`：批量业务应答
3. `caps.103`：批量业务状态查询
4. `caps.104`：批量业务状态查询应答
5. `caps.105`：批量业务结果提回
6. `caps.106`：批量业务结果提回应答
7. `caps.107`：批量业务处理结果回执

### 2.3 规范流程要求

#### 实时

规范要求：

1. 发起 `caps.201`
2. 接收同步 `caps.202`
3. 如企业支持推送，接收异步 `caps.205`
4. 如不支持主动推送，发起 `caps.203`，获得 `caps.204`
5. 收到 `caps.205` 或确认 `caps.204` 终态后，再进行行内业务处理

#### 批量

规范要求：

1. 发起 `caps.101`
2. 接收同步 `caps.102`
3. 如企业支持推送，接收异步 `caps.107`
4. 如不支持主动推送，发起 `caps.103`，获得 `caps.104`
5. 批量处理完成后，发起 `caps.105`
6. 接收 `caps.106`，解析结果文件
7. 收到 `caps.107` 后先回 `caps.900`，再进行行内业务处理
8. 解析 `caps.106` 或 `caps.107` 中的结果文件后更新本地相关业务信息

## 3. 当前实时交易实施链路

### 3.1 接口入口

当前控制器入口：

1. `/yht/realtime/submit`
2. `/yht/realtime/status`
3. `/yht/receive`

分别对应：

1. 实时发起
2. 实时状态查询
3. 异步回执接收

### 3.2 实时发起链路

当前链路：

1. 业务层 `YwglServiceImpl`
2. 分流到 `YhtYwServiceImpl`
3. 控制器/服务调用 `yhtService.submitRealtimeTrade(...)`
4. 编排器 `YhtRealtimeTradeSubmitOrchestrator`
5. 报文构造器 `YhtRealtimeTradeMessageBuilder.buildCaps201(...)`
6. 发送 `caps.201`
7. 解析同步 `caps.202`

### 3.3 实时查询链路

当前链路：

1. `/yht/realtime/status`
2. `yhtService.queryRealtimeTradeStatus(...)`
3. `YhtRealtimeStatusQueryOrchestrator`
4. 构造 `caps.203`
5. 发送查询
6. 解析 `caps.204`

### 3.4 实时回执链路

当前链路：

1. `/yht/receive`
2. `yhtService.receiveCallback(...)`
3. `YhtInboundCallbackFacade.handle(...)`
4. 按 `caps.205` 分发到 `YhtRealtimeCallbackProcessor`

### 3.5 实时业务联动现状

当前已确认：

1. `20601` 单笔付款回执已联动 `fkywJfJgCl(...)`
2. `20602` 单笔收款回执已联动 `skywJfJgCl(...)`

这说明实时交易这条线，已经从“只收敛一户通任务”演进到“回执后可直接推进结算主业务”。

## 4. 当前批量交易实施链路

### 4.1 接口入口

当前控制器入口：

1. `/yht/batch/submit`
2. `/yht/batch/status`
3. `/yht/receive`
4. `/yht/batch/queryTaskPage`
5. `/yht/batch/queryDetailPage`

分别对应：

1. 批量发起
2. 批量状态查询
3. 异步回执接收
4. 批次任务分页查询
5. 批次明细分页查询

### 4.2 批量发起链路

#### 批量付款

当前链路：

1. `YwglServiceImpl.addFkywPlfkjy(...)`
2. 当 `Jsqd=YHT` 时转 `YhtYwServiceImpl.addFkywPlfkjy(...)`
3. 设置：
   - `batchNo = fkyw.getJslsh()`
   - `bizType = PAY`
4. 调用 `yhtService.submitBatchTrade(reqDTO)`
5. 控制器 `/yht/batch/submit`
6. 发送 `caps.101`
7. 解析同步 `caps.102`

#### 批量收款

当前链路：

1. `YwglServiceImpl.addSkywPlskjy(...)`
2. 当 `Jsqd=YHT` 时转 `YhtYwServiceImpl.addSkywPlskjy(...)`
3. 先按付款银行分组
4. 每个子分组生成一个子批次
5. 设置：
   - `batchNo = skyw.getJslsh() + "-" + groupIndex`
   - `bizType = COLLECT`
6. 调用 `yhtService.submitBatchTrade(reqDTO)`
7. 发送 `caps.101`
8. 解析同步 `caps.102`

### 4.3 批量状态查询链路

当前链路：

1. `/yht/batch/status`
2. `yhtService.queryBatchByCaps103(...)`
3. 发送 `caps.103`
4. 解析 `caps.104`

另外已有内部作业/补偿逻辑会主动触发 `queryBatchByCaps103(...)`，说明项目并不是只依赖 `caps.107` 推送，也已经具备主动查状态能力。

### 4.4 批量回执链路

当前链路：

1. `/yht/receive`
2. `yhtService.receiveCallback(...)`
3. `YhtInboundCallbackFacade.handle(...)`
4. `caps.107` 被识别为 `BATCH_RESULT`
5. 分发到 `YhtBatchCallbackProcessor.handle(...)`

### 4.5 批量结果文件处理链路

当前批量回执和批量状态编排都会复用：

- `YhtBatchResultFileProcessor`

主要作用：

1. 解析 Base64 的 `FileData`
2. 逐条匹配 `serialNum/detailSeq`
3. 更新 `YhtBatchDetailDO`
4. 汇总成功/失败/处理中数量
5. 刷新 `YhtBatchTaskDO`

## 5. 更新后最重要的对照结论

### 5.1 实时链路结论

实时这条线和新规范的主流程已经基本对齐：

1. 有 `201/202`
2. 有 `203/204`
3. 有 `205`
4. `205` 回执后已能推进主业务

但仍然存在历史差异点：

1. `caps.201` 请求字段签名和校验口径曾有偏差
2. `caps.203` 查询报文结构曾与原始规范存在差异

所以实时链路的主问题已经不在“有没有链路”，而在“构文是否完全严格贴合最新规范”。

### 5.2 批量链路结论

批量这条线和新规范相比，现状是“前半段齐、后半段偏弱”。

#### 已经具备

1. `101/102` 发起与同步应答
2. `103/104` 状态查询
3. `107` 回执接收
4. 结果文件解析
5. 批次与明细台账收敛

#### 还偏弱或需继续确认

1. 规范强调批量终态应以 `105/106` 结果提回文件为重要更新依据；
2. 当前代码中已明确看到 `103/104` 查询实现；
3. 但本轮没有直接确认到对外显式的 `105/106` 提回入口与完整落地主业务链；
4. 当前已确认的 `107` 回执处理仍主要落在一户通台账 `YhtProtocolTaskDO/YhtBatchTaskDO/YhtBatchDetailDO`；
5. 还没有像单笔 `205 -> fkywJfJgCl/skywJfJgCl` 那样，看到批量 `107/106 -> ZjPlfkmx/ZjPlskmx/YwJg` 的清晰主业务联动入口。

## 6. 新规范下的实施建议

### 6.1 实时交易

建议把实时链路视为“两条终态来源”：

1. 优先 `caps.205`
2. 兜底 `caps.204`

业务处理策略：

1. 收到 `205` 后立即推进主业务；
2. 如果没有收到 `205`，则通过 `203/204` 查询推进；
3. 保证两条路最终落到同一套业务结果处理方法。

### 6.2 批量交易

建议把批量链路视为“三段式”：

1. `101/102`：提交并拿到平台批次号
2. `103/104`：轮询批次状态
3. `105/106` 或 `107`：拿明细终态并推进本地业务

业务处理策略：

1. `107` 用于尽快感知批次终态并先回写一户通台账；
2. `106` 结果文件作为本地批量明细终态更新的重要依据；
3. 最终应把 `YhtBatchDetailDO` 的结果映射回：
   - `ZjPlfkmx`
   - `ZjPlskmx`
   - 必要时汇总推进 `Fkyw/Skyw/YwJg`

## 7. 当前最值得继续补的缺口

按新规范看，后续最值得补的是批量交易后半段：

1. 明确 `caps.105/106` 的现有实现位置；
2. 明确 `YhtBatchDetailDO.serialNum` 如何映射回本地批量明细 `refseqno1/mxlsh`；
3. 明确批量终态如何驱动 `ZjPlfkmx/ZjPlskmx` 更新；
4. 明确批量全部成功、全部失败、部分成功时，主业务 `YwJg` 应如何推进。

## 8. 一句话总结

更新后的原始规范把链路边界讲得更清楚了：

1. 实时交易：`201/202 + 205 或 203/204`
2. 批量交易：`101/102 + 103/104 + 105/106 + 107`

而当前项目实现：

1. 实时交易已经基本形成闭环；
2. 批量交易已经完成“接入、查询、回执、结果台账收敛”的前半段；
3. 但“批量终态反写本地主业务”的后半段，仍是后续最重要的实现重点。
