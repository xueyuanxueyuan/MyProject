### 4. 图谱中心节点

从“规模 + 依赖 + 业务中心性”三个维度看，当前最关键的图谱中心节点如下：

1. `zjjs-ywgl`
2. `cwhs-jzgl`
3. `zjjs-zhgl`
4. `jshs-gm-agg`
5. `zjjs-core`

原因：

- `zjjs-ywgl` 与 `cwhs-jzgl` 两个模块合计占总代码量 71.4%
- `jshs-gm-agg` 是统一外部入口，天然是请求进入图谱的上游枢纽
- `zjjs-core` 虽代码量不大，但提供跨模块复用的 DTO、枚举与工具，属于高连接度节点

## 三、风险与异常边

从 Graphify 视角看，当前系统存在以下“高风险关系边”：

### 1. 循环耦合边

- `ywgl-busi -> cwhs-api`
- `cwhs-busi -> ywgl-api`
- `zhgl-busi -> ywgl-api / cwhs-api`

这会让知识图谱中出现高密度双向连线，降低模块边界清晰度。

### 2. 分层违例边

- `ywgl-busi -> zbkh-busi`

该边直接跨到其他模块的 `busi` 层，违反“业务层优先只依赖 API 层”的设计预期。

### 3. 重复节点簇

- `api` 与 `api-v2` 在多个模块中高度重复
- `YwglV2Controller` 与 `YwglController` 存在大量同构路由

这会在图谱中形成“重复节点簇”，增加维护成本，也会稀释真实业务主干。

1. 当前 `d:\Probject\Gjj` 本质是文档仓，Graphify 在这里首先构建出来的是“知识资料图谱”，不是“源码调用图谱”
2. 真正的大型业务系统 `capinfo-gjj-busi-jshs` 目前只以勘查报告形式被记录在文档中，尚未在当前工作区落盘
