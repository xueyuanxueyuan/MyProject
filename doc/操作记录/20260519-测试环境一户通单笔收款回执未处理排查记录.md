# 测试环境一户通单笔收款回执未处理排查记录

## 1. 现象

测试通过结算系统发起一户通单笔收款业务后，挡板向结算服务推送 `caps.205.001.01` 实时交易回执。

日志显示：

- `YhtController.receive` 已接收到回执；
- 接口已返回 `caps.900` 成功确认；
- 但结算侧单笔收款业务数据未继续推进。

用户提供的关键回执内容：

- `MesgType=caps.205.001.01`
- `TranCode=20602`
- `CorpNo=1111`
- `SerialNum=1779183670955`
- `SysSeqNo=MOCK-SYS-1779183671378`
- `RetCode=000000`

## 2. 回调实际代码链路

当前接收链路如下：

1. `YhtController.receive`
2. `YhtServiceImpl.receiveCallback`
3. `YhtInboundCallbackFacade.handle`
4. `YhtRealtimeCallbackProcessor.handle`

对应代码位置：

- `YhtController.receive` 仅负责接收原始报文并调用 `yhtService.receiveCallback(rawMessage)`。
- `YhtServiceImpl.receiveCallback` 仅负责调用回调门面，并在事务提交后确认 `MesgId`。
- `YhtInboundCallbackFacade` 在识别到 `caps.205.001.01` 后，会调用 `businessHandler.handleRealtimeResult(...)`。
- `YhtRealtimeCallbackProcessor.handle` 负责解析 `caps.205`、定位一户通实时任务、更新任务状态。

## 3. 已确认的事实

### 3.1 `caps.205` 回调不是没有进入系统

从用户日志可确认：

- `YhtController.receive` 已执行；
- `YhtService.receiveCallback` 没有抛异常；
- 系统成功返回了 `caps.900`；
- 因此“挡板没有推到系统”这一层可以基本排除。

### 3.2 `caps.205` 当前只更新一户通任务表，不处理结算业务表

`YhtRealtimeCallbackProcessor.handle` 的处理动作只有这些：

- 解析 `caps.205`；
- 根据 `corpNo + tranCode + serialNum + sysSeqNo` 定位 `zjjs_zj_yht_protocol_task` 中的实时任务；
- 调用 `YhtRealtimeReceiptProcessor.applyReceipt(...)` 计算 `bizStatus/errorCode/errorMsg`；
- 通过 `YhtProtocolTaskStateUpdater.updateByExpectedStatusWithOutcome(...)` 更新一户通任务快照。

该处理器中**没有**以下动作：

- 没有注入 `YwglService`；
- 没有调用 `skywJfJgCl(...)`；
- 没有更新 `Skyw`、`YwJg` 等结算业务表；
- 没有发送“单笔收款结果处理”相关业务事件。

这说明当前 `caps.205` 回调落地后，最多只会把一户通任务状态改掉，不会把结算单笔收款业务继续往下推进。

### 3.3 结算单笔收款的“业务结果处理”仍走老链路

结算业务真正推进收款结果的核心方法是：

- `YwglServiceImpl.skywJfJgCl(...)`

该方法会：

- 通过 `jslsh` 查询 `Skyw`；
- 校验金额；
- 更新 `Skyw` 业务状态；
- 更新或新增 `YwJg`；
- 触发后续对账处理。

但是这个方法当前的调用入口在另一条链路：

- `YqzlYwServiceImpl.skJyJgJs(...)`

也就是说，现有结算业务结果处理仍然依赖“银企直连接口返回结果”的老入口，而不是一户通 `caps.205` 回调入口。

## 4. 为什么会出现“回执收到了，但业务没处理”

根因不是控制器没收到报文，而是**一户通回调链路与结算业务结果处理链路没有打通**。

当前系统的行为实际上是：

1. 一户通模块收到 `caps.205`；
2. 一户通模块返回 `caps.900`；
3. 一户通模块只更新 `zjjs_zj_yht_protocol_task`；
4. 结算主业务表 `Skyw/YwJg` 没有收到任何推进动作；
5. 所以用户看到“挡板结果收到了，但业务数据没处理”。

## 5. 任务匹配层面的补充判断

本次日志中的关键字段：

- `TranCode=20602`
- `SerialNum=1779183670955`
- `SysSeqNo=MOCK-SYS-1779183671378`

从发送链路看，单笔收款发起时：

- `YhtYwServiceImpl.addSkywDbskjy(...)` 会把 `skyw.getJslsh()` 作为 `serialNum` 传入一户通；
- `YhtRealtimeDispatchBoundaryServiceImpl.prepare(...)` 会把该 `serialNum` 存入任务表的 `remark` 字段；
- `YhtRealtimeDispatchBoundaryServiceImpl.complete(...)` 在同步应答为 `caps.202` 时会把 `SysSeqNo` 回填到 `protocolNo` 字段；
- 即使同步阶段尚未拿到 `SysSeqNo`，`YhtRealtimeTaskLocator.findForCallback(...)` 也实现了“按 `serialNum` + `protocol_no is null`”的补偿匹配。

因此，**从当前代码实现看，任务匹配并不是最可疑的第一根因**。  
更大的断点是：即便匹配成功，后续也只更新一户通任务表，不会处理结算业务表。

## 6. 结论

本次问题的主根因可归纳为：

> 一户通 `caps.205` 回调链路只完成“一户通任务状态收敛”，没有接入结算系统既有的“单笔收款业务结果处理”入口，因此出现“日志显示收到挡板推送并返回 `caps.900`，但业务数据未处理”的现象。

## 7. 修复建议

建议按下面方向补齐：

1. 在 `caps.205` 成功匹配到实时任务后，补充结算业务联动处理。
2. 对单笔收款 `20602` 成功回执，按 `serialNum=jslsh` 组装 `ZjjsSFkywJgAddReqDTO`。
3. 调用结算现有结果处理入口 `YwglServiceImpl.skywJfJgCl(...)`，而不是重复造一套业务更新逻辑。
4. 对失败回执补充失败态映射，至少保证 `Skyw/YwJg` 能看到失败结果或转人工。
5. 增加测试：
   - `caps.205 20602 + RetCode=000000` 时，除更新一户通任务表外，还应推进收款业务；
   - `caps.205` 匹配不到任务时，必须明确记录告警日志；
   - `caps.205` 失败码时，应验证结算业务失败态或人工介入态。

## 8. 本次排查结论摘要

- 回执已经进入结算服务，不是“没收到”。
- `caps.205` 当前能返回 `caps.900`，但业务处理只停留在一户通任务表。
- 结算单笔收款真正的结果处理逻辑在 `YwglServiceImpl.skywJfJgCl(...)`。
- 一户通回调链路目前没有调用这条业务处理链，所以业务数据不会自动推进。
