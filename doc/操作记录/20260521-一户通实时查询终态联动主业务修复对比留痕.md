# 一户通实时查询终态联动主业务修复对比留痕

## 1. 对比范围

本次对比只覆盖实时查询终态联动相关文件：

1. `YhtRealtimeStatusQueryOrchestrator`
2. `YhtRealtimeCallbackProcessor`
3. `YhtRealtimeBusinessResultDispatcher`
4. `YhtRealtimeStatusQueryOrchestratorTest`
5. `YhtServiceImplCallbackTest`

## 2. 改动前

### 2.1 查询链路

`YhtRealtimeStatusQueryOrchestrator` 在收到 `caps.204` 后只做：

1. `realtimeReceiptProcessor.applyReceipt(...)`
2. 更新 `YhtProtocolTaskDO.bizStatus / protocolNo / remark / respBody`
3. 返回查询结果

未做：

1. `fkywJfJgCl(...)`
2. `skywJfJgCl(...)`

### 2.2 回执链路

`YhtRealtimeCallbackProcessor` 自己负责：

1. 解析 `caps.205`
2. 判断交易类型与终态
3. 拼装 `ZjjsSFkywJgAddReqDTO`
4. 直接调用 `YwglService`

问题在于：

1. `caps.205` 与 `caps.204` 的主业务联动逻辑分散；
2. 查询链路没有和回执链路收敛到同一入口。

## 3. 改动后

### 3.1 新增共享分发入口

新增 `YhtRealtimeBusinessResultDispatcher`，统一承接：

1. `caps.205` 回执终态
2. `caps.204` 查询终态

统一输出到：

1. `YwglService.fkywJfJgCl(...)`
2. `YwglService.skywJfJgCl(...)`

### 3.2 查询链路变化

`YhtRealtimeStatusQueryOrchestrator` 新增：

1. 注入 `YhtRealtimeBusinessResultDispatcher`
2. 在 `caps.204` 状态原子更新成功后，调用 `dispatchFromQuery(...)`

效果是：

1. 查询终态不再只更新任务台账；
2. 查询终态也会继续推进结算主业务。

### 3.3 回执链路变化

`YhtRealtimeCallbackProcessor` 改为：

1. 保留任务匹配和状态更新；
2. 不再自行组装主业务调用；
3. 状态更新成功后改为调用 `dispatchFromCallback(...)`

效果是：

1. 回执链路仍保持原行为；
2. 与查询链路使用同一套主业务分发逻辑。

### 3.4 测试变化

新增 `YhtRealtimeStatusQueryOrchestratorTest`：

1. 覆盖付款查询成功联动；
2. 覆盖收款查询成功联动。

调整 `YhtServiceImplCallbackTest`：

1. 测试夹具改为装配共享分发组件；
2. 原 `caps.205` 回调断言继续成立。

## 4. 一句话对比结论

改动前是：

1. `caps.205` 能推进主业务；
2. `caps.204` 只能更新任务状态。

改动后是：

1. `caps.205` 和 `caps.204` 都会在终态时推进主业务；
2. 两条路径共用同一套分发逻辑，行为一致。
