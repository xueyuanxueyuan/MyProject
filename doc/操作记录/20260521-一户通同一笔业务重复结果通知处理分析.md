# 一户通同一笔业务重复结果通知处理分析

## 1. 问题定义

本次关注的不是“不同业务重复提交”，而是：

1. 同一笔一户通业务；
2. 已经收到过一次结果通知；
3. 又收到第二次结果通知；
4. 系统会不会重复处理。

这里要区分两种重复：

1. **同一个 `MesgId` 的重复回执**
2. **不同 `MesgId`，但指向同一笔业务的重复回执**

这两种情况，当前代码处理结果并不一样。

## 2. 第一层：入口按 `MesgId` 判重

回执统一入口在 `YhtInboundCallbackFacade`。

当前逻辑：

1. 先从报文头提取 `MesgId`
2. 调用 `idempotentService.acquireMesgId(corpNo, mesgId)`
3. 如果获取失败，说明这个 `MesgId` 已经处理过
4. 直接返回 `caps.900` 成功确认，不再进入业务处理

因此：

### 2.1 结论

如果第二次通知和第一次通知是**同一个 `MesgId`**，那么：

1. 第二次通知会在入口被拦住；
2. 不会再进入实时/批量回执处理器；
3. 不会再次推进主业务。

这部分是**真正的入口幂等**。

## 3. 第二层：任务状态更新的终态保护

如果第二次通知的 `MesgId` 不同，但仍然匹配到同一笔业务，就会继续进入：

1. 实时：`YhtRealtimeCallbackProcessor`
2. 批量：`YhtBatchCallbackProcessor`

这里主要依赖 `YhtProtocolTaskStateUpdater.updateByExpectedStatusWithOutcome(...)` 做条件更新和终态保护。

它的设计特点是：

1. 如果当前已经是终态，且本次想改成**另一个终态**，会返回 `SKIPPED_FINAL`
2. 如果当前已经是终态，且本次还是**同一个终态**，允许更新 `respBody / receiveTime / errorCode` 等字段

因此它不是“终态后完全拒绝任何再次处理”，而是：

1. **拒绝终态冲突**
2. **允许同终态重复收敛**

## 4. 实时链路的真实行为

## 4.1 同 `MesgId` 重复回执

结果：

1. 在 `YhtInboundCallbackFacade` 直接返回 `caps.900`
2. 不会走到 `YhtRealtimeCallbackProcessor`
3. 不会再次调用 `fkywJfJgCl(...) / skywJfJgCl(...)`

这一种是安全的。

## 4.2 不同 `MesgId`，但同一笔实时业务收到同样终态回执

实时回执处理器 `YhtRealtimeCallbackProcessor` 的流程是：

1. 用 `corpNo + tranCode + serialNum + sysSeqNo` 匹配本地任务
2. 记录 `expectedBizStatus = task.getBizStatus()`
3. 根据 `retCode` 计算目标业务状态
4. 调用 `updateByExpectedStatusWithOutcome(...)`
5. 更新成功后调用 `businessResultDispatcher.dispatchFromCallback(...)`

关键点在第 4 步：

如果第一次通知已经把任务更新成 `SUCCESS`，第二次通知也是 `SUCCESS`，则：

1. `expectedBizStatus` 会读到 `SUCCESS`
2. `targetBizStatus` 也是 `SUCCESS`
3. 条件更新会**成功**
4. `dispatchFromCallback(...)` 会再次执行

### 4.2.1 结果判断

这意味着：

**不同 `MesgId` 的同终态重复实时回执，不会被回执层完全挡住，仍可能再次触发主业务处理。**

## 4.3 主业务层是否还能兜住

### 4.3.1 单笔付款 `fkywJfJgCl(...)`

当前付款主业务处理会：

1. 先按 `Jslsh` 查 `Fkyw`
2. 再查已有 `YwJg`
3. 若已有 `YwJg` 则更新，否则新增
4. 无论新增还是更新，后面都会继续：
   - 更新银行日记账
   - 调 `tzYwjz(...)`

因此：

1. `YwJg` 本身不会重复新增
2. 但**日记账更新和通知链路仍可能重复执行**

所以单笔付款目前是：

**部分幂等，不是完全幂等。**

### 4.3.2 单笔收款 `skywJfJgCl(...)`

当前收款主业务处理会：

1. 按 `Jslsh` 查 `Skyw`
2. 查已有 `YwJg`
3. 如果已有 `YwJg` 且 `jszt >= 40`，直接抛“收款交易已完成结算”
4. 否则更新 `YwJg`
5. 再做 `bdSkJyDzcl(...)`

因此：

1. 如果第一笔结果已经把收款业务推进到“已完成结算”，第二次重复通知会被主业务层拒绝；
2. 但如果第一次结果还没把 `jszt` 推到该阈值，第二次通知仍可能再次进入更新和对账逻辑。

所以单笔收款目前是：

**有一定业务态保护，但也不是完全幂等。**

## 5. 批量链路的真实行为

`YhtBatchCallbackProcessor` 在收到 `caps.107` 后：

1. 按 `BatchNo` 找批次任务
2. 查协议任务
3. 根据批次状态映射 `bizStatus`
4. 用 `updateByExpectedStatusWithOutcome(...)` 更新协议任务
5. 更新批次任务
6. 解析结果文件并刷新聚合

### 5.1 同 `MesgId` 重复回执

和实时一样，会在入口被 `MesgId` 判重挡住。

### 5.2 不同 `MesgId`，但同一批业务重复通知

如果第二次通知仍然是相同终态：

1. 协议任务条件更新仍可能成功；
2. 结果文件会再次解析；
3. 明细状态会再次 `updateById(...)`；
4. 聚合会再次刷新。

但当前批量链路没有看到直接调用 `YwglService` 去推进结算主业务，因此：

1. **YHT 台账层会重复收敛**
2. **当前没看到像实时那样直接重复推进主业务**

所以批量当前更接近：

**台账层基本可重复覆盖，主业务层暂未接入，因此重复副作用相对小一些。**

## 6. 最终结论

## 6.1 可以明确安全的部分

### 同 `MesgId` 的重复结果通知

当前已经有入口幂等：

1. 第二次通知会被 `MesgId` 判重拦截；
2. 不会进入业务处理；
3. 这部分是安全的。

## 6.2 当前存在风险的部分

### 不同 `MesgId` 的同笔业务重复结果通知

当前代码并没有把这种情况完全挡住。

更准确地说：

1. **实时链路**：
   - 同终态重复通知仍可能通过条件更新；
   - 回执层可能再次调用主业务处理；
   - 付款的日记账更新和通知链路存在重复执行风险；
   - 收款在部分状态下也可能再次进入业务逻辑。
2. **批量链路**：
   - 会重复收敛任务/批次/明细状态；
   - 目前因为主业务反写本来就偏弱，所以重复副作用主要停留在 YHT 台账层。

## 6.3 一句话判断

当前系统对“同一笔业务收到两次结果通知”的处理能力是：

1. **同 `MesgId` 重复**：基本安全；
2. **不同 `MesgId`、同一业务重复结果**：  
   - **实时链路存在重复推进主业务的风险**；  
   - **批量链路主要是重复收敛台账状态，风险相对较轻。**

## 7. 建议方向

如果后续要补强，优先级建议如下：

### 7.1 第一优先级：实时主业务分发前增加“结果已消费”幂等判断

建议在 `YhtRealtimeBusinessResultDispatcher` 前增加：

1. 基于 `taskId + bizStatus + retCode` 的消费幂等键；
2. 或基于 `YwJg` 当前状态判断“已按该终态处理过”后直接跳过；
3. 让同终态重复回执只更新回执原文，不再重放主业务。

### 7.2 第二优先级：主业务入口补业务态幂等

建议在：

1. `fkywJfJgCl(...)`
2. `skywJfJgCl(...)`

补充：

1. 若当前 `YwJg` 已经是同终态，则直接返回；
2. 不再重复更新日记账；
3. 不再重复触发通知/对账。

### 7.3 第三优先级：增加重复回执测试

建议补测试覆盖：

1. 同 `MesgId` 的重复回执
2. 不同 `MesgId`、同终态的重复实时回执
3. 不同 `MesgId`、冲突终态的回执
4. 批量重复 `caps.107`

这样才能把“入口幂等”和“业务幂等”区分验证清楚。
