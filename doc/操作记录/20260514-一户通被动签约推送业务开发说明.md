# 一户通被动签约推送业务开发说明

## 1. 业务背景
根据需求，单位托收签约业务可由人行 CAPS 系统主动推送至中心（即由银行发起的被动签约）。中心接收到推送信息后，需要：
1. 立即返回通用确认报文（`caps.900`）告知 CAPS 平台已收妥。
2. 自动校验该单位是否符合托收签约条件，核心校验逻辑为：核验推送过来的单位名称（`CstmrNm`）以及基本账户银行账号（`DbtrActId`）是否与系统中单位登记信息相符。
3. 校验符合条件的，将签约信息存入托收签约结果表（`zjjs_zj_yht_protocol`）。不符合条件的拒绝录入。
4. 将校验通过与否的结果通过协议签约管理应答报文（`caps.306`）返回给 CAPS 及银行侧。

## 2. 改造排查与定位
* **入口定位**：所有的 CAPS 回执及主动推送均统一进入 `YhtController.receive` 接口，然后转交至 `YhtInboundCallbackFacade.handle`。
* **分发路由**：在 `YhtInboundCallbackFacade` 中，针对银行发起的被动签约请求，报文类型为 `caps.305.001.01` 且 `SndrFlg=BKSD`。该类型被解析并路由至专门的业务处理器：`YhtBankInitiatedSignProcessor`。
* **机制复用**：`YhtBankInitiatedSignProcessor` 已包含了“自动返回 `caps.900`”（由外层 `YhtServiceImpl.receiveCallback` 的同步提交后确认机制保证）以及“向下游构建和发送 `caps.306` 应答”的基础能力。

## 3. 核心代码改造 (`YhtBankInitiatedSignProcessor`)
1. **依赖注入扩充**：
   在 `YhtBankInitiatedSignProcessor` 中新增注入了往来客户领域服务：
   - `WlkhDmService`：用于核验往来客户（单位）主体信息。
   - `WlkhZhxxDmService`：用于核验往来客户名下的关联银行账户信息。
   - `YhtProtocolDao`：用于将签约结果落地持久化。

2. **新增业务校验逻辑 (`validateBusinessData`)**：
   - **名称核验**：通过 `WlkhDmService` 查询 `WlkhDO` 表，比对 `CstmrNm` 是否存在。若无匹配记录，校验直接失败。
   - **账号核验**：通过上一步获取到的往来客户主键 ID，调用 `WlkhZhxxDmService` 查出其关联的所有账户信息 `WlkhZhxxDO`，遍历核对其中登记的收款账号（`skzh`）是否与报文中的 `DbtrActId` 匹配。若不匹配，校验失败。

3. **新增签约入库逻辑 (`saveOrUpdateProtocol`)**：
   - 在业务校验通过后执行该方法。
   - 根据推送报文中的 `DbtrProtocol`（协议号）进行 `upsert` 操作。
   - 若操作类型为 `ADDD`（新增），则将状态置为 `ACTIVE` (已生效)，处理码置为 `CS00`，并记录生效及到期日期。
   - 若操作类型为 `DELE`（撤销），则将状态置为 `CANCELLED` (已注销)，处理码置为 `CS20`。

4. **流程编排更新 (`handle`)**：
   - 将原有的空 TODO 替换。
   - 当 `validateBusinessData` 校验失败时，阻断入库流程，并直接触发 `dispatchResponse` 发送 `ResFlag=FAIL` 的 `caps.306` 报文给 CAPS 拒绝该笔签约。
   - 校验通过后，调用入库逻辑，最后发送 `ResFlag=SUCC` 的 `caps.306` 报文告知签约成功。

## 4. 验证与结论
* 使用 `vfox` 环境下的 `mvn clean compile` 对 `capinfo-gjj-busi-zjjs-ywgl-basic-svc-busi` 模块进行了全量编译，期间修复了 MybatisPlus 的 `LambdaQueryWrapper` 泛型引入以及包名冲突问题。最终编译成功。
* 回调及分发机制已完全对齐需求①的所有规则。
