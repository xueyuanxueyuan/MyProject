# 一户通实时查询终态联动主业务修复记录

## 1. 背景

上一轮核对已确认：

1. `caps.202` 不是终态，不存在把申请应答直接当作最终结果处理业务数据的证据；
2. 系统存在 `caps.203 -> caps.204` 主动查询能力，也存在对应的定时补查任务；
3. 但查询链路拿到 `caps.204` 终态后，原实现只更新 `YhtProtocolTaskDO`，没有继续推进主业务。

这会带来一个实际风险：

1. 如果现场没有收到 `caps.205` 推送；
2. 但主动查询或补查已经拿到 `caps.204` 终态；
3. 则一户通任务台账会收敛，但结算主业务可能仍未处理。

## 2. 本次修复目标

将实时查询终态与实时回执终态收敛到同一套主业务处理入口，保证：

1. `caps.205` 回执拿到终态时可以推进主业务；
2. `caps.204` 查询拿到终态时也可以推进主业务；
3. `111111` 这类处理中状态仍然只更新任务状态，不误推进主业务。

## 3. 实现方案

### 3.1 抽取共享分发组件

新增 `YhtRealtimeBusinessResultDispatcher`，统一负责：

1. 判断交易类型：
   - `20601` 单笔付款
   - `20602` 单笔收款
2. 判断是否达到可推进主业务的终态：
   - 付款：`SUCCESS` 或 `FAIL`
   - 收款：`SUCCESS`
3. 构造 `ZjjsSFkywJgAddReqDTO`
4. 调用：
   - `YwglService.fkywJfJgCl(...)`
   - `YwglService.skywJfJgCl(...)`

### 3.2 `caps.205` 回执改为复用共享分发组件

`YhtRealtimeCallbackProcessor` 不再自己拼装 DTO 并直接调用 `YwglService`，而是改为：

1. 保留原有任务匹配、状态更新、终态保护；
2. 在任务状态成功更新后，调用共享分发组件；
3. 维持原有 `caps.205` 主业务联动语义不变。

### 3.3 `caps.204` 查询终态补齐主业务联动

`YhtRealtimeStatusQueryOrchestrator` 新增处理：

1. 当 `caps.204` 返回 `ResFlag=SUCC` 时，先按原逻辑调用 `realtimeReceiptProcessor.applyReceipt(...)` 更新任务状态；
2. 仅当任务状态原子更新成功后，再调用共享分发组件；
3. 如果并发保护命中、状态更新未生效，则不重复推进主业务。

### 3.4 查询路径金额回填策略

`caps.204` 本身不携带 `PayAmt`，而主业务处理需要金额校验，因此新增本地金额回填：

1. `20601` 单笔付款：按 `Jslsh` 查询 `Fkyw` 取金额；
2. `20602` 单笔收款：按 `Jslsh` 查询 `Skyw` 取金额；
3. 再把金额写入 `ZjjsSFkywJgAddReqDTO` 后交给主业务处理。

这样可以保证：

1. 查询路径不依赖 `caps.205` 才能拿到金额；
2. 查询终态也具备完整主业务落账所需字段。

## 4. 测试策略

本次按 RED -> GREEN 做了两层验证：

### 4.1 新增查询链路测试

新增 `YhtRealtimeStatusQueryOrchestratorTest`，覆盖：

1. `caps.204` 查询成功后联动单笔付款主业务；
2. `caps.204` 查询成功后联动单笔收款主业务。

### 4.2 回归既有回调测试

同步调整 `YhtServiceImplCallbackTest` 夹具，使 `caps.205` 仍然通过共享分发组件推进主业务，并保留既有行为断言。

## 5. 结果

本次修复后，实时链路的终态处理变为：

1. `caps.205` 终态 -> 更新任务状态 -> 推进主业务；
2. `caps.204` 终态 -> 更新任务状态 -> 推进主业务；
3. 两条路径共用同一套主业务结果分发逻辑。

## 6. 风险边界

本次只补齐了**实时交易**的查询终态联动，未改动批量链路。

当前仍需继续关注：

1. 批量 `caps.106/107` 是否反写本地批量明细；
2. 批量终态是否进一步推进 `Fkyw/Skyw/YwJg`；
3. 查询与回执重复到达时，是否还需要补更细的业务幂等保护。
