## 3. 代码对比留痕

### 3.1 回调处理器改前

`YhtRealtimeCallbackProcessor` 之前的职责只有：

1. 解析 `caps.205`；
2. 匹配 `zjjs_zj_yht_protocol_task`；
3. 更新一户通任务状态。

存在的问题：

- 即使 `20602` 单笔收款回执成功，也不会调用结算业务处理；
- 业务表 `Skyw/YwJg` 不会被推进；
- 联调日志只能看到“收到回执”和“返回 `caps.900`”，看不到业务联动是否执行。

### 3.2 回调处理器改后

新增逻辑：

1. 仅在 `tranCode=20602` 且任务状态成功收敛后，触发单笔收款业务联动；
2. 通过 `ObjectProvider<YwglService>` 延迟获取业务服务，避免一户通回调链路与结算业务服务形成硬依赖初始化问题；
3. 根据回执报文组装 `ZjjsSFkywJgAddReqDTO`：
   - `jslsh <- SerialNum`
   - `yhjslsh <- SysSeqNo`
   - `yhje <- PayAmt`
   - `jyrq <- CheckDate`
4. 调用 `skywJfJgCl(...)` 复用现有结算单笔收款结果处理逻辑；
5. 补充“开始处理 / 完成处理 / 暂不触发处理”日志。

### 3.3 业务处理兼容性调整

`YwglServiceImpl.skywJfJgCl(...)` 原本依赖 `zffs` 推导 `jslx`。

本次兼容调整：

- 当一户通回调未提供 `zffs` 时，优先保留原收款业务已有的 `jslx`；
- 仅在原值为空时，才回退到默认 `ZZSK`；
- 避免因为一户通回调缺少 `zffs`，把原业务类型误覆盖掉。

### 3.4 自动化测试改动

新增/补强测试点：

1. `20602` 成功回执时，验证会调用 `ywglService.skywJfJgCl(...)`；
2. 校验 DTO 映射结果：
   - `jslsh`
   - `yhjslsh`
   - `jyrq`
   - `yhje`
3. 校验新增日志中包含“`caps.205单笔收款业务处理完成`”；
4. 对现有 `20601` 回执测试补充断言，确保不会误触发单笔收款业务处理。

### 5.2 验证过程中的真实阻塞根因

最初“类找不到”的判断并不准确，真实根因是 **Maven 调用方式不对**：

1. `YhtBatchDetailRespDTO`、`YhtBatchTaskRespDTO`、`YhtBatchTaskPageReqDTO`、`YhtBatchDetailPageReqDTO`、`CorpWalletSignReqDTO`、`CorpWalletCancelReqDTO` 实际都存在于 `basic-svc-api` 模块；
2. 之前只编了 `basic-svc-busi`，没有把其依赖模块一起纳入 reactor，导致编译时看起来像“缺失类”；
3. 改用 `-am` 后，依赖模块会一并构建；
4. 再加上 `-Dsurefire.failIfNoSpecifiedTests=false`，即可避免 reactor 中其他无匹配测试的模块提前失败。
