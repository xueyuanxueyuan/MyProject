# 20260512-枣庄-凭证汇总改造-V1.1-P0修复方案

## 1. 修复目标（对齐口径）
当前实现的关键偏差是：**汇总口径名义上引入 `yhzhhm/ywfl`，但汇总组装与标记回写仍按 `ywlx` 维度拆分/更新**，导致无法满足“按 `yhzhhm + ywfl` 汇总替代按 `ywlx` 汇总”的要求。

本修复方案目标：
1. **汇总聚合维度统一**：全链路以 `jzrq + ztbh + zzbj + jzlxfl + yhzhhm + ywfl`（再按 `kmbh` 展开分录）作为汇总口径。
2. **汇总落库一致**：`cwhs_hzpz` 一张汇总凭证对应一个 `(yhzhhm,ywfl,jzlxfl)` 分组。
3. **标记回写精准**：`cwhs_pz.hzpzh/jzbj` 的更新范围与汇总分组一致，禁止靠 `ywlx` 更新导致“串汇总号”。
4. **开关可控可回退**：新旧 SQL/逻辑切换在配置项真实落地后可控。

## 2. 修复方案总览（推荐路径）
### 2.1 推荐方案 A（推荐）
- **SQL 层**：`getJzpzhz` 的 `GROUP BY` 从包含 `a.ywlx` 改为按 `yhzhhm+ywfl(+jzlxfl/xtlx)` 聚合；`ywlx` 如需保留仅作为“兼容展示字段”，采用聚合列（例如 `MIN(a.ywlx)`）。
- **Service 层**：`zdpzhz` 由 “jzlxfl -> ywlx” 二级分组，改为 “jzlxfl -> (yhzhhm,ywfl)” 二级分组。
- **回写层**：`pzhzJzbjXg` 更新条件由 `eq ywlx` 改为 `eq yhzhhm + eq ywfl`（必要时保留 `eq jzlxfl/zzbj/jzrq/ztbh`）。
- **附件数**：`getDjdjsHj` 新增/改造为“按 yhzhhm+ywfl 统计”，避免再依赖 `ywlx`。

### 2.2 备选方案 B（不推荐，仅止血）
- 仅在 `zdpzhz/pzhzJzbjXg` 中按 `yhzhhm+ywfl` 进行二次聚合/更新，但仍维持 `getJzpzhz` 以 `ywlx` 切分。
- 缺点：数据先按 `ywlx` 被拆碎，再由 Java 合并，容易遗漏边界并增加复杂度；不如方案 A “上游就按口径出数”干净。

### 3.1 SQL：修复 `getJzpzhz` 的分组维度（P0）
当前版本仍 `GROUP BY a.ywlx`（导致同 `yhzhhm+ywfl` 下多个 `ywlx` 无法合并）。

**改造建议：**
1. `SELECT` 中 `a.ywlx` 改为聚合列，例如 `MIN(a.ywlx) AS ywlx`（仅用于兼容展示/摘要兜底，不参与分组）。
2. `GROUP BY` 移除 `a.ywlx`，保留（建议）：
   - `a.jzlxfl, a.xtlx`（如果报表仍按记/收/付/转、系统类型分开展示）
   - `COALESCE(a.yhzhhm,'其他账号')`、`COALESCE(a.ywfl,'其他分类')`
   - `b.kmbh`（分录展开）
   - `SIGN(b.jffse), SIGN(b.dffse)` 是否保留：为“最小改动”可以先保留；若想让同科目只出一行，再讨论移除（属于口径变更）。
3. 方言函数：建议将 `NVL` 统一替换为 `COALESCE`，与“达梦/MySQL兼容”的宣称一致（且 MySQL 当前 mapper 里也大量使用 `IFNULL`，`COALESCE`更稳）。

### 3.2 Service：修复 `zdpzhz` 的二级分组（P0）
当前逻辑仍按 `ywlx` 二级分组并假设“同一 ywlx 内 yhzhhm/ywfl 一致”，这是错误前提。

**改造建议：**
1. 将 `ywlxs` 改为分组键集合：`(yhzhhm, ywfl)`，例如 key=`yhzhhm + '|' + ywfl`。
2. 每个二级分组中：
   - `hzYhzhhm/hzYwfl` 直接取分组 key（而不是取第一条明细）。
   - `hzjffse/hzdffse` 仍按分组内汇总。
   - `ywlx` 仅作为兼容字段：可选 `minYwlx`（分组内最小 ywlx）或固定为空（前提是 DB 允许为空）。
3. 摘要生成：
   - 当前 `mapYwflName(xtlx, ywlx)` 依赖 ywlx 查字典得到 `codeNameZl1`，如果一个分组内存在多个 `ywlx`，应先校验这些 `ywlx` 的 `codeZl1` 是否一致；不一致则按严格模式抛错或记录 `WARN` 并统一摘要为 “业务分类：{ywfl}”。（此处属于“防脏数据”关键点）

### 3.3 回写：修复 `pzhzJzbjXg` 更新条件（P0）
当前更新条件仍包含 `eq ywlx`，会把不属于该汇总分组的数据更新到同一汇总凭证号。

**改造建议：**
1. 从更新条件移除 `eq ywlx`。
2. 增加维度条件：
   - `eq(PzDO::getYhzhhm, 当前汇总的 yhzhhm)`
   - `eq(PzDO::getYwfl, 当前汇总的 ywfl)`
3. `jzrq/ztbh/zzbj/jzlxfl/jzbj` 继续保留，确保更新范围严格锁定在当日、当账套、当批次、当记账类型分类的“未汇总记账凭证”集合。

### 3.4 附件数：新增“按维度”统计接口（P1→P0防串数据）
当前 `getDjdjsHj` 仍按 `ywlx` 统计附件数，不再适配新口径。

**改造建议：**
- 增加 mapper 方法：`getDjdjsHjByDim(PzhzReqDTO)`（或新增内部 DTO），SQL 按 `ztbh/jzrq/zzbj/jzlxfl/yhzhhm/ywfl` 汇总 `SUM(a.fjdjs)`。
- 同时扩展 [PzhzReqDTO.java](file:///home/source/Jetbrains/Probject/Gjj/zaozhuang/IdeaProjects/capinfo-gjj-busi-jshs/capinfo-gjj-busi-cwhs-jzgl/capinfo-gjj-busi-cwhs-jzgl-basic-svc-api/src/main/java/cn/capinfo/gjj/busi/cwhs/jzgl/api/dto/req/PzhzReqDTO.java) 增加 `yhzhhm/ywfl`（如果不想影响 API，则仅用于内部查询对象）。

### 3.5 配置：补齐 `application.yml` 的真实落点（P1）
代码已 `@Value("${voucher.*:default}")`，但当前 [application.yml](file:///home/source/Jetbrains/Probject/Gjj/zaozhuang/IdeaProjects/capinfo-gjj-busi-jshs/capinfo-gjj-busi-cwhs-jzgl/capinfo-gjj-busi-cwhs-jzgl-basic-svc-app/src/main/resources/application.yml) 未配置。

**建议配置片段：**
```yaml
voucher:
  summary:
    byYwfl: true
  mapping:
    strictMode: false
    fallback:
      enable: true
```
> 具体落点以你们真实部署方式为准：若生产以 Nacos 为准，则该片段应进入 Nacos 配置，而不是打进包内 application.yml。

## 4. 最小回归用例（用于验证 P0 已修复）
1. **同 ywlx，不同 yhzhhm**：同日同账套，2 个中心账号各 1 笔凭证，汇总应产生 **2** 张汇总凭证；且两组明细凭证的 `hzpzh` 不可相同。
2. **不同 ywlx，同 ywfl**：构造两个 ywlx 映射到同一 `codeZl1`（即同 ywfl），同一中心账号下汇总应产生 **1** 张汇总凭证（按 ywfl 合并）。
3. **串号防线**：汇总后抽样检查 `cwhs_pz` 中同一 `hzpzh` 对应的记录，其 `yhzhhm/ywfl` 必须一致（否则就是串号）。
