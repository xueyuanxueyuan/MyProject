# 结算服务调用一户通批量业务参数透传缺口分析

## 1. 结论先行

当前问题不在一户通批量接口本身，也不在 `YhtController` 的外部 API 转内部 DTO 转换层。

真正有缺口的是：

1. 结算业务入口 `YwglServiceImpl`
2. 路由到 `YhtYwServiceImpl.addFkywPlfkjy(...) / addSkywPlskjy(...)`
3. 在这里组装内部 `cn...busi.yht.dto.YhtBatchTradeReqDTO` 时，参数透传严重不完整

结果是：

1. **批量付款链路**：几乎没有把明细列表传进去，属于结构性缺失；
2. **批量收款链路**：虽然传了部分明细，但关键字段缺失，属于半截透传；
3. 这些缺失字段中，有些会直接导致校验失败，有些会让发给一户通的 `caps.101` 文件内容不完整或语义失真。

## 2. 参考口径：一户通批量请求理论上需要哪些字段

从测试文档和 API DTO 可以确认，批量请求应至少具备：

### 2.1 批次级字段

1. `jbjgbh`
2. `yhdm`
3. `bizType`
4. `batchNo`
5. `feeNo`
6. `corpAcctNo`
7. `fileName`
8. `details`

### 2.2 明细级字段

1. `serialNum`
2. `detailSeq`
3. `dbtrActId`
4. `dbtrActName`
5. `cdtrActId`
6. `cdtrName`
7. `amount`
8. `bankId`
9. `bankType`
10. `protocolNo`
11. `phone`
12. `use`
13. `remark`

## 3. 外部直调接口层没有问题

`YhtController.submitBatchTrade(...)` 对外 API DTO 到内部 DTO 的映射是完整的：

1. 批次级字段会传：
   - `jbjgbh`
   - `yhdm`
   - `bizType`
   - `batchNo`
   - `feeNo`
   - `corpAcctNo`
   - `fileName`
2. 明细级字段也会传：
   - `serialNum/detailSeq`
   - `dbtrActId/dbtrActName`
   - `cdtrActId/cdtrName`
   - `amount`
   - `bankId/bankType`
   - `protocolNo/phone/use/remark`

所以：

**如果是直接调用 `/yht/batch/submit`，透传链路本身是完整的。**

## 4. 真正的问题点：`YhtYwServiceImpl`

## 4.1 批量付款 `addFkywPlfkjy(...)`

当前代码只传了：

1. `batchNo`
2. `bizType = PAY`
3. `corpAcctNo`
4. `jbjgbh`
5. `yhdm`

### 4.1.1 完全没传的批次级字段

1. `feeNo`
2. `fileName`

### 4.1.2 完全没传的核心明细

最严重的是：

1. `details` 整个列表都没有设置

这意味着付款批量链路不是“少传几个字段”，而是：

**根本没有把付款明细透传到一户通内部请求对象。**

### 4.1.3 后果

根据 `YhtBatchTradeRequestValidator`：

1. `details == null || details.isEmpty()` 会直接抛：
   - `批量明细不能为空`

所以当前批量付款链路在逻辑上就是不完整的。

## 4.2 批量收款 `addSkywPlskjy(...)`

当前批量收款比付款多做了一层：

1. 先按 `fkyhdm` 分组
2. 组装子批次
3. 传了部分 `details`

但透传依然不完整。

### 4.2.1 当前已传的字段

批次级：

1. `batchNo`
2. `bizType = COLLECT`
3. `corpAcctNo`
4. `jbjgbh`
5. `yhdm`

明细级：

1. `serialNum = mxlsh`
2. `dbtrActId = fkzh`
3. `dbtrActName = fkhm`
4. `cdtrActId = skyw.yhzhhm`
5. `cdtrName = skyw.yhzhmc`
6. `amount = mx.je`
7. `bankType = bankCode`

### 4.2.2 明显缺失的批次级字段

1. `feeNo`
2. `fileName`

### 4.2.3 明显缺失的明细级字段

1. `bankId`
2. `protocolNo`
3. `phone`
4. `use`
5. `remark`
6. `detailSeq` 也没有显式透传

### 4.2.4 其中哪些字段本地其实拿得到

从 `Skyw / SkywPlmx` 可以明确拿到：

1. `bankId`：应优先来自 `SkywPlmx.fkyhlhh`，必要时再按 `fkyhdm` 兜底
2. `protocolNo`：可来自 `SkywPlmx.dfxyh`
3. `use/remark`：可来自 `SkywPlmx.zhaiyao / beizhu`
4. `detailSeq`：可用循环序号或当前分组内序号生成

也就是说，这些字段并不是“本地没数据”，而是：

**代码当前没有继续往一户通 DTO 透传。**

### 4.2.5 哪些字段本地不一定拿得到

1. `phone`

目前 `SkywPlmx` 实体里没有手机号字段，所以这个字段是否能传，要看是否需要继续从别的业务表补查。

### 4.2.6 后果

根据 `YhtBatchTradeRequestValidator`：

1. `bankId` 不能为空
2. `bankType` 不能为空
3. 代收场景下 `dbtrActId/dbtrActName` 不能为空

所以当前收款链路虽然传了部分明细，但由于没传 `bankId`，会直接卡在校验层。

## 5. 报文构建器最终会用到哪些字段

`YhtBatchTradeMessageBuilder.buildCaps101(...)` 最终会把这些字段写入 `caps.101`：

### 5.1 批次头信息

1. `tranCode`
2. `corpNo`
3. `feeNo`
4. `totalCount`
5. `totalAmt`
6. `yhdm`
7. `corpAcctNo`

### 5.2 代付明细

1. `detailSeq`
2. `bankId`
3. `bankType`
4. `cdtrActId`
5. `cdtrName`
6. `amount`
7. `phone`
8. `serialNum`
9. `remark`

### 5.3 代收明细

1. `detailSeq`
2. `bankId`
3. `bankType`
4. `dbtrActId`
5. `dbtrActName`
6. `amount`
7. `protocolNo`
8. `phone`
9. `serialNum`
10. `remark`

所以当前透传缺口不只是 DTO 看起来不完整，而是：

**最终发给一户通的文件内容本身就会缺字段。**

## 6. 根因归纳

本次根因可以归纳成两类：

### 6.1 付款链路：根本没做明细透传

`addFkywPlfkjy(...)` 只传了批次头，没把 `List<FkywPlmx>` 转成一户通明细。

这是主缺口。

### 6.2 收款链路：只做了最低限度的账户透传，没把业务字段继续带下去

`addSkywPlskjy(...)` 只传了：

1. 付款账号
2. 付款户名
3. 收款账号
4. 收款户名
5. 金额
6. 分组银行代码

但像：

1. 联行号
2. 协议号
3. 摘要/备注
4. 文件名
5. 费项代码

都没有继续透传。

## 7. 一句话判断

如果说“通过结算服务调用一户通批量业务时参数透传有问题”，这个判断是成立的，而且问题不轻：

1. **批量付款**：属于“明细整体没透传”；
2. **批量收款**：属于“关键字段漏传，导致校验和报文内容都不完整”；
3. **直接一户通 API**：透传本身没问题，缺口集中在 `YhtYwServiceImpl` 的业务适配层。

## 8. 修复方向

建议按以下优先级修：

### 8.1 先补批量付款

把 `List<FkywPlmx>` 完整映射到 `YhtBatchTradeReqDTO.details`：

1. `serialNum = mxlsh`
2. `detailSeq = 顺序号`
3. `cdtrActId = skzh`
4. `cdtrName = skhm`
5. `amount = je`
6. `bankId = skyhlhh`
7. `bankType = skyhdm`
8. `remark = beizhu`
9. 其他可选字段按业务口径继续补

同时补：

1. `feeNo`
2. `fileName`

### 8.2 再补批量收款

补齐：

1. `feeNo`
2. `fileName`
3. `bankId = fkyhlhh`
4. `protocolNo = dfxyh`
5. `remark = beizhu`
6. `use = zhaiyao`
7. `detailSeq`

### 8.3 最后决定手机号来源

若一户通联调必须要求 `phone`，需继续查：

1. 是否在本地其他业务表可取
2. 是否允许为空
3. 是否需要调用签约/协议表补查
