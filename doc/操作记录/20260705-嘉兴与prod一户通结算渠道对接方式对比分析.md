# 20260705-嘉兴与prod一户通结算渠道对接方式对比分析

## 1. 目标
- 分析 `prod` 与 `jiaxing` 项目当前“一户通结算渠道”的对接方式。
- 明确业务链路中“何处判定 `jsqd=0103` 并切到一户通发送”。
- 对比 `prod` 基线与 `jiaxing` 区域实现差异，判断差异是否落在一户通适配链本身。

## 2. 结论摘要
- `prod` 与 `jiaxing` 当前的一户通对接方式一致，均采用“业务层按 `jsqd` 选渠道 + 一户通适配层统一封装发送”的实现方案。
- 业务层并不是在某一个固定入口直接硬编码 `jsqd=0103`，而是优先保留请求已传入的 `jsqd`，若为空则从账户信息或 `YwlxSfyhdz` 收付银行对照中补齐，再在 `YwglServiceImpl` 中按 `Jsqd.YHT.code` 分流。
- 一旦命中 `jsqd=0103`，单笔付款、单笔收款、批量付款、批量收款都会直接切到 `YhtYwServiceImpl`，不再走住建部/银企直联的原交易初始化链路。
- 一户通内部参数并非由外部业务层逐项传入，而是由 `YhtSceneParamResolver` 统一补齐 `tranCode`、`bizType`、`feeNo`、`dsjgbm` 等场景参数，再由 `YhtServiceImpl` 调度具体 orchestrator 发送。
- 本次检索到的核心一户通实现文件在 `prod` 与 `jiaxing` 之间哈希一致，说明区域差异不在 YHT 核心适配链。

## 3. 当前对接方式

### 3.1 总体架构
当前实现可概括为四层：
1. 业务建单层：`YwglServiceImpl`
2. 通道分流层：仍在 `YwglServiceImpl`，按 `jsqd` 判断是否走一户通
3. 一户通业务适配层：`YhtYwServiceImpl`
4. 一户通统一服务层：`YhtServiceImpl`

对应关系如下：
- `YwglServiceImpl` 负责生成/补齐业务对象上的 `jsqd`
- `YwglServiceImpl` 负责识别 `Jsqd.YHT.code`
- `YhtYwServiceImpl` 负责把 `Fkyw`/`Skyw`/批量明细组装成一户通内部 DTO
- `YhtSceneParamResolver` 负责补齐通道内部参数
- `YhtServiceImpl` 负责签名、验签、报文发送、状态查询、补查、回调承接

### 3.2 配置方式
一户通运行配置统一放在 `application.yml` 的 `yht.caps.*` 下，至少包括：
- `base-url`
- `corp-no`
- `user-name`
- `password`
- `receiver-id`
- `switch-config`
- `retry`

这部分在 `prod` 与 `jiaxing` 的 YHT 配置块一致，说明当前区域项目未对一户通基础接入配置做额外分叉。

## 4. 业务层如何判定并切到一户通

### 4.1 `jsqd` 的来源
当前链路里，业务层先准备业务对象，再补齐 `jsqd`：
- 若请求 DTO 已带 `jsqd`，后续不会被覆盖。
- 若业务对象上的 `jsqd` 为空，则通过 `applyResolvedJsqd(...)` 从以下来源补齐：
  - 专户账户信息 `yhzhxx.getData().getJsqd()`
  - 收付银行对照 `sfyhdzRespDTOList.get(0).getJsqd()`

`applyResolvedJsqd(...)` 的实现逻辑很关键：
- 仅当当前业务对象 `jsqd` 为空且解析到的 `resolvedJsqd` 非空时才赋值。
- 因此它体现的是“外部传入优先，系统解析兜底”的策略。

### 4.2 `jsqd=0103` 的分流点
真正切到一户通发送的节点在 `YwglServiceImpl` 中，而不是在 Controller 或审批订阅处理器中。

当前已确认的分流点包括：
- `addFkywDbfkjy(Fkyw fkyw)`：单笔付款
- `addSkywDbskjy(Skyw skyw)`：单笔收款
- `addFkywPlfkjy(Fkyw fkyw, List<FkywPlmx> list)`：批量付款
- `addSkywPlskjy(Skyw skyw, List<SkywPlmx> list)`：批量收款

这些方法都包含同样的分支模式：
- 若 `Jsqd.YHT.code.equals(...getJsqd())`
  - 记录“走一户通通道”日志
  - 调用 `yhtYwService.*`
  - `return`
- 否则继续走原有住建部/银企直联交易初始化逻辑

这意味着：
- `审批 -> 建单` 与原结算流程仍在同一业务入口完成
- `选渠道` 的最后一跳在 `YwglServiceImpl`
- `发送` 的一户通实现由 `YhtYwServiceImpl` 接管

## 5. 当前实现方案

### 5.1 单笔付款
链路为：
1. 审批/业务入口调用 `YwglServiceImpl`
2. 业务对象 `Fkyw` 补齐账户、银行、`jsqd`
3. `addFkywDbfkjy(Fkyw fkyw)` 判断 `jsqd`
4. 若 `jsqd=0103`，调用 `yhtYwService.addFkywDbfkjy(fkyw)`
5. `YhtYwServiceImpl` 组装 `YhtRealtimeTradeReqDTO`
6. `YhtSceneParamResolver.resolveRealtimePayTrade(...)` 补齐通道参数
7. `YhtServiceImpl.submitRealtimeTrade(...)` 发起一户通实时交易

### 5.2 单笔收款
链路与单笔付款对称：
1. `YwglServiceImpl` 建单并补齐 `jsqd`
2. `addSkywDbskjy(Skyw skyw)` 判断 `jsqd`
3. 命中 `0103` 后调用 `yhtYwService.addSkywDbskjy(skyw)`
4. `YhtSceneParamResolver.resolveRealtimeCollectTrade(...)`
5. `YhtServiceImpl.submitRealtimeTrade(...)`

### 5.3 批量付款 / 批量收款
批量链路同样是在 `YwglServiceImpl` 里按 `jsqd` 切换：
- `addFkywPlfkjy(...)` 命中 `0103` 后走 `yhtYwService.addFkywPlfkjy(...)`
- `addSkywPlskjy(...)` 命中 `0103` 后走 `yhtYwService.addSkywPlskjy(...)`

随后：
- `YhtYwServiceImpl` 组装 `YhtBatchTradeReqDTO`
- `YhtSceneParamResolver.resolveBatchTrade(...)` 补齐场景参数
- `YhtServiceImpl.submitBatchTrade(...)` 发送批量交易

批量一户通分支有一个显式设计点：
- 发送异常时记录错误日志，但保持结算接收事务继续，由后续补偿/补查处理。

### 5.4 回执、补查与回调
`YhtServiceImpl` 除了发起交易，还承接以下能力：
- `submitRealtimeTrade(...)`
- `submitBatchTrade(...)`
- `queryRealtimeTradeStatus(...)`
- `receiveCallback(String rawBody)`

从实现上看：
- 回调进入 `receiveCallback(...)`
- 若回调处理结果要求确认通信标识号，则调用 `registerMesgIdConfirmation(...)`
- 补查/重试等能力则由 `retry` 配置与相关 orchestrator 支撑

因此一户通链路已经覆盖：
- 发送
- 状态查询
- 回调处理
- 回调确认
- 补查/补偿

## 6. prod 与 jiaxing 的对比结论

### 6.1 核心 YHT 适配链一致
本次对以下核心文件做了哈希对比，`prod` 与 `jiaxing` 完全一致：
- `YhtSceneParamResolver.java`
- `YhtServiceImpl.java`
- `YhtYwServiceImpl.java`

说明以下内容在两边没有实现差异：
- 一户通内部参数解析
- 实时/批量交易发送
- 回调接收与确认
- 一户通业务对象转内部请求 DTO 的方式

### 6.2 业务层 YHT 路由模式一致
虽然 `YwglServiceImpl` 全文件在两个项目中并不完全相同，但一户通相关路由模式一致：
- 都有 `applyResolvedJsqd(...)`
- 都有从账户信息或 `YwlxSfyhdz` 回填 `jsqd`
- 都在单笔/批量收付款方法里按 `Jsqd.YHT.code` 分流到 `yhtYwService`

结论是：
- `jiaxing` 没有自定义另一套一户通路由机制
- 区域项目仍沿用 `prod` 基线的一户通通道切换方案

### 6.3 已看到的区域差异
当前已确认的差异主要有两类：

1. 非一户通核心业务文件体量差异
- `jiaxing` 的 `YwglServiceImpl` 因区域业务扩展，行号和周边逻辑与 `prod` 不同。
- 但一户通分流点本身仍保持同样实现模式。

2. DTO 契约差异
- `jiaxing` 的 `ZjjsSFkywxxAddReqDTO` 增加了 `hsjgbh` 字段。
- 该 DTO 对 `jsqd` 的文案说明更明确指出 `0103-一户通`。

这类差异说明：
- `jiaxing` 在外围业务契约上有区域化扩展
- 但没有改写一户通核心对接方案

## 7. 对当前方案的理解
- 当前方案不是“业务层直接拼一户通报文”，而是“业务层只决定走哪条结算渠道，一户通参数和报文细节由专门适配层处理”。
- 这套方案的优点是：
  - 业务层只关心 `jsqd`
  - 通道参数集中在 `YhtSceneParamResolver`
  - 发送、回调、补查都沉到 `YhtServiceImpl`
  - `prod` 与区域项目可以共享大部分 YHT 核心代码

同时也有一个现实特点：
- `jsqd` 的最终来源较分散，既可能来自请求，也可能来自账户信息或收付银行对照。
- 因此若后续排查“为什么走了一户通/为什么没走一户通”，首要检查点不是发送层，而是建单阶段 `jsqd` 的来源与回填。

## 8. 建议的排查顺序
后续若继续查某一笔业务是否走一户通，建议按以下顺序定位：
1. 看入口 DTO/业务对象上是否已经带 `jsqd`
2. 看 `applyResolvedJsqd(...)` 是否从账户信息或 `YwlxSfyhdz` 补齐为 `0103`
3. 看 `YwglServiceImpl` 是否命中 `Jsqd.YHT.code`
4. 看是否调用到了 `YhtYwServiceImpl`
5. 看 `YhtServiceImpl` 的发送、回调、补查日志
