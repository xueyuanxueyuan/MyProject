# 一户通回执终态语义与主动查询风险核对

## 1. 核对目的

针对当前联调中的核心担忧，核对下面三个问题：

1. 是否把 `caps.202/caps.102` 这类“申请应答/处理中”报文当成最终交易结果；
2. 是否真正存在主动查询与结果提回能力；
3. 当前哪些链路会推进结算主业务，哪些链路只更新一户通任务台账。

## 2. 规范语义结论

基于《上海集中代收付系统报文交换规范 V1.2.7.7》确认：

### 2.1 实时交易

1. `caps.202` 是实时业务应答，规范明确属于“处理中”阶段，不是最终交易结果；
2. `caps.205` 是实时业务处理结果回执，收到后同步回 `caps.900`，之后再进行行内业务处理；
3. `caps.204` 是实时业务查询应答：
   - `RetCode=111111`：处理中
   - `RetCode=000000`：成功
   - `RetCode=000001`：失败

### 2.2 批量交易

1. `caps.102` 是批量业务应答，规范明确属于“处理中”阶段，不是最终交易结果；
2. `caps.107` 是批量业务处理结果回执，收到后同步回 `caps.900`，之后进行行内业务处理；
3. `caps.104` 是批量状态查询应答，核心是批次状态；
4. `caps.106` 是批量业务结果提回应答，规范明确是批量业务包终态结果文件，解析 `FileData` 后更新本地相关业务信息。

## 3. 当前实现核对结论

## 3.1 实时交易

### 3.1.1 没有把 `caps.202` 当最终结果处理

当前代码中，实时主业务处理入口在 `YhtRealtimeCallbackProcessor`：

1. 只有 `caps.205` 回调进入 `handle(...)` 后，才会尝试调用：
   - `fkywJfJgCl(...)`
   - `skywJfJgCl(...)`
2. 没有看到 `caps.202 -> 主业务处理` 的直接联动。

因此，**目前没有证据表明系统把实时申请应答 `caps.202` 直接当成最终交易结果来处理业务数据。**

### 3.1.2 `111111` 没有被误判成终态

`YhtRealtimeReceiptProcessor.fromRetCode(...)` 的映射规则是：

1. `000000 -> SUCCESS`
2. `111111 -> PROCESSING`
3. 其他 -> FAIL

并且 `YhtRealtimeCallbackProcessor` 中：

1. 单笔付款只有 `SUCCESS/FAIL` 才会触发 `fkywJfJgCl(...)`
2. 单笔收款只有 `SUCCESS` 才会触发 `skywJfJgCl(...)`

因此，**实时链路没有把“处理中”回执当作终态推进业务。**

### 3.1.3 主动查询能力是存在的，但更像补偿链路

当前代码中，实时主动查询能力明确存在：

1. 对外接口：`/yht/realtime/status`
2. 服务入口：`yhtService.queryRealtimeTradeStatus(...)`
3. 编排器：`YhtRealtimeStatusQueryOrchestrator`
4. 定时任务：`YhtRealtimeStatusQueryJobHandler`

其中 `YhtRealtimeStatusQueryJobHandler` 会对未终态任务自动发起 `caps.203` 查询。

但是当前还要注意一个关键事实：

1. `caps.204` 查询应答会调用 `realtimeReceiptProcessor.applyReceipt(...)` 更新 `YhtProtocolTaskDO.bizStatus`；
2. **没有看到 `caps.204` 查询终态后继续调用 `fkywJfJgCl(...) / skywJfJgCl(...)`。**

这意味着实时链路当前更像：

1. `caps.205` 回执路径：会推进主业务；
2. `caps.204` 查询路径：目前只收敛任务状态。

所以实时当前的主要风险不是“把申请应答当终态”，而是：

**如果现场没有收到 `caps.205`，即使补查 `caps.204` 已经拿到终态，也可能只更新一户通任务状态，没有继续推进结算主业务。**

## 3.2 批量交易

### 3.2.1 没有把 `caps.102` 当最终结果处理

当前代码中，批量发起后：

1. `caps.102` 只属于提交后的同步受理阶段；
2. 批量终态处理主要落在：
   - `caps.107` 回执处理
   - `caps.103/104` 状态补查
   - `caps.105/106` 结果提回

因此，**目前没有证据表明系统把批量申请应答 `caps.102` 直接当成最终交易结果处理业务数据。**

### 3.2.2 主动查询与结果提回能力都存在

批量这条线当前代码已经具备：

1. `queryBatchByCaps103(...)`：主动发 `caps.103` 查批次状态；
2. `fetchBatchResultByCaps105(...)`：主动发 `caps.105` 提回结果文件；
3. `YhtBatchStatusQueryJobHandler`：自动补查批次状态；
4. `YhtBatchResultFetchJobHandler`：对已完成批次自动发起结果提回。

因此，**批量并不是没有主动查询能力，而是这些能力主要被设计为补偿/后台作业链路。**

### 3.2.3 批量目前的真实断点在“只收敛 YHT 台账”

当前批量处理路径已经明确做到：

1. `caps.107` 进入 `YhtBatchCallbackProcessor`；
2. 更新 `YhtProtocolTaskDO` 与 `YhtBatchTaskDO`；
3. 如果有 `FileData`，交给 `YhtBatchResultFileProcessor.parseAndUpdateDetails(...)`；
4. 逐条更新 `YhtBatchDetailDO.bizStatus/retCode/retMsg`；
5. `refreshAggregate(...)` 重新汇总批次成功/失败/处理中数量。

但当前未看到：

1. `YhtBatchCallbackProcessor` 调用 `YwglService`；
2. `YhtBatchStatusOrchestrator.fetchResultByCaps(...)` 调用 `YwglService`；
3. `YhtBatchResultFileProcessor` 反写 `ZjPlfkmx/ZjPlskmx/Fkyw/Skyw/YwJg`。

因此，批量当前最明显的结构性断点是：

**`caps.107/106` 已经能把结果收敛到一户通任务表、批次表、明细表，但还没有看到稳定的“批量终态 -> 结算主业务”联动闭环。**

## 4. 风险判断

## 4.1 实时交易

### 当前结论

1. 不存在明确证据表明把 `caps.202` 当最终结果处理；
2. 不存在把 `111111` 当成功/失败终态推进业务的问题；
3. `caps.205` 被当作终态来源使用，和规范口径一致。

### 当前风险

1. 现场如果依赖的是查询兜底而不是推送回执；
2. 当前 `caps.204` 查询终态只更新任务状态，不推进主业务；
3. 则会出现“查询已成功，但业务数据未处理”的另一类不一致。

## 4.2 批量交易

### 当前结论

1. 不存在明确证据表明把 `caps.102` 当最终结果处理；
2. 主动查询 `caps.103/104` 和结果提回 `caps.105/106` 都存在；
3. `caps.107` 也被当作终态回执使用，和规范大方向并不冲突。

### 当前风险

1. 批量后半段主要停留在 `YhtProtocolTaskDO/YhtBatchTaskDO/YhtBatchDetailDO`；
2. 没看到结果文件向本地批量明细和主业务表的稳定反写；
3. 所以批量当前最大的风险不是“把申请应答当终态”，而是：
   - **终态已经拿到了，但只停在 YHT 台账，没有推进结算业务。**

## 5. 建议优先级

### 5.1 第一优先级：补齐实时查询终态到主业务的联动

建议目标：

1. `caps.205` 与 `caps.204` 在拿到终态后，都落到同一套业务处理入口；
2. 保证“推送成功”和“查询成功”不会出现不同步的业务结果。

建议原则：

1. `000000` 才走成功处理；
2. `000001` 才走失败处理；
3. `111111` 只更新为处理中，不推进主业务。

### 5.2 第二优先级：补齐批量 `106/107` 到本地主业务的闭环

建议目标：

1. 保留 `caps.107` 的快速收敛能力；
2. 以 `caps.106` 结果文件作为批量明细终态的重要依据；
3. 把 `YhtBatchDetailDO` 结果映射回本地批量明细；
4. 再由本地批量明细汇总推进 `Fkyw/Skyw/YwJg`。

### 5.3 第三优先级：统一“终态定义”和“业务推进入口”

建议后续整理为统一规则：

1. 申请应答只表示受理，不推进业务；
2. 查询应答只有明确终态码才推进业务；
3. 推送回执只有明确终态码才推进业务；
4. 批量结果文件是批量明细反写主业务的最终依据之一。

## 6. 一句话结论

你现在的担心方向是对的，但结合当前代码再精确一点，结论应该是：

1. **实时**：当前看不像是把“申请应答”误当成最终结果，更像是“推送回执能推进业务，但查询终态暂时没有推进主业务”；  
2. **批量**：当前看也不像是把“申请应答”误当成最终结果，更大的问题是“终态结果已经收到了，但主要只更新了一户通台账，没有继续反写结算主业务”。
