# 一户通新增业务需求可行性分析报告

## 1. 需求背景
目前的一户通功能主要集中在核心报文接口层面（底层协议对接）。针对实际业务场景（单位托收管理、资金结算、清单下载等）提出了更具体的业务交互及前端页面改造要求。

## 2. 需求拆解与系统现状排查

### 需求①：单位托收签约业务由人行CAPS系统主动推送至中心，并返回通用确认报文
* **需求逻辑**：CAPS系统主动向中心推送签约信息，中心进行业务校验，符合则入库，不符合则拒绝，但无论哪种情况都要先回 `caps.900` 确认报文，然后可能还需要业务级别的协议应答报文。
* **系统现状分析**：
  * **可行性：底层已具备，业务层需开发。**
  * 当前系统底层存在统一的回执接收端点 `YhtController.receive()` (映射路径为 `/yht/receive`)，该端点已经具备接收 CAPS 异步推送报文（如 `caps.306/107/205` 等）的能力。
  * 并且在 `YhtInboundCallbackFacade` 与 `YhtServiceImpl.receiveCallback` 中，底层已经完整封装了**接收报文后立刻自动生成并返回 caps.900 通用确认报文**的机制。
  * **缺失环节**：虽然底层通道能收能回，但目前代码中缺乏针对“被动接收单位托收签约”（推测可能是 `caps.302` 或特定签约推送报文）的**专属业务处理策略层**。系统内部对企业信息的校验（如核验单位名称、银行账号等逻辑）尚未与一户通底层进行挂接。这部分校验代码和写库逻辑需要全新开发。

### 需求②：发起批量代收申请，根据人数/银行筛选，“按银行分开发送”
* **需求逻辑**：前端在资金结算时触发批量代收（并具有按银行、人数的筛选框），后端按银行分组向 CAPS 发送申请，且有防重发机制。
* **系统现状分析**：
  * **可行性：底层发送通道畅通，防重发与分组业务需全量开发。**
  * 底层已经具备 `caps.101.001.01`（批量交易发起）的核心能力，支持代付(PAY)和代收(COLLECT)两种类型（详见 `YhtController.submitBatchTrade`）。
  * **缺失环节**：
    1. **前端页面缺失**：“单位托收管理”界面上的条件筛选框（缴存职工数量、托收银行）并未实现，属于前端增量开发。
    2. **分组逻辑缺失**：目前的批量发送是按照业务系统原有批次打包的。要实现“按银行分开发送”，必须在进入一户通发送组装前，在业务层（如 `YwglServiceImpl`）将原有的单大批次数据，按照 `FkywPlmx/SkywPlmx` 中的银行代码进行 groupBy 分拆，生成多个 CAPS 批次号分别调用。
    3. **防重发校验**：虽然一户通底层可能会校验 `reqId` 或批次号，但基于状态的业务级防重发（“收到处理结果前不允许重复发起”）需要在结算表层增加状态拦截锁。

### 需求③：清单下载->单位托收 批量状态查询 (caps.103/caps.104)
* **需求逻辑**：点击查询，调用 `caps.103` 查询状态，接收 `caps.104` 结果，并更新至界面的清册列“结果”中。
* **系统现状分析**：
  * **可行性：底层完全支持，需开发页面按钮的触发绑定。**
  * 在底层代码中，`Caps103Builder` 与 `YhtBatchStatusOrchestrator` 已经完整实现了 `caps.103.001.01` 的构建和发送，并能妥善解析 `caps.104.001.01` 应答状态（处理中/成功/失败）。
  * 并且在 `YhtController` 中已经暴露了 `/yht/batch/status` 端点供上层调用。
  * **缺失环节**：业务系统的“单位托收”查询按钮需要改写，不再只查本地数据库，而是要通过网关或直调触发一户通底层的状态同步接口，然后再将刷新后的数据库状态吐给前端展示。

### 需求④：清单下载->成功批次的数据下载与明细查询 (caps.105/caps.106)
* **需求逻辑**：点击“数据下载”调用 `caps.105` 提回报文，接收 `caps.106` 获取明细结果文件，并在界面做明细展示。
* **系统现状分析**：
  * **可行性：底层已完全打通数据流，业务查询接口需封装。**
  * 经查 `Caps105Builder`、`YhtBatchStatusOrchestrator.fetchResultFile` 及定时任务 `YhtBatchResultFetchJobHandler` 中，已经实现了 `caps.105.001.01` 的请求封装。
  * 并且 `Caps106Message` 模型以及相关的明细解析入库逻辑已经存在（CAPS 提回的数据会被落入批量明细表或特定文件系统中）。
  * **缺失环节**：前端缺少“数据下载”和“明细查询”两个具体按钮的实现。后端需要提供将 `caps.106` 落库后的明细数据分页查出并返回给前端展示的 Controller 接口。

## 3. 结论建议
总体而言，**目前的系统架构在底层接口通道上（CAPS协议层）已经 100% 具备实现该业务逻辑的能力**（涉及的 `caps.900/101/103/104/105/106` 报文全部存在并支持解析与构建）。

但由于我们此前做的是“纯底层接口的集成与映射”，**业务应用层与前端展示层属于尚未开发的空白区**。

如需实现上述完整闭环，需要进入**业务研发阶段**，主要工作量集中在：
1. **被动回调业务校验**：新增 CAPS 推送签约请求的单位信息合法性核验逻辑。
2. **集合拆分逻辑**：在发起代收时，编写根据银行分组切割批次的算法。
3. **前端页面改造**：增加所需的筛选框、触发按钮及明细展示弹窗。
