# 20260512-一户通接口逻辑审查与yqzl式业务对接方案

## 1. 背景

本次审查对象为：

- 一户通模块：`prod/IdeaProjects/capinfo-gjj-busi-jshs/capinfo-gjj-busi-zjjs-ywgl/.../busi/yht`
- 现有业务总入口：`.../busi/service/impl/YwglServiceImpl.java`
- 现有企业钱包入口：`.../busi/service/impl/WbjkServiceImpl.java`
- 参考集成实现：`.../busi/yqzl/service/impl/YqzlYwServiceImpl.java`

用户诉求分为两部分：

1. 分析 `yht` 当前接口实现本身是否存在逻辑问题。
2. 结合 `yqzl` 现有接入方式，分析 `yht` 如何接入当前业务链路。

## 2. 现状结论

### 2.1 `yht` 不是“只写了接口壳子”

源码显示，`yht` 已经具备较完整的通道内能力，不只是 `controller + dto`：

- 有控制器：`YhtController`
- 有业务门面：`YhtService` / `YhtServiceImpl`
- 有协议、实时、批量编排器：`YhtProtocolRequestOrchestrator`、`YhtRealtimeTradeSubmitOrchestrator`、`YhtBatchTradeSubmitOrchestrator`
- 有回调总入口和分发器：`YhtInboundCallbackFacade`
- 有协议/实时/批量回执处理器
- 有重试与人工介入能力：`YhtRetryServiceImpl`、`YhtManualInterventionServiceImpl`
- 有任务表、明细表、对账表相关持久化逻辑

结论：`yht` 的问题不在“没实现”，而在“模块内部实现较完整，但还没有接到现有业务主链路”。

### 2.2 当前真正未接通的位置

当前系统外部业务入口仍然主要走旧链路：

1. `YwglController.corpWalletSign()` 仍调用 `wbjkService.corpWalletSign(...)`
2. `YwglController.corpWalletCancel()` 仍调用 `wbjkService.corpWalletCancel(...)`
3. `YwglV2Controller` 同样仍走 `wbjkService`
4. `YwglServiceImpl` 在付款通道分流里只识别 `ZJBJSPT`、`YQZL`，没有 `YHT`
5. `YwglServiceImpl.khzhyxxCx()` 中还明确留有 `// TODO: 一户通渠道查询`
6. `YwglServiceImpl.yhzhHqyeCx()` 也只支持 `ZJBJSPT`、`YQZL`

结论：目前 `yht` 更像“已经可独立访问的通道模块”，但还不是“现有业务流程中的正式结算通道”。

## 3. `yht` 接口逻辑审查结论

## 3.1 总体评价

总体上，`yht` 的主链路设计是成立的，尤其以下方面做得不错：

- 有明确的服务分层与编排层，不是简单堆代码
- 有独立状态机与任务快照
- 有业务键、申请号、MesgId 三层幂等治理
- 回调确认采用 `afterCommit` 再确认 MesgId，思路正确
- 批量、实时、协议三类业务有各自编排器和边界服务
- 查询优先于盲目重发，重试治理方向合理

结论：**不是推倒重来型实现**，可以在此基础上做业务接入。

## 3.2 已确认的问题与风险

### 问题 1：费项映射仍是演示性质的静态硬编码，无法直接支撑真实业务

位置：`YhtFeeMappingServiceImpl`

当前实现把 `dsjgbm -> feeNoList` 写死在静态 Map 中，仅有少量示例值：

- `0001 -> FEE001,FEE002`
- `0002 -> FEE003,FEE004,FEE005`
- `0003 -> FEE006`

问题在于：

1. 真实业务的 `dsjgbm` 很可能不在此映射中。
2. 一旦未命中映射，签约会直接抛异常。
3. 这会导致 `yht` 即使接到业务入口，也无法稳定服务真实机构数据。

结论：这是 **必须先改造** 的接入前置项，建议改为读取业务配置表或基础档案表，而不是静态常量。

### 问题 2：协议查询控制层语义与服务层校验规则不一致

位置：

- `YhtController.queryProtocol()`
- `YhtProtocolRequestValidator.validateQuery()`
- `YhtProtocolRequestOrchestrator.enrichQueryRequest()`

控制层对外声明：

- 协议号 / 账号 / 申请号至少提供一个即可查询

但校验器要求：

- `protocolNo` 非空
- `acctNo` 非空
- `feeNo` 非空

虽然编排器会尝试通过历史任务补齐字段，并在 `feeNo` 为空时默认补 `00000`，但仍存在两个风险：

1. 如果外部仅传 `reqId`，但本地查不到历史任务，最终仍会因为协议号和账号为空而失败。
2. 控制层文档语义与真实执行条件不一致，容易让调用方误判接口能力。

结论：这是 **真实接口契约不一致问题**，需要统一“允许的查询维度”和“校验补齐策略”。

### 问题 3：`caps.306` 回调中 `RE00 -> ACCEPTED` 的处理偏保守，可能导致状态停留在中间态

位置：`YhtProtocolCallbackProcessor.resolveBizStatusByCallback()`

当前逻辑：

- 只要 `CtrctRtrFlg = RE00`，直接返回 `BizStatus.ACCEPTED`

风险点：

1. `RE00` 更像“收妥/已接收”语义，不一定代表最终业务状态。
2. 如果同时返回了可判断最终态的 `ProcessCode`，当前逻辑会提前短路，不再继续用状态机解析。
3. 结果可能导致任务长期停留在 `ACCEPTED`，而不是正确进入 `SUCCESS`、`SMS_PENDING`、`FAIL`、`CANCELLED` 等更精确状态。

结论：这是 **高优先级逻辑风险**。建议改为“优先按 `ProcessCode` 决定业务态；仅在无法识别 `ProcessCode` 时，才退化为 `RE00 -> ACCEPTED`”。

### 问题 4：控制层对签约默认写死 `AuthMd=AM00`，短信签约链路目前无法从旧业务请求自然触发

位置：`YhtController.sign()`

当前逻辑直接：

- `signReqDTO.setAuthMd("AM00")`

这意味着：

1. 旧请求 DTO 没有机会按业务传入 `AM02`
2. 即便 `YhtServiceImpl.submitSmsCode()` 已实现第二步短信确认，现有签约入口也默认不会走短信验证签约模式

结论：这不一定是 bug，但它会限制接入能力。若真实银行或场景需要短信验证，则需要在业务入口补充授权模式来源。

### 问题 5：实时交易接口响应字段存在“通用 DTO 复用”痕迹，虽不一定错误，但语义较绕

位置：

- `YhtRealtimeDispatchBoundaryServiceImpl.complete()`
- `YhtController.submitRealtimeTrade()`
- `YhtController.queryRealtimeTradeStatus()`

当前映射链路是：

- 服务层把 `task.getRemark()` 放到 `YhtRespDTO.processDesc`
- 实际这里的 `remark` 存的是企业流水号 `serialNum`
- 服务层把 `task.getProtocolNo()` 放到 `YhtRespDTO.protocolNo`
- 实际这里的 `protocolNo` 在实时链路中被复用成平台流水号 `sysSeqNo`
- 控制层再把 `processDesc -> serialNum`、`protocolNo -> sysSeqNo`

因此从结果上看，控制层最终响应字段可能还是对的，但中间对象语义是“借道复用”的：

1. `YhtRespDTO` 原本是协议域 DTO，被复用于实时域
2. `protocolNo` 在实时链路里并不真表示协议号
3. `processDesc` 在实时链路里也并不真表示处理描述

结论：这是 **中优先级设计风险**，短期可运行，但后续维护和排障很容易误读，建议后续将协议域 DTO 与实时域 DTO 彻底分离。

### 问题 6：查询前置校验与旧业务 DTO 的字段映射还没有完全业务化

位置：

- `YhtController.sign()`
- `YhtController.cancel()`
- `YhtProtocolRequestOrchestrator.enrichCancelRequest()`

审查结果显示：

1. 解约链路通过 `protocolNo` 反查原签约任务补充账户信息，这个方向是对的。
2. 但控制层只做了最基础的字段映射，没有把旧业务里的更多业务含义沉淀为稳定转换层。
3. 一些字段依赖“历史任务补齐”而不是“当前业务明确传入”，会让对接边界变得脆弱。

结论：这属于 **接入层未完成业务收口**，不是模块内实现错误，但如果直接切流量，排障复杂度会偏高。

## 3.3 不建议误判为问题的点

以下实现虽然看起来“复杂”或“和老系统风格不同”，但目前不建议直接判错：

- `YhtServiceImpl` 使用 `afterCommit` 再确认 MesgId
- 批量/实时/协议分别使用边界服务处理独立事务
- 查询前置补上下文、查询优先重试
- 业务键在失败和未知状态下采用不同释放策略

这些设计总体是合理的，说明编写者考虑了异步回调、重复请求、补查和事务边界。

## 4. 参考 `yqzl` 的对接方式分析

## 4.1 `yqzl` 的接入骨架是什么

`yqzl` 不是直接在控制器里把请求发给银行，而是走了“业务主链路接入”的模式：

### 第一步：业务主入口分流

`YwglServiceImpl` 根据 `Jsqd` 区分不同通道：

- `ZJBJSPT` 走住建部/原链路
- `YQZL` 走 `yqzlYwService`

### 第二步：业务对象落通道表

`YqzlYwServiceImpl.addFkywDbfkjy(Fkyw fkyw)` 会：

1. 把业务对象转换为银企直连交易对象 `ZjYqDbfk`
2. 保存交易表
3. 写入交易初始化表 `ZjYqJycsh`
4. 把主业务结算状态更新为“交易中”

### 第三步：统一发送出口

`YqzlMainEnterServiceImpl.call()` 根据 `exeCode` 从 Spring 容器里找到实际执行器，触发对银行发送。

### 第四步：后续依赖异步回执、补查、动账通知、对账处理

也就是说，`yqzl` 真正接入成功的关键不是“有接口”，而是：

1. 主业务表进入通道
2. 通道有自己的任务/初始化表
3. 通道结果能回写主业务状态
4. 补查、动账、对账都接入总业务框架

## 4.2 `yht` 应当参考的不是报文格式，而是接入方式

`yht` 与 `yqzl` 的通讯方式不同：

- `yqzl` 偏银行直连、初始化表 + 执行器派发
- `yht` 偏 CAPS 协议报文、HTTP 回调 + 本地任务快照

所以对接时不能机械照搬 `yqzl` 的“执行器类 + exeCode”结构，而应借鉴其 **业务接入方式**：

1. 在 `YwglServiceImpl` 加入通道分流
2. 在业务受理阶段把主业务转换为 `yht` 所需的请求参数
3. 把 `yht` 任务状态与主业务状态建立映射
4. 把回调、补查、对账纳入现有总业务处理框架

## 5. `yht` 与现有业务对接的推荐落点

## 5.1 第一层：先接入“企业钱包签约/解约”旧入口

这是最直接、风险最小的第一阶段。

### 现状

以下入口仍走旧链路：

- `YwglController.corpWalletSign() -> wbjkService.corpWalletSign()`
- `YwglController.corpWalletCancel() -> wbjkService.corpWalletCancel()`
- `YwglV2Controller` 同理

### 推荐做法

保留外部请求 DTO 不变：

- 继续使用 `CorpWalletSignReqDTO`
- 继续使用 `CorpWalletCancelReqDTO`

但内部改造成一层通道路由服务，例如：

- `CorpWalletChannelRouterService`
- 或在 `WbjkServiceImpl` 外再抽一层门面

路由规则建议：

1. 根据 `jsqd` 或银行/机构配置判断是否走 `YHT`
2. 走 `YHT` 时，调用 `yhtService.sign/cancel`
3. 不走 `YHT` 时，继续保留旧 `wbjkService` 逻辑

这样可以做到：

- 前端接口不变
- 旧调用方不需要改协议
- 支持逐步按通道切换

## 5.2 第二层：在 `YwglServiceImpl` 中补齐 `YHT` 分流

### 付款业务入口

参考 `Yqzl` 的做法，`YwglServiceImpl` 里凡是目前按 `Jsqd` 分流的地方，都要补 `YHT` 分支。

重点包括：

1. 付款业务发起
2. 付款结果补查
3. 账户变动通知后的对账处理
4. 银行账户有效性查询
5. 余额查询

至少当前已明确看到的缺口有：

- 付款分流只有 `ZJBJSPT` / `YQZL`
- `khzhyxxCx()` 里还留着 `// TODO: 一户通渠道查询`
- `yhzhHqyeCx()` 没有 `YHT`

### 推荐原则

不要只在控制器接 `YhtController`，而是要让 `YwglServiceImpl` 认识 `Jsqd.YHT`，否则：

- 主业务不会把 `YHT` 当正式通道
- 结果处理链无法闭环

## 5.3 第三层：新增 `YhtYwService` 作为“业务接入层”

参考 `YqzlYwServiceImpl`，建议新增一个专门的业务接入层，例如：

- `YhtYwService`
- `YhtYwServiceImpl`

职责不要等同于 `YhtService`。

### 建议职责边界

`YhtService`：

- 只负责一户通通道自身能力
- 报文构建、发送、回调、补查、状态机、任务表

`YhtYwService`：

- 负责把现有业务对象转换成 `yht` 请求
- 负责主业务状态与 `yht` 任务状态映射
- 负责把 `yht` 对账/补查/回执结果回写到业务主表
- 负责与 `YwglServiceImpl` 对接

### 原因

如果直接让 `YwglServiceImpl` 大量拼装 `YhtSignReqDTO`、`YhtRealtimeTradeReqDTO`，后续会出现：

- 通道细节污染总业务层
- 逻辑复用差
- 多处重复拼字段

## 5.4 第四层：建立“主业务表 <-> 一户通任务表”关联关系

`yqzl` 有自己的交易表、初始化表、结果处理链；`yht` 现在也有协议任务表、实时任务表、批量任务表。

但如果要真正接现有业务，还需要补充“业务关联键”设计。

建议至少保证以下关联关系可追踪：

1. 主业务 ID
2. `reqId`
3. `mesgId`
4. 协议号 / 平台流水号
5. 通道类型 `Jsqd`

### 推荐方式

可选方案 A：

- 在 `yht` 任务表中增加主业务 ID、业务类型字段

可选方案 B：

- 单独增加“业务与一户通任务关联表”

建议优先 A，改造成本更低，查询链更短。

## 5.5 第五层：把 `yht` 回调结果翻译成主业务状态

这是与 `yqzl` 集成最关键的一步。

当前 `yht` 内部已经能更新自己的任务状态，但还没有看到它回写现有主业务的完整链路。

必须新增一层“结果翻译器”，把：

- `BizStatus`
- `ProcessCode`
- `errorCode`
- `errorMsg`

翻译为你现有业务主表/结果表能识别的状态。

### 示例

协议域：

- `SUCCESS` / `CS00` -> 协议生效
- `SMS_PENDING` / `CS43` / `CS44` -> 待验证码确认
- `FAIL` / `CS41` -> 业务失败
- `CANCELLED` / `CS20` -> 协议已解约

实时交易域：

- `ACCEPTED` -> 已受理，待异步结果
- `SUCCESS` -> 交易成功
- `FAIL` -> 交易失败
- `UNKNOWN` -> 待补查或人工介入

如果不做这一步，`yht` 只能算“通道自己转起来了”，还不能算“业务真正接通了”。

## 5.6 第六层：把补查/重试纳入业务闭环

`yht` 已经有：

- `YhtRetryServiceImpl`
- `YhtRetryJobHandler`
- `YhtSupplementServiceImpl`

这说明通道内部已经考虑了“未知状态 -> 查询 -> 重试/人工”的治理。

对接业务时，建议不要另起炉灶重做一套轮询，而是：

1. 复用 `yht` 现有补查能力
2. 在补查完成后增加主业务回写
3. 在人工介入场景下增加业务侧状态提示

## 6. 推荐的分阶段改造方案

## 阶段一：先把签约/解约入口切成“可配置路由”

目标：

- 不改前端协议
- 不一次性替换旧链路
- 支持按渠道逐步切换到 `yht`

建议步骤：

1. 抽出签约/解约路由门面
2. 按 `jsqd` 或机构配置判断走 `YHT` 还是旧 `WbjkServiceImpl`
3. 打通 `CorpWalletSignReqDTO -> YhtSignReqDTO`
4. 打通 `CorpWalletCancelReqDTO -> YhtCancelReqDTO`
5. 修正 `AuthMd` 来源和费项映射来源

## 阶段二：在业务总入口补 `Jsqd.YHT`

目标：

- 让 `YHT` 成为正式结算通道

建议步骤：

1. `YwglServiceImpl` 付款分流增加 `YHT`
2. `khzhyxxCx()` 增加 `YHT`
3. `yhzhHqyeCx()` 增加 `YHT`
4. 付款结果补查、对账、动账链路增加 `YHT`

## 阶段三：新增 `YhtYwService` 收口业务接入

目标：

- 避免把通道细节散落到 `YwglServiceImpl`

建议步骤：

1. 新增业务接入层
2. 沉淀业务对象到 `yht` DTO 的映射
3. 沉淀主业务状态与 `yht` 状态的映射
4. 建立主业务与任务表关联键

## 阶段四：完善结果闭环

目标：

- 让 `yht` 真正成为可运营通道，而非“只会发报文”

建议步骤：

1. 回调后回写主业务状态
2. 补查后回写主业务状态
3. 对账/账户变动链路纳入现有业务处理框架
4. 补齐人工介入、失败重发、异常告警

## 7. 建议优先级

### P0：接入前必须处理

1. 费项映射改为真实业务配置来源
2. 查询接口契约统一，修正“至少一个条件”与校验器冲突
3. 评估并修正 `RE00 -> ACCEPTED` 的短路逻辑

### P1：接入首批流量前建议处理

1. `AuthMd` 不要在控制层硬编码为 `AM00`
2. 梳理旧 DTO 到 `yht` DTO 的业务转换规则
3. 设计主业务表与 `yht` 任务表关联键

### P2：进入正式通道后持续优化

1. 协议域 DTO 与实时域 DTO 拆分，减少语义复用
2. 把人工介入、补查、对账统一纳入运营视图
3. 完善 `YHT` 在总业务链的状态跟踪和告警

## 8. 最终结论

本次审查结论如下：

1. `yht` 当前不是“只有接口没实现”，而是“模块内通道能力基本完成，但还没有接入现有业务主链路”。
2. `yht` 主体设计方向是可以继续沿用的，不需要推倒重写。
3. 目前最明显的真实问题有三个：
   - 费项映射仍是静态演示数据
   - 协议查询接口契约不一致
   - `caps.306` 的 `RE00 -> ACCEPTED` 逻辑存在状态判定风险
4. 与现有业务对接时，不应直接模仿 `yqzl` 的报文执行形式，而应借鉴其“业务入口分流 + 通道接入层 + 结果回写主业务”的集成方式。
5. 推荐先从“企业钱包签约/解约旧入口路由化”开始，再补 `YwglServiceImpl` 的 `Jsqd.YHT` 分流，最后做主业务状态闭环。

## 9. 后续改造建议

1. 先修 `P0` 问题
