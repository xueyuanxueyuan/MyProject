# 一户通请求异常补偿处理核对

## 1. 核对问题

本次只回答一个问题：

1. 一户通请求发送异常、查询异常时，当前系统有没有补偿处理；
2. 如果有，做到哪一步；
3. 有没有真正做到自动重发原请求。

## 2. 结论先行

当前代码**有补偿处理**，但属于“状态补偿 + 查询兜底 + 人工接管”这一类，不等同于“请求异常后自动重发原请求”。

更准确地说：

1. **已做**：
   - 发送异常后落库标记为 `UNKNOWN`
   - 后台自动重试任务扫描
   - 自动补查/主动查询对端状态
   - 超限后自动转人工并告警
   - 支持人工查询、人工重发入口
2. **未看到真正完成的能力**：
   - 对实时/批量原始请求报文进行自动重新发送
   - 在发送异常后无条件重放原请求

因此，当前的补偿更像：

1. **先查状态，避免误重发**
2. **查不到再继续等待/转人工**
3. **不是自动原样重发**

## 3. 代码证据

### 3.1 发送异常时先落库为未知状态

实时交易发送异常时，`YhtRealtimeTradeSubmitOrchestrator` 会进入 `markDispatchFailure(...)`，再由 `YhtRealtimeDispatchBoundaryServiceImpl`：

1. 把 `send_status` 标为 `UNKNOWN`
2. 把 `biz_status` 标为 `UNKNOWN`
3. 写入 `SEND_FAIL`
4. 保留错误信息

同类逻辑在批量、签约、协议任务上也有。

这说明系统不是直接丢异常，而是先把异常任务保存下来，给后续补偿链路留入口。

### 3.2 有自动重试任务，但核心动作是“先查状态”

`YhtRetryServiceImpl.executeRetryTasks()` 会扫描：

1. `manual_flag = 'N'`
2. `send_status in ('FAIL', 'UNKNOWN')`
3. `retry_times < maxRetryTimes`
4. `next_retry_time <= now()`

然后领取任务并调用 `retrySingleTask(...)`。

但 `retrySingleTask(...)` 的核心逻辑不是直接重发，而是：

1. 先走 `queryBeforeRetry(task)`
2. 如果查到终态，就更新状态
3. 如果查询失败，就返回失败
4. 如果没查到终态且任务只是已发送/已受理，就继续等回执
5. 如果没查到终态且又不是已发送态，就认定本次重试失败

所以这个“重试”本质上更像：

1. **重试前状态核实**
2. **不是自动重放原始请求**

### 3.3 有自动补查任务

`YhtSupplementServiceImpl.executeSupplementTasks()` 会扫描：

1. `biz_status in ('ACCEPTED', 'PROCESSING', 'UNKNOWN')`
2. `receive_time is null`
3. 超过回执超时窗口
4. `supplement_times < maxSupplementTimes`
5. `next_query_time <= now()`

随后发起正式查询：

1. 实时：`queryRealtimeTradeStatus(...)`
2. 批量：`queryBatchByCaps103(...)`，必要时 `fetchBatchResultByCaps105(...)`
3. 协议：`queryProtocol(...)`

查询成功并进入终态后，才会更新业务状态；如果一直查不到结果，最终转人工。

所以补偿路径是存在的，而且是主动补查型。

### 3.4 查询异常也有落库，但主要是等下个窗口继续查

在 `YhtRealtimeStatusQueryOrchestrator` 中，`caps.203 -> caps.204` 查询如果抛异常，会：

1. 写 `error_code = QUERY_SEND_FAIL`
2. 写 `error_msg`
3. 更新 `last_query_time`

但不会在这里直接重发查询，而是依赖：

1. 下一个 `next_query_time` 窗口
2. 后台查询任务
3. 补查任务
4. 必要时人工接管

### 3.5 有人工介入和告警兜底

`YhtSupplementServiceImpl`、`YhtRetryServiceImpl` 在达到上限后都会：

1. 将 `manual_flag` 置为 `Y`
2. 发送告警
3. 记录人工日志

`YhtManualInterventionServiceImpl` 提供：

1. 人工查询
2. 人工重发
3. 人工改状态

但当前“人工重发”本质仍然是复用 `retryService.retrySingleTask(...)`，并不是单独重新组装并发送原始报文。

## 4. 风险边界

当前补偿能力的边界要说清楚：

### 4.1 已解决的部分

1. 请求异常不会直接丢任务
2. 会保留任务快照与错误信息
3. 有自动补查和自动重试调度
4. 超限后会转人工并告警

### 4.2 仍然存在的缺口

1. **未看到“自动重发原请求报文”的明确实现**
2. `retrySingleTask(...)` 主要做“先查状态”，不是直接调用原提交编排器重新发送
3. 所以对“请求发出去但本地超时，不确定对端是否收到了”的场景，当前策略是：
   - 先查状态
   - 查不到则等待/转人工
   - 而不是自动重放请求

## 5. 一句话判断

如果你问的是：

1. **请求异常后有没有兜底机制**  
   - 有，已经做了。
2. **请求异常后有没有自动补偿闭环**  
   - 有一部分，主要是状态补偿、主动补查、人工兜底。
3. **请求异常后有没有真正自动重发原请求**  
   - 目前从代码上看，**没有明显做到**。
