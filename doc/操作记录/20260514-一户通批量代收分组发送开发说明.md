# 一户通批量代收分组发送与防重发开发说明

## 1. 业务背景
根据业务需求，对于一户通（CAPS）的批量代收业务（对应 CAPS 报文 `caps.101.001.01`），由于不同银行托收的返回时间差异较大，为防止单个银行处理过慢影响整批数据的返回效率，提出以下要求：
1. **按银行分组发送**：将原本一个大批次的明细数据，按照“托收银行”拆分成多个子批次，分别发送。
2. **防重发控制**：提交成功的业务在收到处理结果前，不允许重复发起。

## 2. 改造排查与定位
* **业务入口**：排查 `YwglServiceImpl`，确认资金结算批量代收的实际发送落脚点在 `YwglServiceImpl.addSkywPlskjy` 方法。在该方法内判断了渠道若是 `YHT`，则会路由至 `YhtYwServiceImpl.addSkywPlskjy` 进行专线处理。
* **重构目标**：针对 `YhtYwServiceImpl.addSkywPlskjy`，由原先的“组装单条 `YhtBatchTradeReqDTO` 并下发”，重构为“基于 `List<SkywPlmx>` 分组，组装多条子批次 `YhtBatchTradeReqDTO` 循环下发”。
* **防重发依据**：底层已存在专门记录一户通批量状态的表 `zjjs_zj_yht_batch_task`，通过查询该表中与当前流水号相关的任务状态（`batch_status` 为 `SUBMITTED` 或 `PROCESSING`）即可实现有效拦截。

## 3. 核心代码改造 (`YhtYwServiceImpl.addSkywPlskjy`)
1. **实现防重发拦截**：
   - 注入了 `YhtBatchTaskDao` 依赖。
   - 使用 `LambdaQueryWrapper` 对 `batch_no` 进行 `likeRight` 匹配（因为后续分批时会加后缀）。
   - 如果查到存在状态为 `PROCESSING` 或 `SUBMITTED` 的任务，立刻抛出 `BizException` 阻断本次调用。

2. **明细分组处理 (`groupBy`)**：
   - 利用 Java 8 Stream API：
     ```java
     Map<String, List<SkywPlmx>> bankGroupedMap = list.stream()
             .filter(mx -> mx.getFkyhdm() != null)
             .collect(Collectors.groupingBy(SkywPlmx::getFkyhdm));
     ```
   - 实现了按付款银行代码 (`fkyhdm`) 将明细拆分为独立的子集合。

3. **子批次循环组装与调用**：
   - 遍历 `bankGroupedMap`。
   - 为区分同属一个大批次下的不同子批次请求，将推给底层的 `BatchNo` 设置为：`原始结算流水号 - 分组索引`（例如：`JSLSH-1`, `JSLSH-2`）。
   - 在构建 `YhtBatchTradeReqDTO.Detail` 时，修复了 `SerialNum` 应该取明细主键流水（`mx.getMxlsh()`）而非错写的方法的问题。
   - 将分组后的 `bankCode` 补充到每个明细对象的 `BankType` 中。
   - 每个子批次独立调用 `yhtService.submitBatchTrade(reqDTO)` 进行 `caps.101` 报文的发送。

## 4. 验证与结论
* 通过 `vfox` 环境执行 `mvn clean compile` 全量编译成功，验证了依赖注入、Mybatis-Plus 泛型及 Stream API 语法均符合规范，未对原生非一户通渠道的代码产生干扰。
* 当前后端接口层面已经 100% 具备了“防重发”及“按银行拆分下发”的能力。
* **遗留动作（前端）**：目前后端逻辑已就绪，前端界面只需如约增加“根据企业缴存职工数量、托收银行做筛选”的查询组件，调用现有接口即可享受分批发送与拦截能力。
