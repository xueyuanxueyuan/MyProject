## 1. 现有逻辑痛点深度剖析

通过对 `YwglServiceImpl.jyfs` 与相关入口类（如 `ZjbPlywJobHandler`）的源码分析，我们发现了 GPT 的设计思路（批量提取出所有的记录再传给 Facade，然后通过新调度器分组）与系统现有实现存在的**三大致命冲突点**：

### 1.1 业务类型 (`ywlx`) 的判定时机倒置
- **现有逻辑**：`zjjs_zj_jycsh`（初始化表）中**完全没有** `ywlx` 字段。当前代码是在 `jyfs` 的循环内部，通过 `sqbid` 和 `jslsh` 去查 `fkywDmService.getFkywXq`（付款详情）。如果查不到，再去查 `skywDmService.getSkywXq`（收款详情），以此来动态判断是付款还是收款，然后在这个详情对象里才可能拿到真实的业务类型。
- **GPT 设计冲突**：GPT 假设可以事先在 SQL 层通过 `ywlx = #{plan.ywlx}` 进行 Group By 或 Where 过滤。但由于表中压根没这个字段，所以“按 `ywlx` 分组预检再发送”的基础在不修改大量老数据或不进行大批量历史回填的前提下，根本无法直接运转。

### 1.2 规则引擎调用粒度不匹配
- **现有逻辑**：在 `jyfs` 中，是**单笔**调用 `ywglDmService.ruleExec` 进行交易控制（如拦截、限额检查等）。
- **GPT 设计冲突**：GPT 设想的是“任务级预检”（按业务组调一次，缓存 30 秒）。这直接跨过了现有的单笔风控逻辑。如果不将现有 `ruleExec` 的逻辑重构，强制引入新规则引擎会导致：要不单笔规则被绕过，要不单笔规则和全局预检规则冲突。

### 1.3 `execode` 的核心通道与物理形态路由不可替代
- **现有逻辑**：`execode`（交易码）不仅是后续 `MainEnterService` 选择底层执行器的依据，它更是住建部接口标准的物理通道标识。它严格决定了这一批记录是“发往住建部的批量交易”还是“单笔交易”，或者是“批量查询/单笔查询”。例如 `ZjbPlywJobHandler` 通过硬编码 `exeCodes` 集合来划定“只处理批量发送的指令”。
- **GPT 设计冲突**：GPT 的设计直接移除了基于 `execode` 的扫表逻辑，试图纯用 `ywlx` (业务类型) 来驱动。这是致命的错误，因为 `ywlx` 只能决定业务属性（如：这是提取还是缴存），但无法决定它当前处于住建部交互的哪个通道状态。抛弃 `execode` 等于破坏了与住建部接口的物理形态约定。

## 2. 需求适配与重构建议：`execode` 与 `ywlx` 的“二维协同”方案

既然 `execode` 决定了“怎么发”（物理通道/形态），而 `ywlx` 决定了“发什么”（业务内容），新的重构方案必须是**二维协同**的，不能非此即彼。

### 修正方案：基于 `execode` 扫表 + 内存级 `ywlx` 分组预检

由于 `zjjs_zj_jycsh` 表缺乏 `ywlx` 字段，且 `execode` 扫表逻辑不可废弃，我们可以采取以下架构重构方案：

1. **[Step 1: 维持通道边界] 保留 `JobHandler` 的 `execode` 扫表逻辑**
   保持现有的 `ZjbPlywJobHandler` 等入口不变，依然通过 `execode` 集合去数据库 `zjjs_zj_jycsh` 查出本轮待处理的记录（例如查出 200 条待批量发送的记录）。这确保了通道的正确性。

2. **[Step 2: 内存级业务类型解析] 反向回源补齐 `ywlx`**
   对这批查出来的记录，在内存中循环调用一次 `fkywDmService/skywDmService` 获取详情，为每个 `ZjJycsh` 临时对象打上真实的 `ywlx` 标签。

3. **[Step 3: 按 `ywlx` 内存分组与规则预检]**
   利用 Java 8 Stream API，将打好标签的记录在内存中按 `ywlx` 进行 `groupBy`。然后以组为单位（而不是单笔），向规则引擎发起批量预检请求。
   
4. **[Step 4: 结果过滤与发送]**
   - 预检通过的组：继续往下走，调用现有的 `MainEnterService` 或封装后的 Facade 真正发往住建部。
   - 预检拦截的组：这批记录本次跳过发送。

**优势**：
- **绝对安全**：完美保留了 `execode` 对于批量/单笔、发送/查询的严格控制。
- **满足新需**：实现了按 `ywlx` 业务类型进行分组、并在批量处理前进行规则引擎集中预检的需求。
- **无需改表**：避免了在缺乏 `ywlx` 的现状下强制修改表结构和回填海量历史数据。
