## 1. 背景与目标

### 1.1 背景

v3 结算核算系统是在保留原系统不变的前提下，新建的一套 DDD 分层优化版结算系统。既有实施计划已在 `doc/重构实施路线图/05-v3结算系统实施计划.md` 中明确：

- 新工程：`capinfo-gjj-busi-jshs-v3`
- 核心原则：接口兼容、领域驱动、策略化、消除冗余
- 模块分层：common / api / domain / infrastructure / app / gateway

前期重构已完成多阶段代码切片，但阶段记录主要偏“改动记录”和“测试证据”，缺少一份可供评审的详细设计文档。本文档用于补齐该缺口。

### 1.2 设计目标

1. 在不破坏原系统的前提下，建立 v3 DDD 分层骨架。
2. 将付款、收款、转账、账户、凭证、对账等核心业务按领域拆分。
3. 将 Controller 入参/出参逐步 DTO 化，避免对外暴露领域模型。
4. 将数据库访问收敛到 infrastructure，通过 Repository 接口隔离领域层。
5. 为多地区、多渠道差异预留策略扩展点。
6. 以小步 TDD 切片推进，不一次性替换生产链路。

### 1.3 非目标

1. 当前阶段不直接替换原系统生产服务。
2. 当前阶段不默认执行数据库结构变更。
3. 当前阶段不默认迁移历史数据。
4. 当前阶段不直接连接远程库或生产环境。
5. 当前阶段不承诺 Mapper 中引用的表已经在目标数据库中存在；表结构必须以后续数据库设计评审和 DBA 审批为准。

## 2. 总体架构设计

### 2.1 模块划分

| Maven 模块 | 当前职责 | 设计约束 |
| --- | --- | --- |
| `capinfo-gjj-busi-jshs-v3-common` | 公共枚举、异常、工具、常量 | 不依赖业务上层模块；可被 api/domain/app/infrastructure 使用 |
| `capinfo-gjj-busi-jshs-v3-api` | Feign Client、请求/响应 DTO、降级类 | 对外契约、跨服务契约集中管理；禁止放基础设施实现 |
| `capinfo-gjj-busi-jshs-v3-domain` | 领域模型、领域服务、仓储接口、领域事件、策略接口 | 禁止依赖 Mapper、DO、Feign、Redis、Kafka、Spring MVC Controller |
| `capinfo-gjj-busi-jshs-v3-infrastructure` | Mapper、持久化对象、RepositoryImpl、Redis/Kafka/MyBatis/Feign 适配 | 实现 domain 仓储接口；所有数据库访问必须在此层 |
| `capinfo-gjj-busi-jshs-v3-app` | 启动类、Controller、应用服务、Assembler、Web 配置、异常处理 | 编排请求、调用领域服务、DTO 转换；不写复杂业务规则 |
| `capinfo-gjj-busi-jshs-v3-gateway` | 网关路由、认证过滤、限流 | 统一入口，当前仅本地路由骨架 |

### 2.2 依赖方向

设计依赖方向如下：

```text
外部请求
  ↓
gateway（可选路由）
  ↓
app Controller
  ↓
app ApplicationService / Assembler
  ↓
domain DomainService / Model / Repository接口 / Event
  ↑
infrastructure RepositoryImpl / Mapper / Entity
```

约束：

1. `domain` 只定义业务概念和接口，不知道数据库表名。
2. `infrastructure` 将数据库行对象与领域模型互转。
3. `app` 负责 HTTP 契约与领域模型之间的转换。
4. `api` 中 DTO 是接口契约，不作为持久化对象使用。

### 2.3 运行 Profile 边界

| Profile | 行为 | 说明 |
| --- | --- | --- |
| `dev` | 默认排除 DataSource、事务、MyBatis、Redis、Kafka 自动配置 | 便于本地无中间件启动与单元测试 |
| `dameng` | 启用 MyBatis/Mapper/RepositoryImpl 等持久化能力 | 需要真实数据库结构支撑；当前不表示已执行建表 |

RepositoryImpl 当前标注 `@Profile("dameng")`，说明真实持久化链路被限制在达梦 profile 下启用。

## 4. 应用层设计

### 4.1 Controller 职责

Controller 只允许承担：

1. 接收 HTTP 请求。
2. 触发参数校验。
3. 调用 ApplicationService 或 DomainService。
4. 返回 `R<T>` 响应。
5. 不直接编写复杂业务规则。
6. 不直接暴露领域模型。

当前已治理方向：

- 付款、收款、转账、账户、凭证、对账均已有独立 Controller。
- 转账创建已引入 `TransferCreateReqDTO`，保留 Map 兼容入口。
- 部分接口已经通过 Assembler 返回响应 DTO。

仍需治理：

- 历史 Map 请求入口逐步替换为 ReqDTO。
- Controller 生成流水号的逻辑应下沉到编号组件或领域服务。
- HTTP 参数校验需接入 `@Valid`。

### 4.2 ApplicationService 职责

ApplicationService 用于承接用例编排：

1. 将请求 DTO 转换为领域模型。
2. 调用领域服务。
3. 处理跨领域协作。
4. 组装响应 DTO。
5. 保持事务边界清晰。

当前示例：

- `TransferApplicationService#createTransfer(TransferCreateReqDTO)` 通过 `TransferCreateAssembler` 转换后调用 `TransferDomainService`。
- `YwglPaymentApplicationService`、`YwglCollectionApplicationService` 承接收付款入口治理。

### 4.3 Assembler 职责

Assembler 是对象边界转换器：

| 转换方向 | 示例 | 说明 |
| --- | --- | --- |
| ReqDTO → Model | `TransferCreateAssembler#toTransferModel` | 外部请求进入领域前转换 |
| Model → RespDTO | `TransferAssembler`、`YwglCollectionAssembler` 等 | 领域结果返回接口前转换 |
| 禁止 | Entity/DO → RespDTO 直接透传 | 持久化对象不能跨过领域/应用边界 |

## 5. 基础设施设计

### 5.1 Repository 隔离

领域层定义仓储接口，例如：

- `FkywRepository`
- `SkywRepository`
- `TransferRepository`
- `AccountRepository`
- `VoucherRepository`
- `ReconRepository`

基础设施层实现接口，例如：

- `FkywRepositoryImpl`
- `SkywRepositoryImpl`
- `TransferRepositoryImpl`
- `AccountRepositoryImpl`
- `VoucherRepositoryImpl`
- `ReconRepositoryImpl`

设计原则：

1. 领域层只面向 Repository 接口。
2. Mapper 只在 infrastructure 中使用。
3. Entity 当前为持久化对象，不得出现在 Controller 返回值中。
4. 所有 Model/Entity 字段映射必须显式写在 RepositoryImpl 或专用 Converter 中。

### 5.2 Mapper 现状

当前 Mapper 使用注解 SQL，尚未使用 XML 文件：

| Mapper | 当前代码侧表名 | 规范建议表名 | 操作 |
| --- | --- | --- | --- |
| `FkywMapper` | `zjjs_zj_dbfk` | `zjjs_zj_dbfk` | insert/select/updateStatus |
| `SkywMapper` | `zjjs_zj_dbsk` | `zjjs_zj_dbsk` | insert/select/updateStatus |
| `TransferMapper` | `zjjs_transfer` | `zjjs_zj_zz` | insert/select/updateStatus |
| `AccountMapper` | `zjjs_account` | `zjjs_zh_zhxx` | insert/select |
| `VoucherMapper` | `zjjs_voucher` | `zjjs_cw_pz` | insert/select/updateStatus |
| `ReconMapper` | `zjjs_recon` | `zjjs_zj_dz` | insert/select |

重要说明：当前代码侧表名来自 v3 Mapper SQL，是待整改现状；正式数据库设计和后续 DDL 只能采用规范建议表名。仓库未发现针对这些表的建表 SQL，不能据此认定数据库已经完成重设计或已经执行。

### 5.3 Entity/DO 命名说明

当前 v3 infrastructure 中持久化对象命名为 `XxxEntity`：

- `FkywEntity`
- `SkywEntity`
- `TransferEntity`
- `AccountEntity`
- `VoucherEntity`
- `ReconEntity`

按项目规范，基础设施持久化对象更推荐命名为 `XxxDO`/`XxxPO`，领域对象使用 `XxxEntity` 或聚合。当前代码中 `XxxEntity` 实质承担的是 DO/PO 职责，不是领域实体。后续建议择机重命名为 `XxxDO`，或在文档中明确“infrastructure.dao.entity 下 Entity 为持久化 Entity，不得跨层使用”。

## 6. 数据与对象边界设计

### 6.1 对象类型边界

| 对象类型 | 所在层 | 是否可出层 | 说明 |
| --- | --- | --- | --- |
| ReqDTO/RespDTO | api/app | 可作为接口契约 | 用于 HTTP/Feign 入出参 |
| Model | domain | 仅领域层与应用层内部 | 表达业务状态和行为，不直接持久化注解 |
| Repository 接口 | domain | 被 app/domain 使用，由 infrastructure 实现 | 隔离持久化 |
| Entity（当前持久化对象） | infrastructure | 不可出 infrastructure | 实质为 DO/PO，承接 Mapper 字段 |
| Mapper | infrastructure | 不可出 infrastructure | 只封装 SQL |
| Event | domain | 可由 app/infrastructure 适配发布 | 后续用于 Kafka/事务事件 |

### 6.2 当前主要转换链路

```text
HTTP ReqDTO / Map
  → ApplicationService
  → Assembler.toModel
  → DomainService
  → Repository接口
  → RepositoryImpl.toEntity
  → Mapper SQL
  → 数据库表（代码侧假设）
```

查询返回：

```text
数据库行
  → Mapper
  → Entity
  → RepositoryImpl.toModel
  → DomainService/ApplicationService
  → Assembler.toRespDTO
  → R<T>
```

## 7. 接口兼容设计

### 7.1 兼容原则

1. 对外路径尽量保持与原系统或既有前端调用兼容。
2. 对内逐步 DTO 化、领域化。
3. 对外接口形态变更必须单独评审并提供兼容方案。
4. Map 入口属于兼容过渡形态，不作为最终设计。

### 7.2 当前转账创建兼容策略

- 保留 `createTransfer(Map<String,Object>)`。
- 新增 `createTransfer(TransferCreateReqDTO)`。
- Map 入口内部转换为 DTO，再走统一创建链路。
- 后续 Controller 切换到 `@Valid TransferCreateReqDTO` 后，Map 入口可降级为兼容适配或删除候选。

## 9. 错误处理与校验设计

### 9.1 异常约束

1. 业务参数错误统一使用 `BizException`。
2. 错误码优先使用 `JsErrorCodeEnum`。
3. Controller 层统一由全局异常处理转换为 `R<T>`。
4. 禁止随意向接口抛出未包装的基础设施异常。

### 9.2 校验分层

| 层级 | 校验内容 | 示例 |
| --- | --- | --- |
| DTO | 格式和必填 | `@NotBlank`、`@DecimalMin` |
| ApplicationService | 用例级组合校验 | 批次总金额、明细数量、幂等键 |
| Domain Model/Service | 业务不变量 | 金额必须大于 0、状态流转合法 |
| Infrastructure | 数据约束兜底 | 唯一索引、非空、外键或逻辑外键 |

## 10. 当前事实核查结论

基于 2026-05-25 对当前仓库的检查：

1. v3 工程存在 6 个持久化对象和 6 个 Mapper。
2. Mapper 当前代码中引用了 `zjjs_zj_dbfk`、`zjjs_zj_dbsk`、`zjjs_transfer`、`zjjs_account`、`zjjs_voucher`、`zjjs_recon` 等表名；其中英文表名已在数据库设计文档中修正为规范建议表名。
3. v3 工程目录内未发现 `.sql` 文件。
4. `doc` 目录未发现针对上述 v3 表名的建表脚本或数据库设计文档。
5. 多个阶段记录明确写明“未改数据库结构”。
6. 因此，当前可确认的是：代码侧设计了持久化对象和 Mapper 表结构假设；不能确认、也不应声称数据库已经实际重设计或执行。

## 11. 风险与控制措施

| 风险 | 说明 | 控制措施 |
| --- | --- | --- |
| 代码侧表结构假设与原库不一致 | Mapper 已引用新表名，但没有 DDL 与库表核验 | 补齐数据库设计文档和 DDL 草案；执行前 DBA 评审 |
| Entity 命名与规范不完全一致 | infrastructure `Entity` 实质为 DO/PO | 后续改名或文档约束其不可跨层 |
| Controller 仍存在兼容 Map 入口 | 类型安全不足 | 逐步切换 ReqDTO + `@Valid` |
| 批次模型未完全持久化 | 批量业务审计和重试困难 | 设计批次表和明细表，明确事务边界 |
| 事件未闭环 | 创建、回调、凭证、对账之间仍是骨架 | 引入事件发布与事务一致性设计 |
| 策略接口偏粗 | 地区差异仍未真正承载 | 拆分类型安全策略接口 |

## 12. 后续开发门禁

自本文档补齐后，v3 后续开发应执行以下门禁：

1. 涉及新业务模块：先补详细设计，再编码。
2. 涉及新增/修改持久化字段：先补数据库设计与迁移脚本草案，再编码。
3. 涉及表结构执行：必须单独确认，不得在普通本地开发任务中执行。
4. 涉及 Controller 契约变化：必须说明兼容策略和前端影响。
5. 交付前必须记录验证命令和结果。
6. 声称完成前必须执行 `scripts/guardrails/agent-delivery-guardrail.sh --scan-only`。
