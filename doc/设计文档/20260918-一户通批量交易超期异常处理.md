# 一户通批量交易超期异常处理

日期：2026-09-18

## 目标与范围

修复 prod 与嘉兴的一户通批量交易长期执行 CAPS 103 自动查询、未按期限转异常的问题。两套实现同步，不发布、不修改数据库现存业务数据。

## 根因与实现

- YhtBatchStatusQueryJobHandler 原先只筛选未终态及发送等待窗口，没有累计查询期限判断，候选 SQL 也没有排除 manual_flag=Y。
- 新增 YhtBatchQueryExpiryService，复用住建部 JYCS 参数：PAY 使用 PLFKCQ，COLLECT 使用 PLSKCQ，单位为分钟，参数中心仍为 Constants.HSDWDM。
- 从协议任务 send_time 起算，按完整分钟数严格大于配置值判断，与住建部现有 DateUtil.between(..., MINUTE) > minutes 保持一致。等于期限时不转人工。
- 原子更新 zjjs_zj_yht_protocol_task：manual_flag=Y，error_code=BATCH_QUERY_EXPIRED，记录原因，清空 next_query_time/next_retry_time，不改 biz_status。SQL 同时匹配任务 ID、BATCH 类型、原业务状态、原发送时间和 manual_flag=N，避免覆盖并发终态或重复转人工。
- 人工标记和 YhtManualLogDO 日志在独立事务内提交/回滚，避免一笔配置异常导致整轮已处理任务回滚。既有 /yht/manual/pending 按 manual_flag=Y 返回待人工任务，无须新建队列表。
- 定时 103、自动补查、自动失败重试均调用期限检查；人工单笔操作入口不增加期限拦截。
- 保留区域差异：prod 首次查询等待五分钟，嘉兴一分钟。批量任务候选增加 manual_flag=N 和 ID 升序，避免已转人工任务占满查询上限。

## 边界与上线注意

- 参数缺失或空白保持住建部现有不执行超期判断的行为，不自行引入默认期限；负数、非整数、缺失批量主表或无法识别的批量业务类型使本轮停止发送并记录异常。
- 无发送时间、已终态、非 BATCH 任务不做超期转人工。
- 不改变交易成功/失败结果，不触发退款、重发或资金记账。
- 已经超期的在查交易，在部署后进入下一轮符合筛选条件的自动调度时执行转人工；不需要手工批量改历史数据。已在途请求无法撤回。
- 本次仅确认后端人工队列接口及状态条件，未连接实际数据库，也未在浏览器验证菜单页面。
