# 临沂手续费考核及分批支付改造设计

## 1. 文档信息
- 需求来源：`doc/需求文档/临沂公积金管理系统需求/手续费考核及分批支付.md`
- 适用区域：临沂
- 分析范围：`/home/source/Jetbrains/Probject/Gjj/linyi`
- 当前阶段：需求分析与改造设计，不含代码实施

## 2. 需求摘要

原始需求可拆为 4 个核心点：

1. 手续费考核页面在手续费后新增`考核比例(%)`列，允许录入 `0~100`。
2. 银行考核金额默认按`手续费 * 考核比例`计算，保留 2 位小数；后续仍允许手工修改，且修改后的金额不再强制与比例联动。
3. 手续费考核完成后，要同步处理差额部分冲减对应科目。
4. 支付申请支持多次支付，默认取考核后的结果金额，允许手工修改，但本次支付金额不得大于该条银行预提记录（需求原文称之为明细）的考核金额；每次支付完成后自动生成凭证，直到全部支付完毕。

## 4. 差距分析

### 4.1 与需求不符的点

1. 缺少考核比例存储
   - 当前只能录入考核金额，不能记录用户输入的考核比例。

2. 默认支付金额口径不对
   - 当前批量支付默认取原手续费合计，不是考核后的金额。

3. 缺少分批支付数据模型
   - 当前只支持“生成一批支付记录”，没有对每条明细的累计支付和剩余待支付做持久化。

4. 缺少支付明细级校验
   - 当前支付申请更多是按银行汇总，没有做到“每条明细本次支付金额不得大于该条明细考核金额/剩余金额”。

5. 支付完成记账缺少精确分摊依据
   - 当前支付成功后的记账逻辑是按总额回推，不适合多次支付场景。

### 4.2 已有基础能力

1. 手续费预提、考核、支付审批、支付完成回调链路都已存在。
2. 差额冲减已有服务挂点，不需要从零设计。
3. 前端已有主页面、抽屉、批次申请页面，可在现有页面上增量改造。

## 5. 改造目标

本次改造建议达成以下目标：

1. 在不推翻现有链路的前提下补齐“考核比例 + 考核金额”的双字段模型。
2. 继续保留当前差额存储思路，即以`考核金额 - 手续费 = 差额金额`落入 `yhkhjlje`，降低既有记账链路改造成本。
3. 将“分批支付”落实到银行级预提记录的分次扣减与额度管控。
4. 将支付完成后的凭证生成改为基于“本次实际支付明细”记账，避免重复分摊或回推误差。

## 6. 详细设计

### 6.1 总体方案

总体流程重构为以 `cwhs_sxfyt` 为核心的资金控制，但在记账时按实际支付总额动态冲减明细：

1. 手续费计算生成 `cwhs_sxfyt / cwhs_sxfyt_mx`：
   - 预提头表新增字段 `khhzje` (考核后总额)、`yzfze` (已支付总额)、`ztdjje` (在途冻结金额)。
   - 预提明细表新增字段 `yzfje` (明细已支付金额，用于记账时的动态抵扣)。
2. 手续费考核时，在底层明细录入`考核比例`，默认推导`银行考核金额`。
3. 考核确认时：
   - 将所有明细的“银行考核金额”向上汇总为 `khhzje`，落入预提头表。
   - `差额金额 = khhsxf - sxf` 仍落入 `yhkhjlje` 以适配现有记账链路。
   - 产生差额冲减凭证（按实际差额）。
4. 支付申请时（基于 `sxfzfLy.vue`）：
   - 仅针对预提头表（银行汇总记录）进行查询与申请。
   - 查询当前银行汇总记录的可用额度（`剩余可付金额 = khhzje - yzfze - ztdjje`）。
   - 默认带入剩余可付金额，用户可改小。
   - 若 `ztdjje > 0`（允许在途），发起支付前强校验 `本次金额 <= 剩余可付金额`。
5. 保存支付申请：
   - 累加 `cwhs_sxfyt` 的 `ztdjje`（在途冻结金额）。
   - 针对当前银行生成 `zjjs` 的资金审批流程，携带本次真实的 `zfje`。
6. 资金审批完成（`CwzjzfSpwcSub` 与 `YwglServiceImpl` 记账回调）：
   - 若通过：释放头表 `ztdjje`，累加至头表 `yzfze`。
   - **动态冲减明细并记账**：遍历 `cwhs_sxfyt_mx`，使用本次支付总额 `zfje` 减去各明细尚未支付的金额（`khhsxf - yzfje`）。逐笔扣减的同时生成多笔 `CwjzYwlsMxDTO` 记账流水，并将扣减掉的金额回写至 `cwhs_sxfyt_mx.yzfje`，为下次部分支付提供正确的计算起点。
   - 若驳回/撤销：释放 `ztdjje`，回滚在途额度。
7. 当头表 `khhzje == yzfze` 时，将该预提批次状态置为“已支付完成”。

### 6.2 前端改造设计

#### 6.2.1 `sxfkh.vue` 手续费考核页

改造点：

1. 明细抽屉新增`考核比例(%)`列，位置放在`手续费`之后、`银行考核金额`之前。
2. `考核比例`输入规则：
   - 允许输入 `0~100`
   - 最多 2 位小数
3. `银行考核金额`默认计算规则：
   - `khhsxf = sxf * khbl / 100`
   - 保留 2 位小数
4. 允许继续手工修改`银行考核金额`。
5. 手工修改金额后，不再强制反算或覆盖比例。
6. 考核保存时同时提交：
   - `id`
   - `khbl`
   - `khhsxf`
   - `yhpdjg`

页面展示建议：

- 主列表继续展示`手续费`、`考核后手续费`
- 明细列表展示`手续费`、`考核比例(%)`、`银行考核金额`、`银行考核意见`
- 若金额被手工修改，可在前端用本地状态标识“已手工调整”，但该标识不必入库

#### 6.2.2 `sxfzfLy.vue` 分批支付与额度防超支交互

临沂专用的支付页面 `sxfzfLy.vue` 是基于单条预提记录触发支付弹窗，必须在此时进行防并发超发控制：

1. 额度实时查询与展示：
   - 每次点击“手续费支付”按钮，不仅带入本条记录的初始考核总额，必须调用后端接口实时获取：`khhzje`(考核后总额)、`yzfze`(已支付总额)、`ztdjje`(在途冻结金额)。
   - 在弹窗中增加只读展示字段：“考核总额”、“已支付金额”、“支付审批中金额”、“本次最大可付”。
2. 本次支付金额校验：
   - 默认赋值 `本次支付金额 = khhzje - yzfze - ztdjje`。
   - 用户可修改，但强校验 `0 < 本次支付金额 <= 剩余可付金额`。
3. 在途并发防冲突机制（硬拦截）：
   - 如果业务规约不允许对同一银行同时发起多笔支付申请，前端须判断 `ztdjje > 0` 或 `spzt == '支付中'` 时，将“手续费支付”按钮置灰，并提示“存在在途的支付申请，请等待审批结束后再发起”。
   - 若允许同时在途，则基于剩余额度做防超发拦截即可。
4. 状态联动刷新：
   - 列表中针对部分支付的记录，可增加“部分支付”状态徽标，提升用户辨识度。

#### 6.2.3 `sxfjt.vue` 手续费计算页

建议保持现有功能不变，仅补充展示字段：

- 主列表可增加`考核后手续费`
- 状态枚举增加“已部分支付”“已支付完成”时可同步显示

### 6.3 后端接口改造设计

#### 6.3.1 考核保存接口 `sxfmxKh`

现状：

- 只接收 `khhsxf`

改造建议：

- 请求 DTO `SxfytMxKhReqDTO` 增加 `khbl`
- 服务保存逻辑调整为：
  - 校验 `khbl` 在 `0~100`
  - 校验 `khhsxf >= 0`
  - `yhkhjlje = khhsxf - sxf`
  - 持久化 `khbl` 与 `yhkhjlje`

说明：

- 仍复用 `yhkhjlje` 作为“差额金额”字段，减少既有凭证逻辑调整面。
- 页面显示时继续通过 `sxf + yhkhjlje` 反算考核金额。

#### 6.3.2 考核确认接口 `sxfKhQr`

改造建议：

1. 继续更新头表/明细状态为已考核。
2. 汇总头表时保留：
   - `sxf`：原手续费
   - `yhkhjlje`：总差额金额
3. 调整冲减凭证生成逻辑，明确按照“差额金额”而不是“奖励金额”口径记账。
4. 补充幂等控制，避免重复确认导致重复冲减。

#### 6.3.3 支付申请与并发防超支接口 (`sxfytZfsq`)

现状：
- `sxfytZfsq` 默认直接使用 `sxfyt.sxf` 或前端传入的 `je` 发起支付，没有并发冻结和防超额控制。
- 并未存储每次发起的实际金额与累计金额。

改造建议：
1. `cwhs_sxfyt` 表扩展资金控制字段：
   - 增加 `khhzje` (DECIMAL)
   - 增加 `yzfze` (DECIMAL)，默认 0
   - 增加 `ztdjje` (DECIMAL)，默认 0
2. 改造 `sxfytZfsq` 接口，加入**乐观锁与额度强校验**：
   - 查询 `sxfyt` 最新状态，校验 `本次请求支付金额 <= khhzje - yzfze - ztdjje`。
   - 利用 `update cwhs_sxfyt set ztdjje = ztdjje + #{je} where id = #{id} and (khhzje - yzfze - ztdjje) >= #{je}` 进行原子扣减（或行锁），确保不会发生并发透支。
3. 状态回流：
   - 若支付申请在 `zjjs` 系统成功，`sxfyt` 不再强制被锁定为“已支付完成”，而是标记为“部分支付/支付中”。

#### 6.3.4 资金审批完成回调接口 (`CwzjzfSpwcSub`) 与凭证重构

现状：
- 当前在收到审批通过事件后，会调用 `receiveCwjzxx(...)` 记账，但在多次支付场景下，原记账逻辑是依靠计算公式（总考核额减去本次支付）倒推剩余金额，这在发生过部分支付后会导致明细扣减计算错乱，且未记录明细的已付状态。

改造建议：
1. 回调头表额度释放与累加：
   - **审批通过**：执行 `update cwhs_sxfyt set ztdjje = ztdjje - #{je}, yzfze = yzfze + #{je} where id = #{id}`。若 `yzfze == khhzje`，则将预提头表状态推进为 `已全部支付`。
   - **审批驳回/撤销**：执行 `update cwhs_sxfyt set ztdjje = ztdjje - #{je} where id = #{id}`，恢复可用额度。
2. 凭证记账与明细动态冲减逻辑（`YwglServiceImpl.receiveCwjzxx`）：
   - **算法重构**：从 `Cwzjzf` 取出本次真实的支付申请金额 `je`，以此金额为初始分配游标。
   - 遍历 `cwhs_sxfyt_mx`，取各明细的剩余待付金额 `(khhsxf - yzfje)` 与游标进行抵扣。
   - 抵扣部分直接生成该明细对应的 `CwjzYwlsMxDTO` 业务流水。
   - 同步执行 `update cwhs_sxfyt_mx set yzfje = yzfje + #{抵扣部分金额} where id = #{明细ID}`，将扣减进度持久化。
   - 借方/贷方流水总和必须完全等同于实际向外发出的资金结算金额。

### 6.4 数据库改造设计

1. `cwhs_sxfyt_mx` (手续费预提明细表)
   - 新增 `khbl` DECIMAL(5,2) DEFAULT NULL COMMENT '考核比例(%)'
   - 新增 `yzfje` DECIMAL(16,2) DEFAULT 0 COMMENT '已支付金额（用于记账时动态冲减明细记录）'

2. `cwhs_sxfyt` (手续费预提头表)
   - 新增 `khhzje` DECIMAL(16,2) DEFAULT 0 COMMENT '考核后总额'
   - 新增 `yzfze` DECIMAL(16,2) DEFAULT 0 COMMENT '已支付总额'
   - 新增 `ztdjje` DECIMAL(16,2) DEFAULT 0 COMMENT '在途冻结金额'

说明：
- 放弃独立的“支付-明细分摊关系表”，因为临沂实际业务只需按银行合并发起资金审批。
- 在 `cwhs_sxfyt_mx` 追加 `yzfje` 是为了在资金系统审批完成后，能通过算法对本次支付总额进行逐笔抵扣（动态冲减），从而拆分生成正确的底层明细级借贷凭证流水。

### 6.5 查询口径设计

1. 剩余待支付金额查询
   - `cwhs_sxfyt` 的剩余可用额度 = `khhzje - yzfze - ztdjje`。
   - 每次前端打开 `sxfzfLy.vue` 或调用支付请求前，均调用后端统一工具方法计算此额度。

2. 凭证生成依据
   - 冲减凭证：取 `cwhs_sxfyt.yhkhjlje` (即：差额金额)。
   - 支付凭证：取本次 `cwhs_sxfjs.zfje`，完全对齐实际资金系统下发的付款流水 `Cwzjzf.je`。

## 7. 推荐实施步骤

1. 前端 `sxfzfLy.vue` 增加额度实时获取和防超额前端控制逻辑，增加相关状态的明确提示。
2. 后端 `SxfytMxKhReqDTO` 补充 `khbl`，`sxfmxKh` 接口落库。

## 8. 风险与注意事项

1. 并发资损风险
   - 在多次支付场景下，如果有多个操作员针对同一笔预提记录同时发起支付申请，若只校验剩余额度而不使用 `ztdjje`（在途冻结），必定产生超额度资损。
   - **必须**在发往 `zjjs` 前通过行锁扣减剩余额度累加至 `ztdjje`。
2. 状态机闭环
   - `CwzjzfSpwcSub` 回调必须绝对可靠。一旦 MQ 消息丢失，`ztdjje` 将被永久锁定。需要考虑增加定时任务兜底，或在驳回节点增加主动重试机制释放额度。
3. `pch` 与 `ywslbh` 混用问题
   - 现存代码在 `sxfytZfsq` 生成 `CwzjzfAddReqDTO` 时，给 `cwhs_sxfyt` 的 `pch` 赋予了 `ywslbh`，且部分查询存在 `pch = ywslbh` 假定。在头表级别的多次支付下，一次预提可能对应多笔 `ywslbh`（多次资金申请）。
   - **应对策略**：在多笔支付时，`cwhs_sxfyt.pch` 应当只表示该预提所属的“考核批次”，而不能被资金流水号覆盖。资金系统的关联应当通过新扩展的映射表或在 `Cwzjzf` 反向记录 `sxfyt.id` 来解耦。这需要在开发阶段重点关注与整改。

## 9. 结论

临沂需求不是从零新建功能，而是在现有“手续费计算 -> 考核 -> 支付审批 -> 支付完成记账”链路上补齐 3 个核心能力：

1. 考核比例持久化
2. 头表级控制的分批支付，放弃明细分摊
3. 按本次支付实际金额自动生成凭证

推荐采用“保留现有表结构主干、补充考核比例字段、通过头表资金池字段（在途冻结机制）承接分批支付金额”的方案。该方案严格对齐了实际资金下发口径，有效避免了并发超发风险，同时能够满足临沂“允许多次支付、每次自动生成凭证、最终全部支付完成”的完整业务要求。
