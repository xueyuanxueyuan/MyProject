# 一户通挡板账号校验规则与银行流水号限长实施设计

## 一、背景与诉求

1. 原「场景规则」按中心账户 + 报文类型/请求号等十余个条件组合匹配并强制成功/失败，配置重、语义绕。要求简化为类似账号校验页面的形态：只配置 **账号规则（正则表达式）**、**是否有效**、**是否为一类卡**；且校验对象改为 **对手账号**（而非中心账号），批量交易按明细中的对手账号逐笔核对。
2. 新增 **随机模拟交易状态成功/失败开关**：开启后交易状态按设定概率随机失败，用于压测与异常模拟。
3. 资金流水的 **银行流水号** 统一最长 32 位、不得超限；并提供 **历史数据统一更新** 功能。

## 二、账号校验规则（场景规则简化）

### 模型

`MockScenarioRule` 精简为：`id / name / enabled(默认true) / accountRule(对手账号正则) / valid(默认true) / class1Card(默认true) / remark / updatedAt`。原 `matchAcctNo/matchAcctSuffix/matchProtocolNo/forceStatus/forceRetCode/disableAutoCallback` 等字段与匹配逻辑全部删除；`MockScenarioContext` 与 `matchScenario` 保留为 `@Deprecated` 空实现仅兼容旧调用签名。

### 判定逻辑（MockStoreService.evaluateCounterparty）

按 **对手账号** 校验，规则匹配优先级为 **后更新者优先**：

- 空对手账号：不校验，默认成功。
- 未命中任何规则：不限制，默认成功。
- 命中且 `valid=false`：交易失败，返回码 `ACCT_INVALID`（对手账户无效）。
- 命中且 `valid=true, class1Card=true`：一类卡，全部成功。
- 命中且 `valid=true, class1Card=false`：二类卡，日交易限额 1 万元（`CLASS2_DAILY_LIMIT`），返回码 `LIMIT_EXCEED`；已用金额 = `sumUsedToday`（YHT_MOCK_TRADE 当日成功 + YHT_MOCK_BATCH 结果文件中当日成功明细，按对手账号汇总）+ 同批次内 `runningUsed` 跨明细累计。
- `randomFail` 开启时：仅对判定为成功的结果再按 `randomFailRatio` 概率随机失败，返回码 `RANDOM_FAIL`（规则失败优先于随机失败）。

正则语义：空正则 = 匹配任意；非法正则退化为精确匹配；使用 `find()`（包含语义）而非全匹配。

### 接入点

- 单笔（caps.201/203 等）：`MockGatewaySupport.buildTradeState(document, settings)`，取 `CdtrActId` 为对手账号、`PayAmt/TxAmt` 为金额、`CheckDate` 为业务日期，判定失败时 `status/resFlag=FAIL`、`retCode/retMsg` 取判定结果。
- 批量（caps.101）：`buildBatchState` → `buildBatchResultFileData` 按请求文件逐条明细的对手账号（第 4 列）与金额（第 6 列）判定，结果文件逐条回写 `00 / ACCT_INVALID / LIMIT_EXCEED / RANDOM_FAIL`；批次终态按结果文件汇总推导（全部 00 = SUCC，否则 FAIL 带首个失败明细），`movementEligible` 仅在全部成功时为 true。
- 配置接口 `/yht-mock/api/scenarios` 与 `/callback-config`（`randomFail`/`randomFailRatio`）按模型字段自动适配，无签名变化。

### 数据库（schema v6）

- `schema-dm-migration-v5-v6.sql`：`YHT_MOCK_SCENARIO` 删除 12 个旧匹配/强制列，新增 `C_ACCOUNT_RULE CLOB`、`C_VALID SMALLINT DEFAULT 1`、`C_CLASS1_CARD SMALLINT DEFAULT 1`；`YHT_MOCK_SETTINGS` 新增 `C_RANDOM_FAIL SMALLINT DEFAULT 0`、`C_RANDOM_FAIL_RATIO DECIMAL(5,4) DEFAULT 0.5`；版本升到 6。存量规则迁移后默认「有效 + 一类卡」，行为向后兼容（一律按成功处理）。
- `MockStoreService.init()` 严格校验 `SCHEMA_VERSION=6`，未升级直接启动报错。

### 前端

- `index.html` 场景规则表单精简为：规则名称、账号规则（正则）、启用规则/是否有效/是否一类卡三个勾选、备注；列表只展示 ID / 规则 / 账号规则 / 有效性·卡类型 / 操作。
- 回调配置面板新增「随机模拟交易失败」区块：`randomFail` 勾选 + `randomFailRatio` 数字输入（0~1，步进 0.05，默认 0.5）。
- `app.js` 的 `loadSettings/saveSettings/scenarioPayload/resetScenarioForm/loadScenarioToForm/refreshScenarios` 六处全部对齐新模型。

## 三、银行流水号 32 位限长与历史数据统一更新

### 超长根因

| 来源 | 原逻辑 | 长度 |
|---|---|---|
| 批量按包流水 | `"MOCK" + 确定性UUID去横线(32位hex)` | **36**（超限） |
| 单笔兜底流水（MockGatewaySupport） | `"MOCK-SEQ-" + 24位hex` | **33**（超限） |
| 单笔沿用原交易流水 | `required(trade.sysSeqNo, 40, "银行流水")` | 上限 40，银行请求原值任意长（超限） |

结算端 `yhlsh` 及下游落库按 32 位约束，以上均须收敛。

### 生成端收敛（MovementFlowStore）

- `SERIAL_MAX = 32`，`normalizeSerial(String)`：≤32 原样返回；超长保留前 19 位原值前缀 + `UUID.nameUUIDFromBytes(原值)` 十六进制前 13 位，合计恰好 32 位。**确定性哈希保证同一原值多次归一化结果一致（幂等）**，生成端与历史修复端共用同一规则。
- 批量按包：改为 `"MOCK" + hex前28位` = 32 位（仍由去重键确定性派生，重复处理同批次生成同一流水号）。
- 单笔兜底：`"MOCK-SEQ-" + 23位hex` = 32 位。
- 单笔登记：`normalizeSerial(trade.sysSeqNo)` 后再 `required(..., SERIAL_MAX, "银行流水")`（空值仍拒绝，超长值自动收敛）。

### 历史数据统一更新

- 存储：`MovementFlowStore.normalizeHistoricalSerials()`，在写锁事务内扫描 `LENGTH(C_SYS_SEQ_NO) > 32` 的全部资金流水，逐条收敛并 `save`（版本号自增）；**已生成通知报文（payload）中的 `yhlsh` 同步改写**，避免补推时仍携带超长旧流水号；报文不可解析时保留原报文仅更新流水号字段。返回 `inspected / normalized / fixed[{id, sourceType, status, before, after}]`，原值保留可追溯。
- 接口：`POST /yht-mock/api/movements/normalize-serials`（幂等，可重复执行）。
- 前端：资金流水页新增「修复超长流水号」按钮（`normalizeSerialsBtn`），确认弹窗说明收敛规则，执行后刷新列表并展示修复明细（before → after，最多展示 20 条）。
- 不改表结构：`YHT_MOCK_FLOW.C_SYS_SEQ_NO` 本为 VARCHAR(256)，纯值级收敛，无需 schema 升版。
- 边界说明：截断哈希仅保留 19 位前缀，两个前缀相同且超长的原值可能收敛为同一流水号；资金流水去重键是 `movementKey` 而非流水号，挡板语义下可接受。已受理（SUCC）流水的历史流水号也会被改写，属「统一更新」预期行为。
