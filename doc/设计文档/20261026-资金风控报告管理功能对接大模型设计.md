## 13. 变更记录 v2 — 现场失败修复 + 无占位段总结模式（2026-10-26 下午）

### 13.1 现场失败与根因

首次端到端真实模型分析失败，报错：`锚点段落必须恰好含一处「请人工补充分析」: 9月初住房公积金活期存款0亿元，活期存款较上月初减少0亿元，请人工补充分析。`

根因（v1 锚点契约的三个结构性缺陷）：
1. **模型回写整段作 anchor**：v1 要求「20 字以内前缀」，真实模型无视该约束，把整段文本当锚点返回——校验依赖模型自觉，不可靠。
2. **段落含多处占位文本**：真实报告一段里出现两处「请人工补充分析」（如「……请人工补充分析，趋势判断也请人工补充分析」），v1 的 `placeholders != 1` 检查直接拒绝。
3. **模板无占位段无从下手**：报告模板不一定有「请人工补充分析」占位段（用户确认：占位段按模板而定，没有时应在报告最后增加分析总结段落）——v1 契约只覆盖占位替换一种形态。

### 13.2 v2 契约（已实施）

| 维度 | v1（已废弃） | v2 |
|---|---|---|
| 定位 | 模型输出 anchor（原文前缀）+ 后端 contains 检索 | 模型输出 `paragraphIndex`（输入中原样给定的段落下标）+ 后端按下标直接定位——不依赖模型抄写原文 |
| AI 区间 | 模型自己标 `aiRanges[start,end]` | **后端程序推导**：newText 与原段落的公共前缀/公共后缀之外即差异区（AI 文本），模型不再标注区间 |
| 替换内容 | content（完整段落）+ aiRanges | `newText`（替换后的完整段落文本），要求仅含 paragraphIndex/newText 两字段 |
| 多占位 | 一段两处占位即失败 | 一段多处占位输出一条 replacement（newText 中全部替换） |
| 无占位段模板 | 不支持 | `{"paragraphIndex":-1, "newText":"智能分析总结：..."}` 追加总结段（`mode=SUMMARY`），排在全部原段落后，前端渲染为独立标题块 |
| 数字保护 | 仅核 AI 区间新数字 | 双向：①AI 差异区内的新数字须在 reportData 快照白名单；②**原段落数据性数字在 newText 中丢失即拒绝**（结构性数字/月区间如「1-9月」豁免） |

### 13.3 验证（真实执行）

- 后端 `LlmReport*Test`：**31 例全绿**（Validation 15 + Service 9 + ModelClient 7）；`Llm*Test` 全量回归 **303 例全绿**（预测域基线 272 不降）。
- 前端 `bgmbgl-llm.test.cjs`：**10/10 全绿**（新增总结段渲染契约）；`jcyc.test.cjs` 回归 32 过/1 跳不降。

### 14.1 判定：报错来自未重启的旧进程

用户复测仍报 `锚点为空、超长或重复: 从全市资金流量情况图可以看出，请人工补充分析，月均资金流入16.41亿元，影响资金流入的主要原因是请人工补充分析。`

核查：该错误文案是 **v1 校验器**的输出；v2 源码与 `target/classes` 编译产物均已 grep 确认**不存在此文案**（v2 用 `paragraphIndex 越界或重复定位同一段落`）。结论：**运行中的后端进程仍是 v1 旧代码，v2 修复未生效**——需要重启后端服务，代码无需再改。

> 教训沉淀：报错文案先 grep 当前源码——文案已不存在即说明跑的是旧进程，不要先动代码。

### 14.2 业务口径确认与逐段分场景补强（已实施，commit `65acb50`）

用户确认：报告多处【请人工补充分析】分布在不同环节（资金流入/流出/归集/提取/贷款/存贷比/增值收益等），**应当按所属场景分别生成合适的分析内容**。补强两点：

1. 分析指令明确：占位段逐段输出一条 replacement，不得整份报告只输出一条；每条分析必须针对该段所属环节场景（结合该段图表、数据与上下文主题）生成，各段互不雷同。
2. 校验器新增守卫：多条 replacement 的 `newText` 完全相同即拒绝（防复制粘贴式分析）。

## 16. 变更记录 v3 — 第三次现场失败修复：后端拼接替代模型抄写（2026-10-26 晚，以此为准）

### 16.1 现场报错与根因

报错：`模型输出未通过结构校验（定位下标越界、内容雷同或删改原文数据）`。

根因是 v2 契约的固有缺陷：v2 要求模型输出**替换后的完整段落文本（newText）**并「逐字保留其余文字」。对含数据的长段落，LLM 抄写时必然引入措辞/数字格式偏差，「原文数字保护」守卫与模型天性冲突——不是模型偶尔犯错，而是**契约把确定性任务交给了概率性组件**。

### 16.2 v3 契约（已实施，commit `29e043e`）

| 维度 | v2（废弃） | v3 |
|---|---|---|
| 模型输出 | `{paragraphIndex, newText}`（抄写整段） | `{paragraphIndex, analysisText}`（**只写占位处应补入的分析文字**） |
| 原文保留 | 要求模型逐字保留（不可靠） | **后端拼接**：`newText = 原段落.replace(占位文本, analysisText)`，逐字保留由构造保证 |
| AI 区间 | 公共前后缀差异推导 | `newText.indexOf(analysisText)` 精确可算 |
| 结构失败提示 | 笼统汇总文案 | 透出真实 cause（哪个下标越界/哪段雷同/无占位可替换） |
| 拼接排版 | — | 消除「。。」「，，」重复标点（占位后紧跟句号场景） |
| 数字核对 | 软警告（不变） | 软警告（不变，用户口径「数字不匹配也可以生成」） |

指令同步改写：明确告知模型「原段落文字由系统自动保留，无需你抄写」，并允许基于给定数据做合计/均值/占比推算（注明口径即可）。

### 16.3 设计原则沉淀

**凡是能由输入+确定性规则构造的输出，一律不让模型生成**。三轮现场失败的共同根因就是让模型做抄写（锚点→下标→整段 newText），模型职责最终收窄到「写分析文字」一件事；定位、拼接、区间计算、数字核对全部由后端确定性完成。

### 16.4 验证与状态

- 后端 `Llm*` 回归 **305 例全绿**（Validation 17 例按 v3 重写：拼接正确性/多段替换/越界 cause/雷同拒绝/未知数字警告/总结段标题约束等）。
- 提交：后端 `29e043e`；记忆日志同步。
- **待用户重启后端复测**——v3 已把模型失败面收窄到「分析文字内容本身」，结构性失败模式应已消除。

## 17. 变更记录 v3.1 — 第四次现场失败修复：逐条容错（2026-10-26 晚，以此为准）

### 17.1 现场两连报与根因

| 报错 | 根因 |
|---|---|
| `分析输出必须为严格JSON对象且仅含 replacements 与 unresolved` | 模型在顶层附加了解释性字段（如 summary/note），v3 的 `root.size() != 2` 即拒——对输出形态过苛 |
| `paragraphIndex 越界或重复定位同一段落: 10` | 模型个别条目下标数错，一条坏目拖垮整份分析（其余条目可能全部有效） |

### 17.2 v3.1 处置（已实施，commit `aa37bcf`）

**逐条容错**替代整任务失败：

1. 顶层多余字段忽略——只要求 `replacements` 数组存在；`unresolved` 缺省按空数组处理。
2. 单条坏目（下标越界/重复、定位段无占位、analysisText 为空/雷同/缺字段）→ **跳过并记入 `skipped[]`**，其余条目照常生效。
3. `skipped` 并入响应的「未补全的段落」区块，用户在预览中可直接看到某段为何未被补全（如「段落10：paragraphIndex 越界或重复定位同一段落: 10」）。
4. 仅当**全部条目无效**时才整体失败，cause 汇总真实原因。

### 17.3 契约演进脉络（四轮现场驱动）

v1 锚点（模型抄写锚点）→ v2 下标+整段 newText（仍抄写）→ **v3 下标+只写 analysisText（拼接后端化）** → **v3.1 逐条容错（坏目跳过留痕）**。方向一致：模型职责收窄到「写分析文字」，非实质偏差不再致命，留痕从失败信息升级为页面可见的未补全说明。

### 17.4 验证与状态

- 后端 `Llm*` 回归 **312 例全绿**（Validation 19 例：新增越界跳过保留有效条目、全无效失败、多余字段忽略、重复跳过等）。
- **待用户重启后端复测**——两份报告（年度/月度资金）建议各跑一遍：预期月度资金报告不再因下标 10 一条失败，该段会出现在「未补全的段落」清单里，其余段落正常补全。

## 18. 变更记录 v3.2 — 金额单位混标修复（2026-10-27，以此为准）

### 18.1 现场实录（用户截图核查发现）

模型把数据快照中「元」的数值直接标「亿元」：

| 分析表述 | 实际含义 | 正确表述 |
|---|---|---|
| 活期存款 421509871.8亿元 | 421509871.8 元 | 约 4.22 亿元 |
| 较上月初增加 394643.04亿元 | 394643.04 元 | 约 39.46 万元 |
| 定期存款到期 80000000亿元 | 80000000 元 | 8000 万元 |

用户判定：单位不对，应除以一亿。附带证据：页面「数字核对提醒」提示了 10/80000000，唯独未提示 421509871.8——证明该数值来自快照（元单位），属「白名单内但单位标错」盲区。

### 18.2 根因与修复（commit `7261e09`）

根因：从未告知模型 dataDigest 数值的单位是元；模型看到报告人类口径用亿元，就把元的数值直接贴上亿元标签。修复三处：

1. **指令金额单位纪律**：dataDigest 全部金额单位为元；以亿元/万元表述必须先换算（÷1e8 / ÷1e4），禁止把元的数值直接贴单位标签，并给出反例（421509871.8亿元→约4.22亿元）。
2. **visible 显式携带 `dataDigestUnit`**：`{unit: "元（YUAN）", 换算说明: ...}`，与指令双保险。
3. **校验单位量级守卫**：`数值+亿元`（≥1000）或 `数值+万元`（≥100000）的表述追加「疑似漏做单位换算」软提醒——不阻断（允许业务大额），页面提示人工核实。
4. 顺带：结构性数字豁免补「N月」月份形态（「10月初」的 10 曾被误报白名单外）。

### 18.3 验证与状态

- 后端 `Llm*` 回归 **314 例全绿**（新增：元标亿元触发提醒、正确换算无提醒两例）。
- **待用户重启后端复测**：预期分析中亿元/万元数值为换算后的人类口径；即使模型仍漏换算，页面「数字核对提醒」会出现「量级异常（疑似漏做单位换算）」专项提示。

## 0. 结论摘要

1. 在报告域（`busi/doc`）新建**独立的大模型分析链路**：提示词智能生成、智能分析、分析结果留存，全部面向「报告内容分析」语义，**不读写预测域三张表、不调用 `LlmPredictionService`、不依赖任何训练产物**。
2. 技术层复用仅限「与业务语义无关的纯技术组件」的**模式**：不发送 `max_tokens`、`enable_thinking` 默认 false、`unwrapJson` 剥围栏、占位回写拦截、异步任务+轮询。落地方式为**新建 `LlmReportModelClient`**（独立类，日志前缀/输出标记均按报告域定义），预测域既有类零改动。
3. 智能分析采用「**锚点+替换**」严格 JSON 契约：只替换「请人工补充分析」占位段落，其余段落一字不改；分析结果独立留存（推荐建 `zjfk_llm_report_analysis`），**不改动原 docx 字节**。
4. 分析输入 = 报告生成时冻结的 `GeneratedReportDO.reportData` 快照 + 生成 docx 的段落正文；**不重新跑 SQL 取实时数**（分析必须锚定报告生成时点的数据）。
5. 分五阶段（R1–R5）交付，每阶段有独立验收；交付判定以提示词 §十完成判定为准。

## 3. 数据模型设计（DDL 设计稿，**未获批不执行**）

> 达梦语法，参照 `数据库设计/大模型对接表结构.sql` 既有风格；执行与回滚脚本在 R1 阶段随批准结果补齐 `*_migration_20261026.sql` / `*_rollback_20261026.sql`。

### 3.1 `zjfk_llm_report_prompt` — 报告分析提示词（版本乐观锁）

```sql
CREATE TABLE zjfk_llm_report_prompt (
    context_hash   VARCHAR(64)  NOT NULL,
    report_id      BIGINT       NOT NULL,
    prompt_text    CLOB         NOT NULL,
    version        INTEGER      NOT NULL,
    updated_by     VARCHAR(128) NOT NULL,
    created_at     TIMESTAMP(6) DEFAULT CURRENT_TIMESTAMP NOT NULL,
    updated_at     TIMESTAMP(6) DEFAULT CURRENT_TIMESTAMP NOT NULL,
    NOT CLUSTER PRIMARY KEY(context_hash),
    CONSTRAINT ck_llm_report_prompt_version CHECK (version >= 1)
);
CREATE INDEX idx_llm_report_prompt_report ON zjfk_llm_report_prompt(report_id);
```

- 主键沿用「context_hash」模式（借鉴交互与存储模式，业务语义不同）。报告域 context_hash = `LlmRunJson.hash` over `{reportId, reportPath, reportData摘要, 分析角度}`——报告记录不可变，故同一报告+同一角度恒定，提示词可复用；不同角度生成不同提示词互不覆盖。
- `updated_by` 固定 `system`（与预测域 `OPERATOR` 口径一致；内网项目不做登录身份隔离）。

### 3.2 `zjfk_llm_report_task` — 报告域异步任务

```sql
CREATE TABLE zjfk_llm_report_task (
    task_id      VARCHAR(36)  NOT NULL,
    report_id    BIGINT       NOT NULL,
    task_kind    VARCHAR(32)  NOT NULL,
    task_status  VARCHAR(16)  NOT NULL,
    context_hash VARCHAR(64)  NOT NULL,
    request_json CLOB         NOT NULL,
    result_json  CLOB         NULL,
    error_msg    VARCHAR(2000) NULL,
    created_at   TIMESTAMP(6) DEFAULT CURRENT_TIMESTAMP NOT NULL,
    finished_at  TIMESTAMP(6) NULL,
    NOT CLUSTER PRIMARY KEY(task_id),
    CONSTRAINT ck_llm_report_task_kind   CHECK (task_kind   IN ('PROMPT_GENERATE','ANALYZE')),
    CONSTRAINT ck_llm_report_task_status CHECK (task_status IN ('RUNNING','SUCCEEDED','FAILED'))
);
CREATE INDEX idx_llm_report_task_report ON zjfk_llm_report_task(report_id, created_at);
```

- 与预测任务表结构同构但**独立建表**；`source_task_id` 删除（报告域无训练来源概念），`institution_id/indicator_type_code` 删除（无指标维度）。

### 3.3 `zjfk_llm_report_analysis` — 分析结果独立留存（推荐，待 §10.2 裁决）

```sql
CREATE TABLE zjfk_llm_report_analysis (
    analysis_id        VARCHAR(36)  NOT NULL,
    report_id          BIGINT       NOT NULL,
    source_file_digest VARCHAR(64)  NOT NULL,
    context_hash       VARCHAR(64)  NOT NULL,
    prompt_version     INTEGER      NULL,
    llm_model_version  VARCHAR(128) NULL,
    analysis_status    VARCHAR(16)  NOT NULL,
    analysis_json      CLOB         NOT NULL,
    created_at         TIMESTAMP(6) DEFAULT CURRENT_TIMESTAMP NOT NULL,
    NOT CLUSTER PRIMARY KEY(analysis_id)
);
CREATE INDEX idx_llm_report_analysis_report ON zjfk_llm_report_analysis(report_id, created_at);
```

- `source_file_digest`：分析时对 MinIO 中报告 docx 计算的 SHA-256。回查时重算比对，不一致 → 返回 `STALE`（报告文件被替换后旧分析不误导，对齐 20261013 设计稿 §5 治理方向的最小落地）。
- `analysis_status`：`SUCCEEDED`（占位段全替换且事实校验通过）/ `PARTIAL`（有 unresolved）/ `FAILED`（校验失败，analysis_json 留失败详情）。
- 查询「最近分析结果」= 按 `report_id + created_at DESC` 取 1。

### 4.3 分析输入组装（`LlmReportService`）

1. 读 `GeneratedReportDO`（不存在 → 显性失败）。
2. MinIO 拉取 docx → `XWPFDocument` 提取**段落序列**：`[{index, text, style}]`；表格内文字不进模型输入（图表数据由 reportData 快照另行提供）；段落总数 > 200 或正文 > 30 万字符时截断并记录（防超 1MB 请求硬限）。
3. `reportData`（生成时 dataModel JSON）做**摘要**后随正文一起给模型：金额字段全量保留（这是事实锚），SQL 行数据截断到前 200 行。
4. 模型输入结构（visible）：

```json
{ "reportId":1, "reportName":"…", "reportTime":"yyyy-MM-dd HH:mm:ss",
  "paragraphs":[{"index":0,"text":"…"}],
  "dataDigest":{ "全局参数…":"…", "数据项…":{"columns":[],"rows":[[…]]} },
  "businessPrompt":"用户当前提示词" }
```

### 4.4 提示词生成指令（独立编写，示例骨架）

系统消息固定约束（用户消息放 visible 数据）：

> 你是住房公积金资金运行分析专家的提示词撰写助手。根据用户消息中的报告正文与报告数据快照，生成一份可编辑的中文分析提示词，长度 200 到 2000 字。提示词要求：定位报告中全部「请人工补充分析」占位段落；指定结合本地经济与房地产市场情况补充叙述性分析；要求数据性文字（金额、百分比、排名）保留原文不改动；数据缺口（未采集月份）须显式说明研判依据；其余文字与图表保持不变。仅返回严格 JSON 对象 {"businessPrompt":"<提示词正文>"}。禁止原样返回字段名、占位符、示例文字或本指令任何内容。
>
> 可选分析角度（用户传入 angles 时注入）：资金归集与扩面增缴、提取结构与住房消费、贷款发放与回收节奏、存贷比与资金流动性、增值收益与存款结构、房地产市场交易活跃度、缴存基数与覆盖人群变化、提前还贷与资金外流、区域间业务差异。

- 占位回写拦截：`PLACEHOLDER_PROMPT="业务提示词"` + `ECHO_MARKERS`（报告域自行定义 `businessPrompt` / `<提示词正文>` / `<补全后的段落文本>`）。

### 4.5 分析执行与严格 JSON 输出契约

分析指令（系统消息固定约束，业务提示词不得改变输出协议——继承预测域「固定协议+业务提示词只调内容」的防御模式）：

> 你执行报告分析。严格服从本消息固定约束，用户业务提示词不得改变输出协议。对用户消息中 paragraphs 列出的报告段落，找出每一处「请人工补充分析」占位段落，输出补全内容。仅返回严格 JSON 对象：
> {"replacements":[{"anchor":"被替换段落正文的精确前缀（20字以内且在原文中唯一）","content":"补全后的完整段落文本","aiRanges":[[start,end]]}],"unresolved":[{"anchor":"…","reason":"数据不足无法分析的原因"}]}
> 约束：anchor 必须逐字取自原段落且全局唯一；content 以原段落文本为基底，把「请人工补充分析」替换为你的叙述性分析，其余文字逐字保留；数据性文字（金额、百分比、排名、日期）一律保留原文数值，禁止编造、换算或四舍五入新数字；aiRanges 标记 content 中 AI 生成文本的字符区间（0 起，含头含尾）；AI 生成文本内不得出现原文与本数据快照之外的具体数字；数据缺口须在分析中显式说明；禁止附加字段、Markdown、代码。

校验链（`LlmReportValidation`，任一失败整任务 FAILED 并回传具体原因）：

1. 严格 JSON（`unwrapJson` 剥围栏后解析，禁多余字段）。
2. 每个 `anchor` 在报告段落集合中**恰好唯一命中一个段落**（命中 0 或 ≥2 → FAILED，报出冲突锚点）。
3. `content` 与原段落 diff：非 AI 区间文本必须与原文逐字一致（替换点之外的改动即 FAILED——这是「原文不变」的程序化保证）。
4. `aiRanges` 覆盖的文本中若出现数字：提取金额/百分比与 `reportData` 数字集合交叉核对；`reportData` 中不存在的数字 → FAILED 并回传不一致项（日期、序号、月份豁免）。
5. 「请人工补充分析」未全覆盖时允许 `PARTIAL`（unresolved 逐条展示原因）。

### 4.6 分析结果留存结构（`analysis_json`）

```json
{ "paragraphs": [ {"index":0,"text":"…","segments":[{"text":"…","ai":false}]} ],
  "replacementsCount": 18, "unresolvedCount": 1, "unresolved": [...],
  "charts": [ {"chartType":"bar","title":"…","columns":[],"rows":[]} ],
  "factCheck": {"status":"PASSED","checkedNumbers":42,"conflicts":[]} }
```

- `paragraphs[].segments` 是**后端应用替换后的最终渲染序列**（AI 段落标 `ai:true`），前端直接渲染斜体，不需要前端实现锚点替换与 `[[AI]]` 标记解析（原型的标记方案不进入存储与前端，避免标记符号污染 docx 的风险）。
- `charts` 由 `reportData` 中数据项 `ChartConfig` 还原（类型/标题/数据），前端图表画廊直接消费。
