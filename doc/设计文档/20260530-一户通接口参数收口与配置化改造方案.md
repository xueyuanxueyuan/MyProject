# 20260530-一户通接口参数收口与配置化改造方案

## 1. 方案目标

针对当前一户通接口中暴露给业务侧的以下参数：

- 业务类型 / 交易代码
- 企业编码
- 费项代码 / 费项列表
- `dsjgbm`
- `processCode`

本方案目标是完成“业务入参收口”，把不属于业务语义的通道参数从外部 DTO 中逐步内收，改为由系统根据场景自动确定或配置化推导，避免业务侧承担一户通底层协议知识。

## 2. 当前问题

### 2.1 业务接口暴露了通道内部参数

当前多个 DTO 中把一户通内部参数直接暴露给业务侧，例如：

- `YhtRealtimeTradeReqDTO` 暴露 `tranCode`、`feeNo`
- `YhtBatchTradeReqDTO` 暴露 `bizType`、`feeNo`
- `PlQyJyReqDTO` 暴露 `dsjgbm`、`processCode`

这导致接口呈现出以下问题：

1. 业务方需要理解一户通协议细节。
2. 业务方无法判断参数是否正确。
3. 通道切换或规则调整时，外部调用方也被迫跟着改。
4. 一部分参数在系统内部本来已经固定，但仍以“必填外部入参”形式暴露。

### 2.2 当前代码已经部分呈现“内收”趋势

现有代码实际上已经说明，这些字段多数不应交给业务方：

1. `CorpNo` 来自配置项 `yht.caps.corp-no`。
2. 单笔实时交易 `tranCode` 由业务动作决定：
   - 单笔付款固定为 `20601`
   - 单笔收款固定为 `20602`
3. 实时与批量交易 `feeNo` 当前已经被系统默认写成 `00001`。
4. 批量交易 `bizType` 当前也已按场景固定为 `PAY` 或 `COLLECT`。

这说明，系统本身已经在做“参数内收”，只是外部接口契约还没有完全收干净。

## 3. 设计原则

### 3.1 业务入参只保留业务语义字段

业务入参应该只保留调用方真正理解且能准确提供的字段，例如：

- 业务流水号
- 经办机构
- 银行代码
- 账户信息
- 金额
- 摘要 / 备注
- 业务动作（签约 / 解约 / 代付 / 代收 / 批量查询）

### 3.2 通道参数全部内收

以下字段不应再由普通业务调用方直接维护：

- `corpNo`
- `tranCode`
- `bizType`
- `feeNo`
- `feeNoList`
- `dsjgbm`
- `processCode`

### 3.3 区分“固定值”和“配置值”

这些字段虽然都应内收，但来源不完全一样：

1. **固定值**：某接口在业务上天然唯一，例如某个业务动作只对应一个 `tranCode`。
2. **配置值**：某字段可能随渠道、机构、业务子类变化，应由配置表推导，而不是硬编码。
3. **状态回填值**：例如 `processCode`，只应由一户通返回后回写，不应作为业务发起入参。

## 4. 字段归属建议

### 4.1 企业编码 `corpNo`

**建议归属**：系统配置项

**处理方式**：

- 外部业务接口全部不再暴露
- 统一从 `yht.caps.corp-no` 读取
- 若未来存在多企业号场景，再扩展为“机构 -> 企业号”配置关系

### 4.2 业务类型 / 交易代码 `bizType` / `tranCode`

**建议归属**：由业务动作自动决定

**处理方式**：

- 单笔付款：系统内固定映射为 `20601`
- 单笔收款：系统内固定映射为 `20602`
- 批量付款：系统内固定映射为 `PAY`
- 批量收款：系统内固定映射为 `COLLECT`
- 协议上传 / 查询 / 对账 / 撤销等场景，同样通过内部枚举或映射器统一确定

**不建议**：

- 让业务方显式传 `20601`、`20602`、`PAY`、`COLLECT`

### 4.3 费项代码 / 费项列表 `feeNo` / `feeNoList`

**建议归属**：系统配置推导

**处理方式**：

- 若某接口场景在业务上只有唯一费项，则由系统固定
- 若不同机构 / 渠道 / 业务子类存在不同费项，则由配置表推导
- 不再让业务方直接传 `feeNo` 或 `feeNoList`

### 4.4 `dsjgbm`

**建议归属**：过渡期内部映射参数，长期应消失于业务接口

**处理方式**：

- 短期：不建议业务方填写，由系统根据配置表或机构规则自动带出
- 中期：把 `dsjgbm -> feeNoList` 静态映射改造成正式配置表
- 长期：若 `dsjgbm` 只是中间推导参数，则应只存在于系统内部，不再出现在业务 API 契约中

### 4.5 `processCode`

**建议归属**：状态回填字段

**处理方式**：

- 不再出现在业务发起请求 DTO 中
- 仅保留在：
  - 一户通响应 DTO
  - 协议主表 / 任务表
  - 补偿、查询、回执处理对象

## 5. 外部接口收口建议

### 5.1 一户通实时交易接口

当前问题：

- `YhtRealtimeTradeReqDTO` 暴露了 `tranCode`、`feeNo`

建议：

1. 新增面向业务的请求 DTO，例如：
   - `YhtRealtimePayBizReqDTO`
   - `YhtRealtimeCollectBizReqDTO`
2. 外部不再传：
   - `tranCode`
   - `feeNo`
3. 服务层根据调用入口自动补：
   - `tranCode`
   - `feeNo`
   - `corpNo`

### 5.2 一户通批量交易接口

当前问题：

- `YhtBatchTradeReqDTO` 暴露了 `bizType`、`feeNo`

建议：

1. 拆分为两个业务入口：
   - 批量付款发起
   - 批量收款发起
2. 外部不再传：
   - `bizType`
   - `feeNo`
3. 服务层按入口自动补：
   - `bizType`
   - `feeNo`
   - `corpNo`

### 5.3 批量签约 / 解约接口

当前问题：

- `PlQyJyReqDTO` 暴露了 `dsjgbm`、`processCode`

建议：

1. `processCode` 从请求 DTO 中删除
2. `dsjgbm` 从业务 DTO 中删除，改为系统根据：
   - 渠道
   - 机构
   - 业务子类型
   自动推导
3. 若短期无法立即删除，可先改为：
   - 非必填
   - 文档标注“内部参数，业务侧无需传”

## 6. 内部实现建议

### 6.1 新增统一参数解析层

建议新增一层统一的“一户通场景参数解析器”，例如：

- `YhtSceneParamResolver`

职责：

1. 根据业务动作识别场景
2. 推导 `corpNo`
3. 推导 `tranCode`
4. 推导 `bizType`
5. 推导 `feeNo / feeNoList`
6. 兼容过渡期 `dsjgbm`

### 6.2 建立正式配置表

建议新增配置表，至少维护如下关系：

| 字段 | 含义 |
|------|------|
| `scene_code` | 场景编码，如实时付款、实时收款、批量付款、批量收款、批量签约 |
| `jsqd` | 结算渠道 |
| `jbjgbh` | 经办机构编号，可为空表示全局 |
| `biz_sub_type` | 业务子类，可为空 |
| `corp_no` | 企业编码 |
| `tran_code` | 交易代码 |
| `biz_type` | 一户通业务类型 |
| `fee_no` | 费项代码 |
| `fee_no_list` | 费项列表 |
| `dsjgbm` | 代收机构编码 |
| `enabled` | 是否启用 |

### 6.3 参数优先级

建议统一优先级如下：

1. 场景级显式配置
2. 机构级配置
3. 渠道级默认配置
4. 系统内硬编码兜底

过渡期允许保留硬编码兜底，但必须有日志告警。

## 7. 分阶段实施计划

### 阶段一：先收口文档与校验

目标：

- 不改动主流程行为，先减少误导

建议动作：

1. 在 Swagger 文档中标注：
   - `dsjgbm` 为内部参数，业务侧无需填写
   - `processCode` 为状态字段，请求侧无须填写
2. 对明显已固定的字段去掉“外部必填”要求
3. 为过渡期保留字段增加兼容日志

### 阶段二：新增内部解析层

目标：

- 不再让 Controller 直接信任外部传入的通道参数

建议动作：

1. 增加 `YhtSceneParamResolver`
2. 在服务层统一补齐：
   - `corpNo`
   - `tranCode`
   - `bizType`
   - `feeNo / feeNoList`
3. 将硬编码集中，避免散落多处

### 阶段三：清理外部 DTO

目标：

- 完成业务接口契约收口

建议动作：

1. 从业务请求 DTO 中移除：
   - `processCode`
   - `tranCode`
   - `bizType`
   - `feeNo`
2. 将 `dsjgbm` 改为内部字段或彻底移除
3. 保留兼容版本接口一段时间，输出废弃告警

### 阶段四：配置化替代硬编码

目标：

- 替换当前静态映射和默认值

建议动作：

1. 上线正式配置表
2. 用配置表替换：
   - `corp-no` 单值依赖
   - `feeNo = 00001` 静态写死
   - `dsjgbm -> feeNoList` 静态 Map
3. 增加配置缺失检测与启动校验

## 8. 验证要点

实施后应重点验证以下内容：

1. 外部业务调用方在不传通道参数时，链路仍可正常发起
2. 实时付款 / 收款场景自动落入正确 `tranCode`
3. 批量付款 / 收款场景自动落入正确 `bizType`
4. `CorpNo` 统一来自配置或配置表
5. `feeNo / feeNoList` 不再依赖业务方输入
6. `processCode` 仅在响应与状态回写链路出现

## 9. 最终结论

当前一户通接口的主要问题，不是“字段不够”，而是“把系统内部通道参数暴露成了业务参数”。

本次建议的核心，不是简单删字段，而是建立明确的分层：

1. **业务层**：只表达业务动作和业务数据。
2. **通道适配层**：负责推导一户通参数。
3. **配置层**：负责维护企业编码、费项、业务类型等映射关系。
4. **状态层**：负责承接 `processCode` 等通道返回状态。

按此方案推进后，一户通接口会更符合业务认知，也更利于后续切换正式配置与多机构扩展。
