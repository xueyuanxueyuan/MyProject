# 20261016 多智能体协同编排系统设计方案

> 版本：V1.0 ｜ 日期：2026-10-16 ｜ 状态：待评审
> 关联：`AGENTS.md`、`doc/项目规范/统一主规则-通用工具链接入说明.md`、`doc/技能库/技能索引.md`、`doc/记忆库/决策记录/000-架构与工具决策.md`

## 1. 背景与目标

### 1.1 背景

Gjj 工作区已存在多种 AI 代理形态：主会话代理（WorkBuddy / Codex）、可派发的专业子代理（Explore、Plan、general-purpose、doc-*、sheet-agent 等）、专家中心领域专家（数量以实时清单为准）、项目技能库（61 个，以技能索引为准）。当前协同行为由 `AGENTS.md` 入口 + 三省六部工作流 + 共享任务板 + 消息机制 + 三层记忆承载，但缺少一份统一的「代理协同方案」，把角色分工、任务生命周期、交接协议、质量门禁、记忆规则与错误处理固化为可复用、可审计的规范。本方案补上这一层。

### 1.2 目标

1. **统一入口与路由**：任何实质任务先经编排者判定再派发，禁止绕过编排直接开工。
2. **角色单一职责**：编排者只做路由 / 跟踪 / 汇报，执行者不自行变更任务状态。
3. **交接自包含**：每次交接消息必须包含五要素（见 5.2），接收方无需翻历史即可动手。
4. **质量门禁前置**：无证据不交付；失败有界、可恢复、可升级。
5. **记忆分层且事实源唯一**：`doc/记忆库` 为长期事实源（ADR-0001），跨代理可继承。

### 1.3 适用范围与假设

- 假设 1：协同主体为当前环境内的代理（主会话 + Agent 工具子代理 + 专家中心专家 + 技能），星型拓扑（单编排者、多执行者）。
- 假设 2：跨机器 / 跨工具的代理注册发现（平台化编排服务）不在本期范围，仅作为演进方向（见第 10 节 P3）。
- 未验证项：外部自建代理的接入方式；待用户确认（见第 12 节）。

## 2. 总体架构：四层 + 横切门禁

```text
┌──────────────────────────────────────────────────────────────┐
│ L0 接入层    AGENTS.md 统一入口 · 用户请求接入                  │
├──────────────────────────────────────────────────────────────┤
│ L1 编排层    太子 → 中书省 → 门下省 → 尚书省 → 翰林院            │
│              (判定)   (拆解)   (审议)   (派发)   (汇总)          │
├──────────────────────────────────────────────────────────────┤
│ L2 执行层    六部：吏(技能/记忆) 户(工具链) 礼(文档)             │
│              兵(构建/发布) 刑(质控) 工(编码)                    │
│              ＋ 专业子代理（隔离上下文执行）＋ 领域专家           │
├──────────────────────────────────────────────────────────────┤
│ L3 支撑层    任务板 TaskList · 消息 SendMessage · 三层记忆      │
│              技能库(61) · 质量门禁脚本 · 自动化 automation      │
├──────────────────────────────────────────────────────────────┤
│ 横切门禁（适用于所有层）                                        │
│   防偷懒防撒谎 anti-laziness-anti-hallucination                │
│   ＋ 交付验证 verification-before-completion（无证据不报喜）    │
└──────────────────────────────────────────────────────────────┘
```

设计原则：

1. **单一入口**：所有实质任务经 `AGENTS.md` 进入，编排者独占路由权。
2. **编排与执行分离**：编排者不「顺手干活」——一旦亲自执行，即失去对全局的跟踪（agent-team-orchestration 技能将此列为头号反模式）。
3. **状态显式**：任务板是唯一状态源；状态转移只能由编排者执行并留痕。
4. **证据驱动**：每个「完成」声明必须附可复核的验证证据。
5. **并行有度**：仅无依赖子任务并行；并行结果必须由编排者复核后才计入完成。
6. **失败有界**：重试有上限、升级有路径，禁止无声卡死与假装完成。

## 3. 角色与职责矩阵

| 角色 | 职责 | 输入 | 输出 | 禁做 |
|---|---|---|---|---|
| 编排者（Orchestrator） | 路由、状态跟踪、优先级裁决、汇总汇报 | 用户请求 | 派发单、状态更新、最终报告 | 亲自执行实现 |
| 太子（edict-triage） | 意图判定（闲聊/正式）、技能路由、报告格式编排 | 用户消息 | 👑 太子批复块、路由建议 | 跳过判定直接开工 |
| 中书省（edict-planning） | 拆解 ≥3 步可验证子任务 | 判定后的任务 | 任务清单（落盘任务板） | 无验收证据的空计划 |
| 门下省（edict-review） | 规则 / 记忆 / 技能 / 风险审议 | 计划清单 | 🛡️ 审议结论（通过 / 驳回 + 理由） | 低风险时中断等待用户 |
| 尚书省（edict-dispatch） | 匹配六部与工具、控制并行、跟进度 | 批准的计划 | 🐎 派发清单、进度更新 | 自行生成最终报告 |
| 六部（吏/户/礼/兵/刑/工） | 技能记忆 / 工具链 / 文档 / 构建发布 / 质控 / 编码 | 派发单 | 产物 + 验证证据 | 越部抢活、自行标记完成 |
| 专业子代理 | 隔离上下文执行专项（探索 / 规划 / 表格 / 文档 / 工程） | 自包含派发 prompt | 结果回传（含路径与验证方式） | 直接面向用户汇报 |
| 刑部 / 质检 | 独立验证产物与完成声明 | 产物 + 完成声明 | PASS / FAIL + 证据 | 证据不足时默认放行 |
| 翰林院（edict-hanlin） | 汇总执行结果为报告正文 | 各部结果 | 📚 汇总内容 | 绕过太子直接呈报 |

## 4. 任务生命周期（状态机）

```text
[Inbox 提交]
     │
     ▼
[Triaged 太子判定] ──闲聊──→ [直接回复，不进流水线]
     │ 正式任务（G1 门禁）
     ▼
[Planned 中书省拆解]
     │ 计划产出（G2 门禁）
     ▼
[Reviewed 门下省审议] ──驳回──▶ 回到 [Planned 中书省拆解] 重新拆解
     │ 通过（G3 门禁）
     ▼
[Dispatched 尚书省派发]
     │
     ▼
[In Progress 执行中] ⇄ [QA/刑素质检] ──PASS（G5 门禁）──→ [Reported 翰林院汇总] → [Done]
     ▲                      │
     └────FAIL（≤3 次）──────┘
                            │ 第 3 次仍失败
                            ▼
                    [Blocked 升级上报用户]（合法终态，记录原因）
```

流转规则：

1. 状态转移只能由编排者执行；每次转移留痕（谁、做了什么、为什么）。
2. `Failed` / `Blocked` 是合法终态：记录原因后放行，禁止假装完成。
3. 执行代理必须在「开始 / 阻塞 / 交接 / 完成」四个节点留评论；静默超过预期视为卡住，由编排者介入（silent agent = stuck）。
4. 质检不通过时回退执行并附具体反馈；同一任务最多 3 次尝试。
5. 审议驳回后回到中书省重新拆解（edict-review：不合规当即驳回，要求重新生成计划），驳回原因随回退消息传递。

状态命名映射：本文九态是 agent-team-orchestration 技能五态（Inbox → Assigned → In Progress → Review → Done | Failed）的编排期细化——Inbox=Inbox；Assigned 细分为 Triaged / Planned / Reviewed / Dispatched；In Progress=In Progress；Review=QA；Done=Done；Failed / Blocked 为合法终态。三者语义兼容：编排者独占状态转移、转移留评论、Failed 合法终态均保留。

图注：G4（破坏性操作前）与 G6（每次修改后）为执行期横切门禁，不是状态转移点，故不在状态机图中标注。

## 5. 通信与交接协议

### 5.1 消息类型

| 类型 | 方向 | 必载荷 |
|---|---|---|
| task_assign | 尚书省 → 六部 / 子代理 | 任务 ID、目标、上下文、产物路径、验收标准、约束 |
| status_update | 执行 → 尚书省 | 进度、阻塞点、已有证据 |
| review_request | 尚书省 → 门下省 | 计划 / 差异、风险清单 |
| review_verdict | 门下省 → 尚书省 | 通过 / 驳回 + 理由 |
| qa_report | 刑部 → 尚书省 | PASS / FAIL + 证据 + 修复反馈 |
| escalation | 任何角色 → 编排者 / 用户 | 阻塞描述、已尝试次数、可选方案 |
| completion | 翰林院 → 用户 | 摘要、交付物、验证证据、遗留风险 |

### 5.2 自包含交接五要素

1. **做了什么**——变更 / 产出摘要；
2. **产物在哪**——精确文件路径；
3. **如何验证**——可执行的命令或验收口径；
4. **已知问题**——未完成部分与风险点；
5. **下一步**——接收方的明确动作。

反例：「完成了，看文件吧。」
正例：「产物在 `doc/设计文档/20261016-多智能体协同编排系统设计方案.md`；运行 `grep -c '^## ' <file>` 可核对章节完整性；已知问题：第 12 节三项待用户确认；下一步：门下省审议合规性。」

### 5.3 广播纪律

- broadcast 仅用于全员阻塞级通知（例：「停止当前工作，发现阻塞级缺陷」）。
- 常规进度走 DM + 任务板评论，避免消息过载。
- broadcast 成本随接收方数量线性增长，非必要不使用。

## 6. 质量门禁（六道）

| 门禁 | 时点 | 通过条件 |
|---|---|---|
| G1 入口门禁 | 任务进入 | 太子完成意图判定 + 技能路由，未判定不开工 |
| G2 计划门禁 | 拆解后 | ≥3 个可验证子任务落盘，每步写明完成证据 |
| G3 审议门禁 | 执行前 | 规则 / 记忆 / 技能 / 风险审查通过；高风险操作用户批准 |
| G4 执行门禁 | 破坏性操作前 | dry-run / scan-only 先行；备份优先；影响范围已确认 |
| G5 交付门禁 | 宣告完成前 | verification-before-completion：真实命令 + 输出核对 + 失败数清点 |
| G6 回归门禁 | 每次修改后 | 既有通过项仍通过；无新增 lint / 类型错误；签名兼容 |

## 7. 记忆与知识管理

三层记忆 + 唯一事实源：

| 层 | 位置 | 范围 | 写法 |
|---|---|---|---|
| L1 云端画像 | 服务端注入 | 跨项目用户画像 | 本地只读，服务端维护 |
| L2 用户级 | 用户目录 `MEMORY.md` | 跨项目显式规则 | 用户明确要求时写入 |
| L3 工作区 | `.workbuddy/memory/YYYY-MM-DD.md` + `MEMORY.md` | 本项目 | 日志只追加；MEMORY.md 精选 ≤3000 字 |
| 事实源 | `doc/记忆库` | 跨代理长期事实 | ADR-0001；RAG / 向量库仅作可重建加速层（ADR-0002 / 0003） |

写入规则：沉淀稳定约束、已验证决策、跨会话结论、易踩坑问题；禁止写入密钥 / Token / 连接串、未验证猜测、大段原始日志、一次性临时进度。30 天以上日志蒸馏进 `MEMORY.md` 后清理。

## 8. 错误处理与恢复

| 故障 | 策略 |
|---|---|
| 子代理派发失败 | 重试 ≤2 次 → 记录 → 换类型或人工兜底 |
| 任务执行失败 | ≤3 次重试且每次带质检反馈；第 2 次失败换实现方案；第 3 次失败标记 Blocked 并升级，流水线其余任务继续 |
| 质检失败 / 证据不足 | 默认不通过（安全侧优先）；证据不清时复测而非放行 |
| 代理静默 | 视为卡住，编排者主动介入 |
| 高风险 / 不可逆操作 | 执行前完整列表 + 用户确认；批量操作分批确认 |
| 派发前能力不熟 | 先核证代理能力再派活（例：浏览器类任务派给无浏览器代理必然失败） |

## 9. 环境能力映射（当前可用）

| 协同能力 | 当前实现 |
|---|---|
| 统一入口 | `AGENTS.md` + 调度达专家（agent-orchestrator） |
| 任务板 | TaskCreate / TaskUpdate / TaskList（团队模式跨代理共享） |
| 消息 | SendMessage（DM / broadcast）、频道 |
| 子代理派发 | Agent 工具（以当前会话工具注册表实测为准）：general-purpose、Explore、Plan、sheet-agent、doc-converter、doc-formatter、doc-writer、engine-capabilities、agent-orchestrator |
| 领域专家 | 专家中心（按会话选择，数量以实时清单为准） |
| 技能 | Skill 工具（市场技能）+ `doc/技能库` 61 个（Read SKILL.md 使用） |
| 记忆 | 云端画像 + conversation_search + 用户级 / 工作区 MEMORY.md + `doc/记忆库` |
| 自动化 | automation_update（一次性 / 周期） |
| 可视化与交付 | show_widget（内联图）/ present_files（文件交付） |

计数口径说明：技能数取 `doc/技能库/技能索引.md` 自称的 61；`AGENTS.md` 三处记 56、磁盘实有 62 个技能目录（serena 未入索引），三者差异已在第 11 节「技能 / 专家版本漂移」风险行覆盖，待同步。

**差异说明（如实）**：专家目录中的 ArchitectUX、EvidenceQA、testing-reality-checker 等专职代理在当前环境不在可派发子代理清单内，不能直接 spawn。本方案以可用子代理类型等价替代（架构 / 计划 → Plan 或 general-purpose；质检 → 独立 general-purpose 子代理），并以角色规范约束主代理行为。这是本方案与专家目录宣传能力之间的实际差异；后续环境开放相应代理类型时，只需更新本节映射，架构不变。

## 11. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 上下文爆炸 | 子代理隔离上下文 + 摘要交接，主代理不背全量细节 |
| 门禁形式化 | 证据强制 + 守卫脚本扫描 + 无验证不报喜 |
| 消息过载 | broadcast 纪律 + 状态走任务板 |
| 记忆污染 | 写入规则 + 定期蒸馏 + 敏感信息禁令 |
| 技能 / 专家版本漂移 | 以 `doc/技能库/技能索引.md` 为索引主源，定期核对 |
| 单点编排者故障 | 状态在任务板 / 文件可恢复；失败任务有界 |
| 并行结果未复核 | 并行后必须由编排者复核实际改动再计完成 |
