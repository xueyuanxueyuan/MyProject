## 3. 数据库设计原则

### 3.1 当前阶段原则

1. **文档先行**：任何表结构执行前必须先有数据库设计文档和 DDL 草案。
2. **不默认改库**：普通本地开发阶段不得默认执行 DDL。
3. **兼容优先**：若原系统已有表承载同类业务，应先评估复用、视图适配、影子表或迁移表方案。
4. **字段可追溯**：领域模型字段、持久化对象字段、数据库列必须有映射表。
5. **审批执行**：建表、改表、删表、迁移历史数据必须经过用户明确授权和 DBA/项目评审。
6. **回滚可控**：任何 DDL 必须配套回滚方案或说明不可逆原因。

### 3.2 命名原则

| 类型 | 推荐规范 | 当前代码情况 | 后续建议 |
| --- | --- | --- | --- |
| 业务表 | `zjjs_业务域缩写_业务名拼音缩写`，例如 `zjjs_zj_zz`、`zjjs_zh_zhxx` | 当前部分 Mapper 引用了 `transfer/account/voucher/recon` 等英文表名 | 正式 DDL 和后续 Mapper 整改必须改为拼音缩写表名 |
| 主键 | `id` | 当前 Entity 均有 `id` | 建议 BIGINT，自增或序列 |
| 业务编号 | 拼音缩写，如 `ywslbh`、`pzbh`、`dzbh` | 已采用 | 应建唯一索引 |
| 金额 | `DECIMAL(18,2)` | Java 使用 BigDecimal | 精度需由财务规则确认 |
| 状态 | `zt` 或拆分具体状态 | 当前统一 `zt` | 批次/结果类建议拆分办结状态与结果状态 |
| 时间 | `cjsj`、`gxsj` | 当前 Mapper 仍引用 `created_time`、`updated_time` | 正式 DDL 建议使用拼音缩写；代码整改时同步调整 Mapper/DO |
| 持久化对象 | `XxxDO` | 当前为 `XxxEntity` | 建议后续重命名 |

## 8. DDL 草案生成原则

本文档不直接给出可执行 DDL，原因：

1. 未确认这些表是新建、复用原表还是只作影子表。
2. 未连接测试库核验现有结构。
3. 未评审字段长度、索引命名、序列/自增策略、达梦兼容语法。
4. 凭证、账户、对账等模块与原系统主数据/财务数据关系复杂，不能按当前骨架直接建表。

后续如需产出 DDL，应按以下流程：

1. 确认目标数据库类型和 schema。
2. 查询现有表结构。
3. 与原系统 DO/Mapper/XML 对比字段。
4. 决策：复用原表 / 新建 v3 表 / 影子表 / 视图适配。
5. 生成达梦 DDL 草案。
6. 生成回滚脚本或不可逆说明。
7. 测试库执行验证。
8. 发布检查单登记。

## 9. 迁移与兼容风险

| 风险 | 影响 | 建议 |
| --- | --- | --- |
| 新表与原表并存造成口径不一致 | 业务流水、凭证、账户可能分裂 | 优先建立原系统表映射矩阵，再决定是否新建 |
| 当前 Mapper 使用 `SELECT *` | 字段变更容易引入隐性映射问题 | 改为显式字段列表 |
| 当前 Mapper 使用 `NOW()` | 达梦兼容性不确定 | 改为 Java 侧传入时间或使用达梦兼容函数 |
| 缺少唯一索引 | 重试可能重复写业务流水 | `ywslbh`、`pzbh`、`dzbh`、`zhbh` 建唯一索引 |
| 缺少批次表 | 批量业务不可审计、不可重试 | 先补批次数据库设计 |
| 凭证表字段过少 | 无法替代原会计凭证体系 | 凭证模块单独建模，不按骨架表直接执行 |
| Entity 命名不清 | 领域对象与持久化对象混淆 | 后续改名为 DO 或建立专用 persistence 包 |

## 10. 后续门禁

从本文档生效后，v3 后续开发涉及数据库时必须满足：

1. **新增 Mapper 前**：必须先在本文档或新增数据库设计文档中登记表与字段。
2. **新增字段前**：必须同步更新领域模型、持久化对象、Mapper SQL、映射表和测试。
3. **执行 DDL 前**：必须获得明确授权，并提供执行脚本、回滚脚本和验证 SQL。
4. **声称已改库前**：必须提供真实执行日志或数据库查询结果。
5. **不能确认时**：必须明确写“未连接数据库确认”或“仅代码侧假设”。

## 11. 本次补充文档结论

1. 前期 v3 重构确实已经重新抽象了一批持久化对象和 Mapper。
2. 这些对象目前是代码侧的持久化模型，不等同于真实数据库已经重设计。
3. 当前缺失正式数据库设计、DDL 草案、原系统表映射矩阵和迁移方案。
4. 后续可以继续按计划开发，但数据库相关开发必须先补设计与映射，避免代码侧模型脱离真实库结构。
5. 若下一阶段继续推进，建议优先做“原系统表结构/DO/Mapper 与 v3 模型映射矩阵”，再决定 v3 是复用原表、建影子表还是做迁移表。
