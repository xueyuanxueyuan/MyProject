# 资金风控模型连接：取消内外网判定与密钥托管（内网项目口径）

日期：2026-10-23。覆盖 `20261014-资金风控通用大模型连接配置首批实现说明.md` 的二分判定，并覆盖本文档第一版"内部域白名单 + master-key 加密"方案。

## 0. 最终口径（2026-10-23 二次调整，以此为准）

项目定位为**内网项目**，对外边界由**统一认证 + 网关**承担，模型全部为内网部署的私有大模型。因此：

| 项 | 最终处理 |
|---|---|
| `zjfk.llm.master-key` | **删除**，不再要求配置，不再有"密钥托管未启用" |
| `zjfk.llm.internal-domains` | **删除**，不再做内部域白名单 |
| `zjfk.llm.free-chat-external-enabled` | **删除**，不再有公网自由对话开关 |
| 地址校验 | 仅校验 `http/https` 协议 + 含 host；不限域名、端口、地址段、路径 |
| DNS 解析检查 | **删除**，不再做公网/私网解析判定 |
| API 密钥 | **选填**，页面填什么就存什么（明文存 `api_key_cipher` 列，不改 DDL），有值就带 `Authorization: Bearer` |
| 连接测试 30 秒冷却 | **删除**，对话与测试不再被限流 |
| 规则训练/预测链路 | 同步放开，不再要求 RFC1918 + 免密，有密钥即带认证头 |

保留的最小限制仅为**数据格式校验**（非安全限制）：供应商/模型名正则、测试参数范围、消息角色与长度、响应体大小。

> 安全边界：应用层不再承担网络出域控制，由网关与统一认证负责；前后端传输脱敏仍按项目统一规范执行。数据库 `api_key_cipher` 列现存明文，列名沿用以免触发 DDL 变更。

日期：2026-10-23。覆盖 `20261014-资金风控通用大模型连接配置首批实现说明.md` 中"公网 HTTPS 必带密钥 / 内网 http 免密"的二分判定。

## 1. 问题

原实现用协议判定内外网与认证方式：

| 原判定 | 位置 | 结果 |
|---|---|---|
| `internal = baseUrl.startsWith("http://")` | `LlmModelConfigServiceImpl.save/test/chat` | HTTPS 一律当公网 |
| `internal && apiKey 非空` → 抛错 | `save()` | HTTPS 内部模型无法提交密钥 |
| 非 internal 必走 `encryption()` | `save()/test()/chat()` | 未配 `ZJFK_LLM_MASTER_KEY` 即抛"模型配置密钥托管尚未启用" |
| `!internal && !externalChatEnabled` → 拒绝 | `chat()` | HTTPS 内部模型被公网自由对话开关误拦 |
| `validatePublicResolution` 拒绝私网解析 | `test()/chat()` | 内部域名解析到私网时被拦 |

现场故障：`POST /api/v1/zjfk/llm-config/save` 报"模型配置密钥托管尚未启用"，即内部自建模型 `https://api.capinfo.com.cn/v1`（带密钥）被误判为公网连接。

## 2. 改造原则（第一版，已被第 0 节覆盖）

认证方式由"是否提交 API 密钥"决定，网络域由"内部域白名单"决定，二者都不再由 http/https 协议推断。

| 连接形态 | 判定 | 密钥存储 | 对话开关 |
|---|---|---|---|
| `http://` + 私有 IPv4 | 内部（免密） | 密文为 NULL；提交密钥直接拒绝 | 不受公网开关限制 |
| `https://` + 内部域 + 密钥 | 内部（带密钥） | AES-GCM 加密，需 master-key | 不受公网开关限制 |
| `https://` + 内部域 + 无密钥 | 内部（免密） | 密文为 NULL | 不受公网开关限制 |
| `https://` + 非内部域 + 密钥 | 公网（带密钥） | AES-GCM 加密，需 master-key | 受 `free-chat-external-enabled` 限制 |
| `https://` + 非内部域 + 无密钥 | 公网（缺密钥） | — | 保存即拒绝 |

## 3. 代码改动（第一版记录，最终实现见第 0 节）

- `mxgl/security/LlmConnectionSecurity.java`
  - 新增 `isInternalEndpoint(endpoint, internalDomains)`：`http://` 直接视为内部；HTTPS 按 host 与后缀白名单匹配（`equals` 或 `.suffix`，防 `capinfo.com.cn.evil.com` 绕过）。
  - `validatePublicResolution(endpoint)` → 保留为 `validateResolvedAddress(endpoint, false)` 的兼容包装。
  - 新增 `validateResolvedAddress(endpoint, internalDomain)`：内部域允许解析到私网地址，但仍拒绝回环 / 任意地址 / 链路本地 / 组播；非内部域保持原严格公网要求。
- `mxgl/service/impl/LlmModelConfigServiceImpl.java`
  - 构造器新增 `@Value("${zjfk.llm.internal-domains:capinfo.com.cn}")`，保留两参构造器供单测与兼容。
  - `save()`：`plainHttp + 密钥` 拒绝（密钥不得明文出网）；`非内部域 + 无密钥` 拒绝；内部域 HTTPS 允许带密钥。
    - 更新分支：有密钥 → 加密覆盖；`http://` 免密 → 显式清空历史密文；内部域 HTTPS 留空 → 保留原密文（不轮换）。
  - `test()/chat()`：Authorization 由 `apiKeyCipher != null` 决定；一致性校验改为"明文 HTTP 不得带密钥"与"非内部域必须有密钥"；`chat()` 的公网开关只拦非内部域。
  - `list()`：`secretConfigured` 改为取 Mapper 派生列，不再由协议推断。
- `mapper/mxgl/LlmConnectionMapper.xml`：`listConnections` 增加 `CASE WHEN api_key_cipher IS NULL THEN 0 ELSE 1 END AS secret_configured`，仍不返回密文。
- `LlmConnectionDO`：新增只读派生字段 `secretConfigured`。
- `application.yml`：新增 `zjfk.llm.internal-domains`（默认 `capinfo.com.cn`，可用 `ZJFK_LLM_INTERNAL_DOMAINS` 覆盖）。
- 前端 `LlmConnectionPanel.vue`：密钥输入框常显；`http://` 时提示留空；保存不再强制清空内部连接密钥。

## 6. 规则运行兼容思考型模型（2026-10-23 12:2x）

**现象**：规则任务失败，错误 `模型未返回严格规则JSON`，但日志显示请求已发出、`httpStatus` 正常。落库的响应摘要为：

```json
{"object":"chat.completion","model":"Qwen3.8-27B-Capinfo",
 "choices":[{"index":0,"message":{"role":"assistant","content":null,"reasoning_content":"..."}}]}
```

**原因**：`Qwen3.8-27B-Capinfo` 为思考型模型，输出先进入 `reasoning_content`。规则链路默认 `max_tokens=1024` 在思考阶段即耗尽，`content` 始终为 `null`（`finish_reason=length`），不是网关拦截，也不是没有外呼。

**修复**（`LlmRuleProposalClient`、`LlmModelConfigServiceImpl`、`LlmPredictionModelClient`）：

| 项 | 处理 |
|---|---|
| 默认 `max_tokens` | 1024 → **8192**，给思考阶段留出空间 |
| `content` 为空 | 回退从 `reasoning_content` 中抽取 JSON 块（优先 `{"rules"` 起点），抽取结果仍走严格规则校验 |
| 连通测试 | `reasoning_content` 有文本也算 `formatValid=true`，不再误判格式无效 |
| 预测链路 | 同样支持 `reasoning_content` 回退 |
| 关闭思考 | 任务参数 `sampling` 中可传 `enable_thinking`，透传为 `chat_template_kwargs.enable_thinking` |
| 可观测 | 失败信息带 `finishReason` 与响应摘要，直接落库并在页面错误栏展示 |

**说明**：若任务参数显式指定了较小的 `max_tokens`，仍以任务参数为准；此时若思考未完成，错误会显示 `finishReason=length`，需调大该值或关闭思考。

### 6.1 内置提示词与数据格式（2026-10-23 12:3x 定稿）

发给模型的请求固定为两条消息：

| 角色 | 内容 |
|---|---|
| `system` | `LlmRuleProposalClient.INSTRUCTION`（内置固定，不允许页面覆盖） |
| `user` | 候选 `promptTemplate` + `\n` + 可见数据 JSON + `\n/no_think` |

`system` 提示词正文：

```text
/no_think
You are a forecasting-rule selector. Output exactly ONE JSON object and nothing else.
Output schema: {"rules":[{"strategy":"SEASONAL_NAIVE","window":12,"trendWeight":0}]}
Hard requirements:
1. The top level has exactly one key: "rules". No other keys.
2. "rules" is an array of 1 to 6 objects.
3. Each object has exactly three keys: strategy, window, trendWeight.
4. strategy must be one of: SEASONAL_NAIVE, MOVING_AVERAGE, SEASONAL_TREND.
5. window is an integer from 1 to 24. For SEASONAL_NAIVE and SEASONAL_TREND, window must be 12.
6. trendWeight is a number from -1 to 1 with at most 8 decimal places. For SEASONAL_NAIVE and MOVING_AVERAGE, trendWeight must be 0.
7. Use only the training history and optional validation feedback provided in the user message.
8. Do NOT output markdown code fences, comments, explanations, or any text before or after the JSON.
9. Do NOT think step by step. Your answer must start with { and end with }.
```

`user` 消息中的可见数据 JSON 结构：

```json
{
  "training": [{"month": "2020-01", "value": 123456.78}, ...],
  "validationFeedback": {"validationSelection": ["SEASONAL_NAIVE", "MOVING_AVERAGE"]},
  "seedRule": {"strategy": "SEASONAL_NAIVE", "window": 12, "trendWeight": 0}
}
```

- `training`：最近 24 个月的 `{month: yyyy-MM, value: 数值}`，按时间升序。
- `validationFeedback`：首轮为 `null`，后续轮次为上一轮验证选中的策略列表。
- `seedRule`：仅 `mode=CONTINUE` 时出现，`OVERWRITE` 时不出现。
- 审计字段（`previousArtifact`、`executionJson`、完整 config）不会进入模型可见数据。

配套调整：`max_tokens` 前端上限 4096 → 16384、默认 2048 → 4096；后端候选参数校验与连接测试同步放宽；`sampling` 允许 `enable_thinking` 布尔字段并透传为 `chat_template_kwargs`。

## 7. 基础预测链路：去掉登录身份校验与数据集白名单配置（2026-10-23 13:4x）

### 7.1 问题

现场用真实账号通过统一认证登录后，基础预测页仍报两类错误：

- `无当前机构的精确授权`
- `来源不可用或数据集未声明元单位，请核实源单位后配置prediction-yuan-dataset-ids`

数据库实证（红顺公积金 `172.20.116.25:5236` / `CAP_GJJ_ZJFK`）：规则任务 `36e60640-...` 已 `SUCCEEDED` 且有制品，候选 `154b412f-...` 已 `CANDIDATE`，数据集 `id=2`（机构 `370400000000000`、`jcje`、ready、120 条）——数据侧完全就绪，卡在两道纯代码校验上。

### 7.2 两道校验为什么不合理

| 校验 | 代码 | 问题 |
|---|---|---|
| 机构授权 | `authorize()` 要求 `identity.orgCodes().contains(institution)` | `orgCode` 与前端传入的 `institutionId`（如 `370400000000000`）不是同一套编码，天然对不上；`currentIdentity()` 还要求 `InnerUserOrgs` 非空，统一认证上下文缺字段即失败 |
| 操作员归属 | `sources()/freeze()` 要求 `identity.username().equals(task.getCreatedBy())` | 规则任务由内部程序以 `auto` 身份创建，与 `authorize()` 又拒绝 `auto` 身份自相矛盾，形成死锁：`auto` 建的任务永远不能作为预测来源 |
| 数据集白名单 | `zjfk.llm.prediction-yuan-dataset-ids` | 训练来源的有效性本就由规则任务 SUCCEEDED + 制品 + 数据集状态/机构/指标一致性保证，再让运维手工维护一份 ID 白名单属于重复且易错配置 |

### 7.3 改动

`LlmPredictionService`：

- 删除 `Identity` record、`currentIdentity()`、`parseYuanDatasets()`、`yuanDatasets`、`identities`，以及 `AuthTools` / `CurrentUser` / `InnerUser` / `StpUtil` / `RequestContextHolder` / `@Value` 相关 import 与构造参数。
- `authorize()` → `checkIndicator()`：只保留指标白名单（`jcje/tqje/dkff/dkhs`），不再校验登录身份与机构。
- `sources()`：只按 `indicatorCode` 匹配 + 候选未停用 + 任务 `SUCCEEDED` 过滤；`freeze()` 仍对每个候选做完整校验（候选/任务状态、指标、版本、run、制品、数据集状态、机构与 storagePath 一致性），无效来源照旧不进列表。
- `freeze()`：去掉 `createdBy` 比较与 `yuanDatasets` 过滤。
- 预测草稿的创建者/查询统一用常量 `OPERATOR = "system"`（内网项目不按用户隔离）。

**保留的业务约束**（非身份类）：指标必须在支持范围内；候选未停用；任务 `RULE_PROMPT` + `SUCCEEDED` + 有 `currentRunId`；候选版本与冻结版本一致；run 快照哈希与请求哈希匹配；制品归属当前 run；数据集 `ready` 且机构、指标、storagePath 与锁定行一致。
