## 3. 第一轮优先模块选择

本轮优先分析 `payment` 与 `collection`，原因：

1. 原系统 `zjjs-ywgl` 是最大核心模块，包含收付款、一户通、转账等关键业务。
2. v3 已经落出付款 `FkywDomainService` 和收款 `SkywDomainService`，具备继续完善的基础。
3. 付款/收款是后续凭证、对账、账户联动的上游，应优先厘清边界。

## 4. 付款模块现状分析

### 4.1 当前代码入口

| 层 | 文件 | 说明 |
|---|---|---|
| Controller | `capinfo-gjj-busi-jshs-v3-app/.../YwglPaymentController.java` | 提供 `/api/payment/dbfk`、`/api/payment/plfk`、`/api/payment/result/{ywslbh}`。 |
| Domain Service | `capinfo-gjj-busi-jshs-v3-domain/.../payment/service/FkywDomainService.java` | 创建付款、处理付款结果回调。 |
| Model | `capinfo-gjj-busi-jshs-v3-domain/.../payment/model/FkywModel.java` | 付款聚合根，封装初始化与状态流转。 |
| Repository | `capinfo-gjj-busi-jshs-v3-domain/.../payment/repository/FkywRepository.java` | 付款仓储接口。 |
| RepositoryImpl | `capinfo-gjj-busi-jshs-v3-infrastructure/.../dao/repository/FkywRepositoryImpl.java` | 领域模型与基础设施 Entity 的转换、Mapper 调用。 |

### 4.2 已具备能力

- 单笔付款：Controller 构建 `FkywModel` 后调用 `FkywDomainService.createPayment()`。
- 批量付款：Controller 循环构建多个 `FkywModel` 并逐笔保存。
- 结果查询：通过 `FkywRepository.findByYwslbh()` 查询状态。
- 状态流转：`initialize()` 设置待处理；`markProcessing()`、`markCompleted()`、`markFailed()` 封装状态变更。
- 地区策略接入点：`createPayment()` 中根据 `hsdwdm` 获取 `RegionBusinessStrategy`。

### 4.3 主要缺口

| 缺口 | 影响 | 完善建议 |
|---|---|---|
| Controller 直接注入 `FkywRepository` 做结果查询 | 应用入口绕过领域服务，分层不够一致 | 在 `FkywDomainService` 增加 `queryResult(String ywslbh)`，Controller 只依赖领域服务。 |
| `createPayment()` 只获取策略并记录日志，没有调用策略能力 | 地区差异没有真正落地 | 明确付款领域策略接口，如 `PaymentRegionStrategy`，承载付款校验、渠道选择、记账差异。 |
| 付款创建未校验金额、账户、渠道、核算单位等业务不变量 | 聚合根仍偏数据载体 | 在 `FkywModel.initialize()` 或领域服务中增加不变量校验，异常使用 `BizException`。 |
| 批量付款逐笔保存，无批次聚合对象 | 批次号与明细关系不完整，失败回滚/部分成功语义不清 | 增加 `PlfkBatchModel` 或应用服务层批量用例，明确批次状态、明细状态和事务边界。 |
| 结果回调参数 `yhlsh` 未落库 | 银行流水号丢失 | 补充模型、Entity、Mapper 字段或明确该字段后续由回执表承载。 |
| Controller 生成业务流水号 | 编号规则散落在接口层 | 下沉为领域编号服务或 common 工具，便于统一单笔/批量/收款/转账流水规则。 |

## 5. 收款模块现状分析

### 5.1 当前代码入口

| 层 | 文件 | 说明 |
|---|---|---|
| Controller | `capinfo-gjj-busi-jshs-v3-app/.../YwglCollectionController.java` | 提供 `/api/collection/dbsk`、`/api/collection/plsk`、`/api/collection/result/{ywslbh}`。 |
| Domain Service | `capinfo-gjj-busi-jshs-v3-domain/.../collection/service/SkywDomainService.java` | 创建收款、查询收款结果、处理收款回调。 |
| Model | `capinfo-gjj-busi-jshs-v3-domain/.../collection/model/SkywModel.java` | 收款聚合根，封装初始化与状态流转。 |
| Repository | `capinfo-gjj-busi-jshs-v3-domain/.../collection/repository/SkywRepository.java` | 收款仓储接口。 |
| RepositoryImpl | `capinfo-gjj-busi-jshs-v3-infrastructure/.../dao/repository/SkywRepositoryImpl.java` | 领域模型与基础设施 Entity 的转换、Mapper 调用。 |

### 5.2 已具备能力

- 单笔收款：`dbsk()` 接收 `DbskRequest`，构建 `SkywModel` 并保存。
- 批量收款：`plsk()` 遍历 `skxxList`，逐笔创建收款业务。
- 结果查询：`SkywDomainService.queryResult()` 已承接查询逻辑。
- 状态流转：与付款类似，已有初始化、处理中、完成、失败状态方法。
- 地区策略接入点：`createCollection()` 中根据 `hsdwdm` 获取策略。

### 5.3 主要缺口

| 缺口 | 影响 | 完善建议 |
|---|---|---|
| Controller 直接返回 `SkywModel` | 对外暴露领域模型，不符合 DTO 化规范 | 增加收款响应 DTO 或复用 api 模块 DTO，Controller 返回 `R<SkywRespDTO>` / `R<PlskRespDTO>`。 |
| 请求 DTO 位于 app 模块 `app.dto` | DTO 分布不统一，Feign/API复用困难 | 将 `DbskRequest`、`PlskRequest` 对齐迁移或映射到 api 模块 ReqDTO。 |
| 批量收款返回 `List<SkywModel>` | 缺少批次流水、明细结果结构 | 对齐付款批量响应，形成 `PlskRespDTO` + 明细 DTO。 |
| `createCollection()` 只记录策略，没有执行差异逻辑 | 地区/渠道策略未真正生效 | 拆出 `CollectionRegionStrategy` 或在统一策略中增加明确的收款处理方法。 |
| 缺少金额、账户、渠道、核算单位不变量校验 | 可能保存非法业务数据 | 在领域服务/聚合根增加校验，使用 `BizException` 和业务错误码。 |
| UUID 作为业务受理编号 | 与付款编号规则不一致，可读性和对账追踪较弱 | 统一流水号生成规则，下沉到领域或 common。 |

## 6. 共享策略模块现状分析

当前共享策略接口为：

- `RegionBusinessStrategy`
- `RegionBusinessStrategyFactory`
- `DefaultRegionStrategy`
- `WzStrategy`

### 6.1 已具备能力

- 按 `hsdwdm` 注册并获取地区策略。
- 默认策略代码：`000000000000000`。
- 温州策略代码：`330300000000000`。
- 策略接口包含业务记账、渠道代码、是否通知转移接续认领资金等方法。

### 6.2 风险与缺口

| 问题 | 说明 | 建议 |
|---|---|---|
| 策略接口粒度偏粗 | `processBusinessAccounting(String txCode, String jylx, Object header, Object body)` 仍像旧系统通用入口 | 按领域拆分为付款、收款、转账、凭证、对账等策略接口。 |
| 参数使用 Object | 类型不安全，难以测试和审计 | 使用明确命令对象/上下文对象，如 `PaymentContext`、`CollectionContext`。 |
| 默认策略缺失保护 | `getDefaultStrategy()` 可能返回 null，调用方继续 `strategy.getClass()` 会 NPE | 工厂层若无默认策略应抛 `BizException` 或启动期失败。 |
| 地区覆盖不足 | 仅默认 + 温州，未体现枣庄、临沂、嘉兴等差异 | 后续按原系统 HSDWDM 引用点和业务差异逐步补齐策略。 |

## 7. 分层合规性初评

| 检查项 | 当前状态 | 结论 |
|---|---|---|
| Controller 是否返回 `R<T>` | 大体满足 | 付款返回 DTO，收款仍返回领域模型。 |
| Controller 是否只编排入参/出参 | 部分不满足 | 付款 Controller 生成流水号、直接查 Repository；收款 Controller 生成 UUID。 |
| Domain 是否无基础设施依赖 | 基本满足 | 领域模型无 ORM 注解；领域服务依赖 Repository 接口。 |
| Infrastructure 是否实现 Domain Repository | 满足 | RepositoryImpl 位于 infrastructure，调用 Mapper。 |
| DTO 是否统一在 api 模块 | 部分不满足 | 收款 app 模块存在 `DbskRequest`、`PlskRequest`。 |
| 异常是否统一 `BizException` | 不满足 | 当前多处使用 `IllegalArgumentException`。 |
| 策略是否真正承载地区差异 | 不满足 | 当前多为接入点和日志，业务差异尚未落地。 |

## 8. 后续逐模块完善顺序建议

### 第一阶段：收付款基础闭环

1. 统一收付款 DTO：收款 Controller 不直接返回 `SkywModel`。
2. 统一查询入口：付款结果查询从 Controller 直查 Repository 改为 Domain Service。
3. 统一流水号生成：从 Controller 下沉到领域服务或 common 编号组件。
4. 增加基础不变量校验：金额、账户、核算单位、渠道必填和状态流转合法性。
5. 使用 `BizException` 替换 `IllegalArgumentException`。

### 第二阶段：批量业务建模

1. 增加批量付款/批量收款批次模型。
2. 明确批次流水号、明细流水号、总金额、成功/失败数量。
3. 明确事务边界：全成功、部分成功、失败重试策略。
4. 补充批量结果查询接口。

### 第三阶段：策略细化

1. 拆分 `RegionBusinessStrategy` 为领域策略：付款、收款、转账、凭证、对账。
2. 引入类型安全上下文对象，替换 Object 参数。
3. 补齐枣庄、临沂、嘉兴、温州等地区差异策略。
4. 引入渠道策略：一户通、银行前置、政务平台等。

### 第四阶段：凭证、对账、账户联动

1. 付款/收款成功后发布领域事件。
2. 凭证模块订阅或应用层编排创建凭证。
3. 对账模块按渠道回执和本地流水做核对。
4. 账户模块处理账户余额、状态、总账联动。
