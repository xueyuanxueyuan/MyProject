# 资金预决算及执行情况 - 共性规则组设计

## 1. 设计目标

共性规则组用于在进入具体功能组设计前，先统一整套系统的公共约束。

本设计解决的问题不是某一张表怎么做，而是先确定：

- 谁能看、谁能填、谁能审
- 数据什么时候生成、什么时候锁定
- 全市与分中心数据如何汇总
- 哪些格子手工填、哪些系统自动算、哪些系统自动取
- 报表到底按几层模型建设
- 跨年度、跨表的数据如何衔接

本设计一旦确认，后续所有功能组都必须遵守。

## 2. 适用范围

本规则组适用于以下全部报表：

- 住房公积金资金使用预算总表
- 住房公积金资金使用预算附表
- 住房公积金业务收支预算总表
- 住房公积金业务收支预算附表
- 住房公积金资金使用预算执行情况表
- 住房公积金业务收支预算执行情况表
- 住房公积金扩面工作完成情况表
- 住房公积金归集使用决算总表
- 住房公积金归集使用决算附表
- 住房公积金业务收支决算总表
- 住房公积金业务收支决算附表
- 住房公积金增值收益分配情况总表
- 住房公积金增值收益分配情况附表

## 3. 设计原则

### 3.1 先统一公共规则，再设计单表

后续每个功能组只讨论自身业务差异，不重复争论公共口径。

### 3.2 事实数据与报表模板分离

系统不能只按“存结果值”思路设计，必须把：

- 业务事实
- 报表模板
- 计算规则
- 导出快照

分层管理。

### 3.3 原始录入值与派生值分离

系统只允许用户直接填写原始事实值。

自动汇总值、公式值、同比值、完成率值、跨表带入值，不作为人工录入字段处理。

### 3.4 全市汇总优先自动生成

原则上“全市”列不作为分中心人工填报字段，而由系统根据分中心数据汇总生成。

若业务上确有“市中心终审调整”需求，则调整值必须留痕，不能覆盖原始汇总结果。

### 3.5 规则可追溯

任意一个自动生成的值，都应能回答：

- 从哪张表来的
- 从哪条规则来的
- 是哪次计算生成的
- 是否被人工调整过

## 4. 统一角色与权限设计

## 4.1 角色划分

本系统统一定义 4 类业务角色：

### 4.1.1 分中心填报人

职责：

- 只能查看本机构数据
- 只能填报本机构允许填写的原始事实值
- 可保存草稿、提交审核

限制：

- 不能查看其他分中心原始录入值
- 不能修改系统公式值
- 不能修改全市汇总值
- 不能越过审核流程直接锁表

### 4.1.2 市中心汇总审核人

职责：

- 查看全市全部机构数据
- 查看系统汇总后的全市口径
- 执行审核、退回、终审前校验

限制：

- 不直接改分中心原始录入值
- 只能通过“审核退回”要求分中心修改

### 4.1.3 市中心终审人

职责：

- 对审核通过的数据执行终审
- 在允许的场景下录入终审补充信息
- 执行锁定
- 触发正式导出与快照归档

限制：

- 若有调整行为，必须留痕
- 不允许无痕覆盖分中心事实数据

### 4.1.4 系统管理员

职责：

- 维护模板、规则、基础机构、科目映射
- 维护开放期间和锁定期间

限制：

- 不参与普通业务填报
- 不作为业务审批主体

## 4.2 权限控制原则

统一按“单元格类型 + 数据归属 + 单据状态”三维控制权限：

1. 单元格类型
   - 原始录入格
   - 自动取数格
   - 自动计算格
   - 汇总展示格

2. 数据归属
   - 本机构
   - 全市汇总
   - 他机构

3. 单据状态
   - 草稿
   - 已提交
   - 审核退回
   - 审核通过
   - 已锁定

最终原则：

- 只有“本机构 + 原始录入格 + 草稿/退回”允许填报人编辑
- 自动取数格、自动计算格、汇总展示格全程只读
- 已锁定状态所有业务角色只读

## 5. 统一流程与锁定规则

## 5.1 通用状态流转

所有报表统一采用以下状态流转：

1. 草稿
2. 已提交
3. 审核退回
4. 审核通过
5. 已锁定

## 5.2 状态说明

### 草稿

- 分中心或市中心录入阶段
- 允许编辑原始事实值
- 不允许正式导出

### 已提交

- 进入审核队列
- 提交后普通填报人不可继续修改

### 审核退回

- 审核人发现问题退回
- 退回后仅允许责任机构继续编辑

### 审核通过

- 数据内容认可
- 等待终审锁定

### 已锁定

- 不允许继续修改
- 作为正式导出口径
- 必须生成快照

## 5.3 时间规则

### 预算表

- 每年 3 月编制
- 审议通过后锁定

### 执行情况表

- 按月编制
- 原则上次月填报上月数据

### 决算表

- 次年 1 月编制

### 扩面表

- 按月截止日期生成
- 1 月、2 月可按业务规则为空或不编制

## 5.4 锁定规则

锁定后：

- 原始事实值不可改
- 自动计算结果按锁定时口径固化
- 必须保留可追溯快照

若锁定后需修正：

- 不允许直接解锁覆盖
- 必须走“反锁/重开/重新生成快照”流程，并留下日志

## 6. 全市汇总与机构口径规则

## 6.1 机构维度统一口径

机构维度统一使用：

- `HSJGBH` 作为核算机构编号
- `JBJGBH/JBJGMC` 作为机构基础信息

前端展示上仍然可以按 Excel 形式渲染：

- 全市
- 市本级
- 嘉善县
- 平湖市
- 海盐县
- 海宁市
- 桐乡市

但数据库事实层原则上不采用“一个机构一列”的存储方式。

## 6.2 全市列规则

全市列统一定义为：

- 系统汇总展示列
- 原则上不作为分中心录入列

计算规则：

- 全市 = 所有纳入口径机构值之和

## 6.3 全市调整规则

本项目明确不允许市中心对“全市最终展示值”做人工调整。

全市最终展示值统一定义为：

- 分中心纳入口径数据的系统自动汇总结果

因此本项目不采用以下口径：

- 人工调整全市值
- 终审覆盖系统汇总值
- 通过补录方式修正全市展示值

若全市展示结果异常，处理方式只能是：

- 追溯到对应分中心原始事实值
- 退回责任机构修正
- 重新汇总生成全市结果

不允许直接修改全市结果本身。

## 6.4 分中心录入规则

分中心只录入：

- 本机构原始事实值

不录入：

- 全市值
- 他机构值
- 系统公式值
- 自动取数值

## 7. 手工填报、自动取数、自动计算边界

## 7.1 三类值定义

### 原始事实值

由业务人员手工录入或确认录入的值，例如：

- 本年预算数
- 当年统筹调剂资金
- 目标任务
- 某些无法从科目自动取到的实际数

### 自动取数值

由系统根据明确来源带入的值，例如：

- 取上一年度同表本年预算数
- 取上一年度决算年末余额
- 取执行情况表结果
- 取会计科目发生额或余额

### 自动计算值

由系统按公式实时或批量计算的值，例如：

- 合计
- 年末余额
- 完成率
- 同比增长
- 占比
- 全市汇总

## 7.2 编辑规则

统一规则如下：

- 原始事实值：允许编辑
- 自动取数值：默认只读
- 自动计算值：只读

## 7.3 特殊例外

若业务要求“自动带出后允许人工修正”，必须额外拆分为：

- 系统原始带出值
- 人工修正值
- 最终采用值

不能直接覆盖系统取数结果。

## 8. 跨年度与跨表勾稽规则

## 8.1 跨年度规则

统一支持以下跨年度带值关系：

- 上年预算数 <- 上一年本年预算数
- 年初余额 <- 上一年决算年末余额

## 8.2 跨表规则

统一支持以下跨表带值关系：

- 附表全市汇总 -> 总表对应字段
- 预算表 -> 执行情况表预算口径
- 执行情况表 -> 决算表本年实绩口径

## 8.3 勾稽规则

系统必须支持至少三类勾稽：

1. 表内勾稽
   - 合计 = 明细之和
   - 余额 = 期初 + 增加 - 减少

2. 表间勾稽
   - 附表全市 = 总表对应值
   - 执行结果 = 决算来源值

3. 跨年勾稽
   - 上年末 = 本年初

勾稽失败时：

- 允许保存草稿
- 不允许正式锁定

## 9. 会计科目取数规则

## 9.1 取数原则

会计科目取数只作为“自动取数来源”，不是最终业务规则本身。

也就是说，系统不能把公式直接写死在页面和 SQL 代码里，而要通过配置维护：

- 科目范围
- 取借方还是贷方
- 取发生额还是余额
- 是否需要正负调整

## 9.2 典型应用场景

例如需求中已出现：

- `201`
- `401`
- `411`
- `121`

这类口径后续应落在“科目映射规则”中统一维护，而不是分散写在各功能表代码里。

## 9.3 人工兜底规则

若科目自动取值失败或业务口径暂未稳定，则允许：

- 先由系统带出空值或建议值
- 由授权角色手工补录

但该字段仍应保留“取数失败/人工补录”状态标记。

## 10. 数据模型分层设计

## 10.1 推荐采用四层模型

### 事实层

存储真正业务数据，包括：

- 分中心原始录入值
- 终审调整值
- 锁定时最终结果

### 模板层

存储报表版式定义，包括：

- 行定义
- 列定义
- 分组层级
- 是否百分比
- 是否显示 `-`
- 是否可编辑

### 规则层

存储规则配置，包括：

- 公式规则
- 自动取数来源规则
- 勾稽校验规则
- 科目映射规则

### 快照层

存储正式导出时刻的定版结果，包括：

- 锁定时导出快照
- 审核意见快照
- 版本留痕

## 10.3 分层使用边界

本项目虽然保留模板层和规则层，但不采用“大一统通用模板引擎”思路。

统一原则如下：

- 每个功能组、每张业务表仍以独立业务建模为主
- 优先使用固定字段承载该表的核心业务指标
- 模板层只承担辅助作用，不承担所有业务字段通用化职责
- 规则层只管理少量共性规则，不强行抽象所有表的全部差异

模板层允许承载的内容主要包括：

- 行显示顺序
- 列显示顺序
- 是否显示百分比
- 是否只读
- 是否允许为空
- 导出样式控制

模板层不承担的内容包括：

- 试图把所有业务表都抽象成同一套通用指标模型
- 用统一单元格模型覆盖所有业务字段
- 为了追求通用而牺牲业务可读性和表结构清晰度

## 10.2 为什么不能只做事实层

如果只做事实层，会出现：

- 无法完整还原 Excel 版式
- 无法解释公式来源
- 无法稳定导出
- 无法保留历史口径快照

因此本项目不建议只使用“业务主表 + 明细表”的两层模型。

## 13. 本轮已定规则

当前我建议先作为首版定下的规则有：

1. 采用四层模型：事实层、模板层、规则层、快照层
2. 全市列默认自动汇总，不作为分中心手工填报列
3. 市中心不允许对全市最终展示值做人工调整，全市结果只能通过分中心数据重新汇总生成
4. 每张业务表按独立业务语义建模，优先采用固定字段承载核心指标，不过度模板化
5. 模板层只做辅助配置，不作为所有模块通用字段承载方案
6. 只允许编辑原始事实值，自动取数值和自动计算值只读
7. 所有报表统一采用“草稿 -> 已提交 -> 审核退回 -> 审核通过 -> 已锁定”状态流转
8. 锁定后必须生成正式快照
9. 跨表、跨年、科目取数规则统一配置，不分散写死
10. 1 月、2 月相关报表单据照常生成，但允许特定业务字段为空值，不采用“该月不生成单据”口径
11. 会计科目自动取值失败时不允许人工补录兜底，只能修正源数据或取数规则后重新取数

## 14.2 会计科目取数失败处理规则

针对会计科目自动取值失败场景，统一采用以下口径：

- 不允许人工补录兜底
- 不允许带着取数失败结果继续流转
- 不允许通过手工改值绕过取数规则

唯一允许的处理路径为：

1. 排查源数据是否缺失或异常
2. 排查科目映射规则是否错误
3. 修复后重新执行自动取数
4. 重新校验取数结果后再提交流转

设计约束如下：

- 取数失败字段必须明确标记失败状态
- 失败原因必须可追溯
- 失败状态下允许保存草稿
- 失败状态下不允许提交审核
- 失败状态下不允许锁定

这样做的目的，是保证：

- 报表结果与财务来源一致
- 不因人工兜底造成口径失真
- 后续审计可追溯

## 14.0 月度空值规则

针对执行情况表、扩面表等存在月度差异的报表，统一采用以下口径：

- 1 月、2 月单据照常生成
- 特定业务字段允许为空值
- 空值表示“该月该字段暂不适用或按业务口径不取值”
- 不因为字段为空而取消整张单据的生成

该规则主要用于承载以下场景：

- 3 月起才出现预算口径值
- 1 月、2 月某些同比、完成率字段不具备计算条件
- 某些会计科目口径在特定月份尚未形成有效值

设计约束如下：

- 空值字段必须在页面上按只读/可填规则明确展示
- 空值不等于 0，导出时必须保留“空”语义
- 公式计算时应区分空值和 0 值
- 勾稽校验时，对允许为空的字段不按缺失数据直接判错

## 14.1 执行情况表两版设计对比

本节仅针对以下 2 张执行情况表进行建模对比：

- 住房公积金资金使用预算执行情况表
- 住房公积金业务收支预算执行情况表

设计目标是让你对比两种方案的优缺点，再决定后续正式落哪一版。

### 方案 A：行驱动模板版

#### 设计思路

把执行情况表理解为：

- 行结构复杂、层级稳定、公式语义丰富的“模板型报表”

数据库不直接把“预算数、实绩数、同期数、完成率、同比增长”全部固化成物理列，
而是拆成：

- 模板定义行
- 模板定义列
- 单元格规则
- 单元格事实值

#### 适合承载的 Excel 特征

- 同一张表中既有分组行，也有指标行
- 不同行的取数规则不同
- 有的行是金额，有的行是百分比
- 有的行是自动公式，有的行是手工填报
- 有的行只在某些月份有效
- 有的行在说明中要求“由市中心统一制表”

#### 推荐数据结构

1. 模板主表
   - 报表编码
   - 报表名称
   - 适用年度
   - 适用月份类型

2. 模板行定义表
   - 行号
   - 行名称
   - 行分组
   - 父级行
   - 行类型
   - 值类型
   - 是否显示
   - 是否可编辑

3. 模板列定义表
   - 列编码
   - 列名称
   - 列类型
   - 机构编码
   - 排序号

4. 单元格规则表
   - 行编码
   - 列编码
   - 取值方式
   - 公式表达式
   - 科目映射规则
   - 是否允许为空

5. 单元格事实值表
   - 年度
   - 月份
   - 报表编码
   - 行编码
   - 列编码
   - 机构编码
   - 原始值
   - 计算值
   - 最终展示值

#### 页面交互方式

- 页面完全按模板渲染
- 行顺序、列顺序、是否展示百分比、是否只读，都由模板控制
- 不同月份可动态控制“1-2 月为空、3 月起显示预算数”等逻辑

#### 优点

- 最贴近 Excel 原表
- 最适合承载复杂行规则
- 最适合动态列和多机构列
- 后续新增一行或新增一列时不用改表结构
- 导出 Excel 时最稳定

#### 缺点

- 前后端实现复杂度高
- SQL 查询不如固定列直观
- 普通接口联调时，前端要做模板渲染和行列透视

### 方案 B：固定字段列版

#### 设计思路

把执行情况表理解为：

- 有固定业务字段的“指标明细表”

数据库直接把常用指标固化成物理字段，例如：

- 本年预算数
- 本年实绩数
- 上年同期数
- 完成率
- 同比增长率

每个机构一行，每个项目一行，通过字段列直接承载业务值。

#### 推荐数据结构

1. 执行情况主表
   - 年度
   - 月份
   - 报表编号
   - 编制单位
   - 状态

2. 执行情况明细表
   - 行号
   - 项目名称
   - 机构编码
   - 本年预算数
   - 本年实绩数
   - 上年同期数
   - 完成率
   - 同比增长率
   - 手工补录值

#### 页面交互方式

- 页面按固定列渲染
- 行显示由字典或行配置控制
- 列大部分写死为预算、实绩、同期、完成率、同比

#### 优点

- 数据结构简单
- 接口直观，前后端联调快
- 统计 SQL 好写
- 业务人员更容易理解落库方式

#### 缺点

- 对 Excel 复杂结构承载力弱
- 行规则差异大时，需要不断打补丁加字段
- 百分比、余额、说明型行、特殊月份规则不好统一处理
- 业务收支执行表和资金使用执行表结构并不完全一致，后续容易分叉成两套模型

### 两版核心对比

#### 1. Excel 还原能力

- 行驱动模板版：强
- 固定字段列版：中

原因：

- 执行情况表里存在“分组行 + 指标行 + 百分比行 + 公式行 + 特殊说明行”的混合结构，行驱动更容易承载。

#### 2. 前端交互难度

- 行驱动模板版：中到高
- 固定字段列版：低

原因：

- 行驱动需要前端按模板渲染和透视。
- 固定列版直接绑定字段即可。

#### 3. 数据库实现难度

- 行驱动模板版：高
- 固定字段列版：低

#### 4. 后续扩展能力

- 行驱动模板版：强
- 固定字段列版：弱

原因：

- Excel 一旦改一行、加一行、改规则，固定列版很容易动表结构或改代码。

#### 5. 导出与客户表样一致性

- 行驱动模板版：强
- 固定字段列版：中

#### 6. 适合当前项目目标程度

- 行驱动模板版：更适合“完整产出 Excel 原表、后续可持续维护”
- 固定字段列版：更适合“先快速上线一个简化版执行表”

### 当前采用方向

结合当前讨论结果，本项目对执行情况表的采用方向调整为：

- 优先采用“固定字段列版”

采用原因：

- 每张表的指标和项目差异较大，难以通过统一模板完全通用化
- 业务表独立建模更符合后续开发、联调和维护习惯
- 过度模板化会增加表关联数量，削弱结构可读性
- 当前目标不是做一个通用报表平台，而是做一套贴合这 13 张表的业务系统

但同时保留以下约束：

- 固定字段不等于放弃规则配置
- 仍可用少量模板配置控制展示顺序、只读状态、导出样式
- 不允许为了简单而把明显不同的业务表硬塞进同一张通用表

### 本轮结论

基于当前讨论结果，执行情况表建模方向先定为：

- 固定字段列优先
- 按表独立建模
- 模板只做辅助，不做全局通用承载

后续在进入“资金使用预算执行情况组”设计时，将按这个口径展开，不再回到“大一统模板模型”。
