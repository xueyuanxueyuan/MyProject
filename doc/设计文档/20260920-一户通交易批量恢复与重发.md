# 一户通交易批量恢复与重发（上一版设计）

> 调度入口已由《20260920-嘉兴一户通无参自动恢复跑批》替代，嘉兴与 prod 均已实现无参按状态扫描。下文清单参数属于上一版设计，不再适用于当前 XXL-JOB 入口；旧 dryRun 参数不会启用预检查，请改用独立预检查处理器。

## 范围

仅修改 prod 结算服务。批量原始业务明细已经在 skyw_plmx、fkyw_plmx 落库，不解析历史文件、不补造明细。提供 XXL-JOB 任务，限定机构、银行、收付款方向及明确结算流水清单，每次最多 100 笔主业务，默认只预检查。未连接真实数据库或平台，不执行部署。

## 执行路径

1. 原业务按机构、银行、结算流水精确查找，限定一户通渠道及自动经办；拒绝取消、成功、记账、待确认等受保护状态。
2. 没有一户通任务：锁定原业务并重新检查，校验批量笔数、金额、明细流水唯一性和银行信息。按原业务 ID 补建业务结果，复用既有适配器和异步提交边界创建一户通协议任务、批次任务和明细。原业务和原始明细不重复插入。
3. 已有完整任务：保持申请号、结算流水号、子批次号及明细流水不变，通过专用重发边界认领已有协议任务后外发，不重复建立任务。
4. 结果不明、正在发送、已受理不盲目重发；使用原有补查机制或人工核实。历史 SEND_FAIL 不能被解释为平台未收到。
5. 存在局部子批次或不一致记录时不重新分组、不自动覆盖：返回需核查原因，避免改变已有子批次身份。

## 使用方法

任务处理器：`yhtTradeRecoveryJobHandler`（XXL-JOB 的 BEAN 模式）。可以手动触发，也可配置定时执行同一份清单；本次未创建调度配置、不默认开启定时外发。仅实现 prod 后端，不新增前端页面。

预检查参数示例（替换机构、银行和实际结算流水）：

```json
{"jbjgbh":"机构编号","yhdm":"102","direction":"sk","jslshList":["实际结算流水1","实际结算流水2"],"dryRun":true}
```

付款使用 direction=fk。清单 1–100 个主业务流水，不是批量明细流水。一次请求只处理一个机构、银行、收付款方向；机构上限30字符、银行20字符、结算流水32字符，不接受空白、重复流水、未知参数或字符串形式的 dryRun。未填写 dryRun 时为 true。

执行顺序：先以 dryRun=true 检查，确认范围和结果后将同一清单设为 dryRun=false 执行。建议使用串行阻塞策略，失败重试设为0，由操作者检查后再次触发。不要同时人工取消、修改或删除同一批业务。自动周期任务每次仍须限定清单，不全表扫描。

| 结果 | 含义 |
| --- | --- |
| READY_CREATE | 没有一户通任务且基础数据符合补齐条件，未实际发送 |
| READY_RESEND | 原任务证据符合重发规则；实际执行仍会检查业务键与最新状态 |
| NEEDS_QUERY | 历史发送结果不明，执行时仅查询 |
| DISPATCH_REQUESTED | 已安排提交后异步外发，不等于平台已受理；继续检查协议/批次任务 |
| SENT | 原报文已重发且同步结果已回写，不等于银行交易成功 |
| QUERY_ONLY | 只进行了状态查询，没有重发 |
| SKIPPED | 保护状态、人工经办、幂等占用等原因跳过 |
| ERROR / SEND_FAILED | 数据校验、执行或发送失败；整次调度标记失败，其余流水继续处理 |

任务日志仅打印结算流水、结果类型和计数，不打印账号、原报文或异常详情。服务返回的 message 用于受控排查。SKIPPED 不算发送成功；任务成功只表示这一轮处理没有报告执行错误。

## 重发证据与限制

- 新增 SEND_NOT_STARTED：仅 HTTP 客户端确认尚未调用请求体写入时设置；失败原因排除后可以复用完整原任务、原报文重发。已有幂等键仅释放当前待发送占用，不删除其他已确认键。
- 历史 UNKNOWN/SEND_FAIL 没有上述证据，不能通过改状态强制重发。正式执行仅调用已有状态查询链路，不因查询超时或“未查询到终态”就重新扣款。INIT/SENT/ACCEPTED、人工接管或终态任务跳过，按原补查/人工流程处理。
- 同步拒绝仅允许已核对原报文关联的 CAPS900 E054（报文格式错误）及 E419（schema校验失败）；不把银行业务失败视为可重发。重发使用原始完整报文，不重新签名或改业务字段，只有平台规则或配置修正等情况下这类原报文重发才可能有效。
- 累计最多3次既有任务恢复认领，同时遵守 nextRetryTime；不重置历史计数。标记与历史响应冲突时跳过。
- 部分子批次、孤立协议任务、明细缺失、笔数/金额/流水不一致时拦截，不自动拼凑或重新编号。本次支持“原业务及原始明细完整、后续任务完全缺失”与“后续任务完整”两条路径，不承诺修复任意中间表损坏。
- 原始主业务/明细不插入副本。补齐范围为业务结果和现有一户通链路，不补建传统银企渠道专用表。缺少业务结果时使用原主业务ID。
- 数据库事务不跨外网持锁：恢复事务内锁定原业务和结果，重发单独锁定协议任务认领；网络之前再次检查业务有效状态。尚未进行真实数据库、Redis及人工取消竞争的集成测试，执行窗口必须避免同一业务人工修改/取消。

## 一致性与验证

预检查不调用写库、查询平台或有写库副作用的日志服务。单笔恢复独立事务；原业务行锁防止两个恢复任务同时补建。外发依赖既有业务幂等键，并在提交后进行。既有任务重发使用持久化认领，发送中断保留不确定状态，禁止下一轮盲目重发。每个流水单独返回状态，单笔异常不阻断剩余清单。

通过单元测试验证预检查、原始明细校验、源数据补齐、既有任务复用、保护状态、并发认领和请求参数。真实数据库 SQL、跨服务并发及真实平台验收另行开展。
