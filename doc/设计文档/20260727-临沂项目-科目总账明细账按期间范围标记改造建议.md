# 临沂项目科目总账明细账按期间范围标记改造建议

## 1. 背景

当前科目总账、科目明细账使用统一表 `cwhs_zb` 存储报表结果，现状主要依赖以下条件识别一次制作结果：

- `ztbh`
- `bbbh`
- `kmbh`
- `tjny`
- `czy`

其中：

- `tjny` 实际被用作“本次报表截止日期/报表批次标识”
- `czy` 被用作“当前操作员隔离维度”

用户希望调整为：

1. 不再用 `tjny` 判断报表结果。
2. 生成时按所选 `jzrq` 日期范围把对应数据重新制作。
3. 直接查报表时，也按 `jzrq` 日期范围查询。
4. 这样便于在月结中自动制作总账和明细账。

## 2. 直接按行级 `jzrq` 范围替代 `tjny` 的问题

这个方向本身是合理的，但**不能直接把现有 `tjny` 条件删掉，再仅靠行级 `jzrq` 做删除和查询**。原因如下。

### 2.1 汇总行的 `jzrq` 为空

当前生成逻辑里，下列行保存时 `jzrq = null`：

- 上年结转
- 上次结转
- 本月合计
- 本年合计

而只有逐日或逐笔明细行才带实际 `jzrq`。

这意味着如果未来只按：

```sql
where jzrq between :ksrq and :jzrq
```

做删除或查询，那么这些关键汇总行会出现以下问题：

- 删除时删不掉，导致新旧结果混杂
- 查询时报不出来，账页结构不完整
- 只能查到发生行，查不到结转和合计行

### 2.2 同一科目不同期间会互相污染

如果只按 `ztbh + bbbh + kmbh + jzrq范围` 删除：

- 做 2026-07-01 ~ 2026-07-31
- 又做 2026-07-15 ~ 2026-07-31

两批结果的行级 `jzrq` 有重叠，但它们对应的：

- 上次结转
- 本月合计
- 本年合计

并不相同。

若没有“这批报表属于哪个期间”的独立标记，就无法区分：

- 哪些汇总行属于 7 月整月
- 哪些汇总行属于 7 月下半月

### 2.3 月结自动制作需要“批次边界”而不是“行日期”

月结自动制作的核心诉求是：

- 系统能自动生成某一期间的总账、明细账
- 后续查询时，能稳定取回这一期间的完整结果

这本质上需要的是：

- 一组“报表期间边界”或“报表批次标识”

而不是仅靠每一行自身的业务日期。

行级 `jzrq` 只适合表达“这笔发生发生在哪天”，不适合单独承担“这张报表是针对哪个期间制作的”。

## 3. 推荐方案

## 3.1 保留“按期间制作、按期间查询”的业务口径

用户提出的业务口径我建议保留：

- 制作时：以选择的起止日期作为本次报表期间，重做这一期间的数据
- 查询时：以选择的起止日期作为查询条件，读取这一期间对应的报表结果

这个方向是对的，尤其有利于月结自动制作。

## 3.2 不建议继续用 `tjny`，但建议新增“期间字段”

推荐不要再把 `tjny` 作为核心判定字段，而是显式新增两列，例如：

- `bbksrq`：报表开始日期
- `bbjzrq`：报表截止日期

也可以命名为：

- `ksrq`
- `jzrq_end`

但为避免与行级 `jzrq` 混淆，更建议使用：

- `bbksrq`
- `bbjzrq`

这样每一行都同时具有两层日期含义：

- `jzrq`：当前账表行对应的实际记账日期，汇总行可为空
- `bbksrq/bbjzrq`：这整批报表的统计期间，所有行都相同

## 3.3 查询和删除都改成按“期间字段”识别整批结果

未来建议删除条件调整为：

- `ztbh`
- `bbbh`
- `kmbh`
- `bbksrq`
- `bbjzrq`

如仍需保留人工隔离，可以保留 `czy`；若月结自动任务希望结果可被所有人共用，则应去掉 `czy` 作为主判定条件。

查询条件也改为：

- `ztbh`
- `bbbh`
- `kmbh`
- `bbksrq`
- `bbjzrq`

这样做的好处：

- 一次制作对应一整批完整结果
- 汇总行即便 `jzrq=null` 也不会丢
- 支持按所选期间稳定重做
- 支持月结自动制作和人工查询复用同一批结果

## 4. 对用户诉求的落地翻译

如果用更贴近实现的话，建议把需求口径明确为：

### 4.1 生成口径

- 用户选择 `开始日期`、`截止日期`
- 系统先删除同账套、同报表类型、同科目、同期间的历史账表结果
- 再基于原始凭证和余额数据，重新生成这一期间的完整账表
- 生成结果中的每一行都打上：
  - `bbksrq = 开始日期`
  - `bbjzrq = 截止日期`

### 4.2 查询口径

- 用户直接打开报表时，按 `开始日期 + 截止日期` 查询账表结果
- 报表模板按整批期间取数，而不是只按行级 `jzrq` 过滤

### 4.3 月结自动制作口径

- 月结程序直接传入当月 `bbksrq/bbjzrq`
- 自动制作完成后，人工查询同期间报表时直接读取这批结果
- 不再依赖“是谁制作的”

## 5. 是否还需要 `czy`

这个点需要业务上明确。

### 方案 A：保留 `czy`

适合场景：

- 不同操作员希望有自己的临时制作结果
- 人工重算不影响别人

缺点：

- 月结自动制作后，其他人查询未必能看到同一批结果
- 自动任务的 `czy` 需要约定固定值，例如 `SYSTEM`

### 方案 B：去掉 `czy` 作为关键条件

适合场景：

- 月结自动制作后，全员查询同一份账表
- 总账、明细账属于公共标准结果

优点：

- 更适合自动月结
- 同期间只有唯一一份标准结果

缺点：

- 人工临时试算会覆盖正式结果，若要保留试算能力，需要再引入“结果类型/版本号/是否正式”字段

### 推荐意见

如果您的首要目标是“月结自动制作后可直接查正式账表”，更建议：

- **弱化甚至移除 `czy` 作为核心判定条件**
- 如有试算需求，再增加：
  - `sjlx`：数据类型，例如 `official/trial`
  - 或 `scfs`：生成方式，例如 `manual/auto`

## 6. 最推荐的改造口径

综合当前代码结构与您的目标，我更推荐以下方案：

### 6.1 字段层

- 废弃 `tjny` 的“批次识别职责”
- 新增：
  - `bbksrq`
  - `bbjzrq`
- `jzrq` 继续保留，表示行级发生日期

### 6.2 生成层

- 删除旧结果时按 `bbksrq + bbjzrq` 删除整批
- 生成每一行时补齐 `bbksrq + bbjzrq`

### 6.3 查询层

- 报表模板不再按 `tjny` 查
- 统一按 `bbksrq + bbjzrq` 查
- 若需要公共结果，则不再把 `czy` 作为必选条件

### 6.4 月结层

- 月结自动调用总账/明细账制作接口
- 传入月度期间
- 自动生成公共正式版本

## 7. 结论

您的方向我赞同，但建议做一个实现层修正：

- **赞同**：不要再用 `tjny` 做报表结果判定
- **赞同**：生成和查询都按选择的日期期间口径来理解
- **不建议直接做法**：只用现有行级 `jzrq` 范围替代 `tjny`
- **建议改法**：新增“报表开始日期/报表截止日期”作为整批结果标记，`jzrq` 继续只承担行级日期含义

这样既满足：

- 按期间重做
- 按期间查询
- 月结自动制作

又不会丢掉：

- 上次结转
- 本月合计
- 本年合计

这些 `jzrq` 为空的关键账表行。
