## 2. 需求匹配度分项打分（二次评审）

### 2.1 考核比例列与金额计算、脱钩功能
- **需求点**：新增“考核比例（%）”列，自动计算“银行考核金额=手续费*考核比例”保留2位小数；手动修改考核金额后，不再与比例挂钩。
- **设计评估**：设计在 `cwhs_sxfyt_mx` 中增加了 `khbl` 字段，明确“手工修改金额后，不再强制反算或覆盖比例”，完美契合业务边界。
- **分项评分**：**100 / 100**

### 2.2 考核完成后同步差额冲减
- **需求点**：考核完成后，同步进行差额部分冲减对应科目的操作。
- **设计评估**：复用 `gdsxfYtCjPzSc(...)` 生成冲减凭证，`yhkhjlje` 存差额，思路清晰。
- **分项评分**：**100 / 100**

### 2.3 允许多次支付、默认金额、金额上限及生成凭证 🌟（核心亮点）
- **需求点**：允许多次支付，默认考核后的结果数据，修改不可大于当条明细的考核金额。每次支付完成自动生成凭证。
- **设计评估（整改后）**：
  - **纠正了数据粒度**：放弃了明细级拆分，明确在 `cwhs_sxfyt`（预提头表）增加 `khhzje`(考核后总额)、`yzfze`(已支付总额) 和 `ztdjje`(在途冻结金额)，完全契合了临沂按银行汇总发起资金结算的真实情况。
  - **严密的在途防资损控制**：在 `sxfytZfsq` 接口引入了乐观锁（或原子扣减）机制 `update cwhs_sxfyt set ztdjje = ztdjje + #{je} where ... and (khhzje - yzfze - ztdjje) >= #{je}`，彻底堵死了多次支付场景下的并发超额风险。
  - **精准的凭证回写**：利用回调接口 `receiveCwjzxx` 根据本次实际支付金额动态冲减明细（`yzfje`），不仅凭证金额完全对齐实际资金下发口径，还解决了旧逻辑倒推错乱的问题。
- **分项评分**：**98 / 100**（设计不仅满足了需求，在防并发超发和凭证拆分算法上展现了极高的专业度）

### 2.4 多次支付后的结清要求
- **需求点**：多次支付后需将考核结果数据支付完毕。
- **设计评估（整改后）**：结清判定条件修正为头表级别的 `khhzje == yzfze`，准确无误。
- **分项评分**：**100 / 100**

## 3. 总体评价

经过一轮打回重构，设计团队准确抓住了临沂区域**“按银行汇总发起资金结算”**的真实业务粒度，并引入了**“在途冻结金额（ztdjje）”**这一关键的资金池控制概念，从根本上消除了并发超额支付的资损风险。
