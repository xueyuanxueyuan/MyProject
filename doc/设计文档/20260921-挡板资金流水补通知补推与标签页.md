# 挡板资金流水、补通知、补推及标签页

## 用户确认
补动账通知生成缺失通知，补推动账指将通知重新发送到结算服务，不是重新触发结算端记账。新增资金流水查询，补推入口集中于流水页；所有模块改为标签页，同一时刻仅展示一个模块。

## 实施计划与验收
1. 工部：新增持久化流水及独立操作记录；每个成功交易/批量成功明细使用稳定业务键唯一标识。先写关闭自动通知、补生成、失败重发及并发去重回归。
2. 工部：自动发送与人工补推共用发送实现；缺失通知生成后为待推送，失败/未知补推须核对确认，成功/发送中禁止重推。使用版本号阻止连续重复点击；原银行流水与报文不改变。
3. 工部：资金流水支持业务日期、中心银行、中心账号、银行流水/批次/请求标识、收付方向及通知状态筛选、分页、详情及操作记录。同步已有成功交易只入账册，不产生外部请求；来源无法核实时跳过并报告。
4. 工部：沿用现有视觉样式，将侧栏导航改为顶部可滚动标签，支持键盘、地址锚点、刷新和浏览器前进后退。切换不重建表单。
5. 刑部：运行相关测试到全量回归、前端静态和浏览器测试；验证补生成不发送、成功不重推、失败需确认、旧版本请求拒绝、并发单次发送、分页与标签切换。
6. 礼部：Schema 升至3，提供版本2到3增量脚本和使用说明。真实达梦及结算联调未授权，不执行数据库变更、发布或真实补推。

## 安全与兼容
流水仅代表挡板已确认成功的模拟资金变动，不是银行真实流水。自动开关控制自动发送，不妨碍查询及人工操作。补生成按中心账户银行匹配；首次生成后的报文快照固定，补推使用当前页面接口地址与鉴权变量，操作记录保存实际目标和响应，禁止保存鉴权值。
资金流水和操作审计独立于普通接口日志，清历史仍保留。旧去重有记录但无已保存通知的流水保留保护，不根据当前配置伪造历史报文后重发。发送中禁止重新占用；进程中断遗留记录需运维先停止原发送节点并重启、核对结算接收后人工恢复为UNKNOWN，不按定时超期盲目释放。数据库持久化发送者标识和尝试版本；当前进程拥有的尝试不可释放，旧尝试迟到不能覆盖新尝试。多实例原节点是否已停止必须由运维确认，勾选确认不等于系统能自动验证远程节点存活状态。

## 修订（2026-09-22，用户四点反馈）

用户反馈：① 录入手动推送原因后「我已核对」勾不了、「推送到结算」按钮无法使用；② 流水条目多，详情与补操作区域在页面底部要滚到底，应改弹窗；③ 失败数据太多，需要批量推送；④ 流水要记录推送状态，只有未推送与推送失败的才能重复推送。

1. **控件可用性与原因说明（缺陷修复）**。原 `renderFlowButtons` 把「我已核对」勾选框按状态硬禁用（仅失败 / 结果不明可勾），且推送按钮不可用时没有任何说明——用户在「未生成 / 待推送 / 已受理」等状态下看到的是两个点不动的控件。改为：勾选框只随「操作中 / 未选中流水」禁用，是否必勾由推送动作在提交时校验；推送按钮的可用性判定收敛到单一函数 `flowPushRule(status)`，不可用时通过 `title` 与弹窗内的状态说明行给出原因；列表每行「通知状态」下方直接写出该行能否推送及原因。理由：控件禁用的判定依据必须对用户可见，否则等同于控件损坏。
2. **流水详情改为页面级模态弹窗**。`#flowDetailPanel` 内联面板删除，改为页面级 `<dialog id="flowDetailDialog" class="mock-dialog">`（放页面级而非区块内，避免祖先 `hidden` 影响 `showModal`），ESC 与「关闭」按钮均可关闭；`app.css` 移除失效的 `#flowDetailPanel` 规则，新增勾选列与推送状态提示样式。
3. **新增批量补生成并推送**。接口 `POST /yht-mock/api/movements/batch-push`（`ids` / `reason` / `confirmedNotReceived`），逐条处理并返回 `pushed` / `generated` / `rejected` 明细；`rejected` 带逐条原因。页面在流水表格上方提供勾选列、全选（含半选态）、批量原因、核对确认、执行与清除选择。服务端为唯一裁判：单次最多 50 条，超出直接拒绝；逐条状态校验与单笔推送共用同一套规则。
4. **推送口径固化（只有未推送与推送失败可推）**。
   - `MISSING`（未生成）/ `PENDING`（待推送）＝未推送，`FAIL`（推送失败）可以推送；其中 `MISSING` 在批量入口先补生成通知再推送。
   - `SUCC`（已受理）、`SENDING`（发送中）、`LEGACY`（历史保护，缺通知快照）一律拒绝，不重复动账。
   - `UNKNOWN`（结果不明）**批量入口一律拒绝**，只允许在详情弹窗中核对结算结果后单笔补推。这是对用户口径的一处收紧解释：结果不明意味着「可能已经推送」，批量无差别重推与「避免重复动账」相冲突；若不允许单笔补推，该状态将永久无出路，故保留单笔且强制勾选核对确认。**此项需业务确认，如要求批量也放开，改动点只有 `MovementNotificationService.batchPush` 的状态集合。**
5. **通知状态筛选支持多选**。`MovementFlowStore.query` 的 `status` 参数改为接受逗号分隔多值（逐值校验，非法值仍报「通知状态无效」），页面筛选新增「可推送（未推送 / 失败）」与「未推送（未生成 / 待推送）」两个预设项。用途：一次筛出全部可补推流水 → 全选 → 批量推送，替代逐条翻页操作。
