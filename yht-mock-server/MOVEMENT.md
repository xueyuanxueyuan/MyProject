# 交易成功自动动账通知

## 启用

1. 打开挡板的「回调配置」，找到「交易成功自动动账通知」。功能默认关闭，开关和接口地址仍在页面保存；数据库必须升级到版本 3（版本1依次执行03、04脚本，版本2执行04脚本）。
2. 接口地址未保存时，按结算 CAPS 接收地址推导 /api/v1/ywgl/saveZhbdzt，保留主机、端口和已识别的网关前缀；已有非空动账接口地址不覆盖。页面可以手动修改并保存。仅识别结尾 /yht/yht/receive 或 /api/v1/ywgl/yht/yht/receive 的接收地址，其他路径需手填。不要将 CAPS 接收路径本身当作动账路径。
3. 按已确认的测试口径，收款、付款动账代码均默认 SBDC100；可手动覆盖。该字段是动账通知 jydm，不修改请求中的 CAPS 交易码。
4. 在独立的「银行对手账户配置」区域，逐个填写中心账户所属银行标识、银行名称、对手账号、户名及行号，并启用、保存。银行标识必须与原请求完全一致，不按银行名称或行号前缀匹配。结算系统需配置相同的对手账户信息用于对账。以前的统一虚拟账户不自动绑定到任何银行，也不作为兜底；需要沿用时请明确配置到相应中心银行。余额默认 0.00，是固定模拟值，并非真实或累计余额。
5. 如接口需要 Authorization，在挡板进程环境中设置对应变量，页面仅填写变量名称，例如 YHT_MOVEMENT_AUTH；变量值是完整 Authorization 请求头值。不要将 Token 写入页面、配置文件或日志。环境变量变更需重新启动进程才能生效。
6. 开启并保存配置。通知独立于 CAPS 自动回调总开关，但遵守场景规则「禁止自动回调」。沿用「回调延迟(ms)」，由独立单线程有界队列发送。

## 支持范围与字段

动账代码空白时默认 SBDC100；已有非空代码与显式接口地址保留。旧统一对手字段仅为历史数据兼容保留，不参与发送。每个中心银行配置一组稳定的对手账户，不按笔随机生成。中心账号、金额、交易方向和流水来自请求；请求不含真实余额，不从交易金额推算余额。交易日期（jyrq）固定取原交易 checkDate（交易处理完成日），随通知报文发送，结算端按原接口接收落 zjZhbdtz.jyrq，不随推送时间变化；通知时间和文件名仍由结算端生成。

| 场景 | 中心账号 | 金额 | 触发条件 |
| --- | --- | --- | --- |
| 20601 单笔付款 | DbtrActId | 负数 | status/resFlag=SUCC 且 RetCode=000000 |
| 20602 单笔收款 | CdtrActId | 正数 | status/resFlag=SUCC 且 RetCode=000000 |
| 40501 批量付款 | CorpAcctNo | 成功明细金额合计取负 | 批次 SUCC、ResFlag=SUCC、ErrorCode 为空或 00 |
| 40502 批量收款 | CorpAcctNo | 成功明细金额合计取正 | 同上 |

- 批次状态在受理（caps.101）时即按同一次生成的结果文件推导：明细结果码全 00 且 ResFlag=SUCC 落 SUCC，否则落 FAIL 并带首个失败明细的结果码与描述；场景规则显式指定强制状态时以规则为准。**推送 caps.107 之前再幂等兜底一次**（仍处 PROC/PEND/INIT 则按结果文件落终态），因此 107 报文里的 BatchStatus、业务查询列表与动账判定始终一致。**caps.105/106 是查询请求，只回显状态，不修改、不写库**（此前 106 里「PROC 自动改 SUCC」的副作用已删除）。
- 失败、处理中、未知交易类型、缺少中心账号、缺少原始金额或原始明细，不伪造通知。既有演示报文中的 201/101 不作为动账交易码。
- 请求字段：yhzhhm、jydm、jydszh、jydshm、jydshh、je、yue、zhaiyao、beizhu、yhlsh，以及 **jyrq（交易日期，固定为原交易 checkDate / 交易处理完成的日期）**。摘要和备注明确标记挡板模拟。
- 单笔银行流水使用挡板交易的 SysSeqNo；**批量按包生成——整个批次只登记一条流水**，金额取成功明细金额合计，失败明细不计入，银行流水为按批次维度去重键派生的 MOCK 串。接收端按原接口生成通知时间和文件名（交易日期由本挡板在报文中携带 jyrq，不再由结算端按推送日生成）。

## 中心银行匹配与账户维护

- 单笔付款 20601：中心银行取 DbtrBankId，与中心账号 DbtrActId 对应。
- 单笔收款 20602：中心银行取 CdtrBankId，与中心账号 CdtrActId 对应。
- 批量 40501/40502：取原请求文件汇总行第六列（中心账户所属银行），持久化到批次 centerBankId；不使用明细中的个人银行。
- 每个银行标识精确对应一条配置；编辑时锁定标识，修改标识请新增配置。保存同标识会更新原账户，可独立停用、删除。
- 缺失、未配置或停用时，MOVEMENT 记录标记 FAIL 并说明中心银行问题，不发送、不占用发送去重。补充配置后可在「资金流水」补生成通知，再人工推送；不会自动补发历史通知。
- 已经发送过的流水仍受持久化去重保护，修改账户配置不会导致重发。
- 清除历史数据保留银行账户配置。升级前的批次缺少中心银行时不猜测、不从结果明细回填；使用含完整汇总行的新测试交易验收。
- 管理接口：GET/POST /yht-mock/api/bank-counterparties；DELETE /yht-mock/api/bank-counterparties/{bankId}。配置独立保存到 YHT_MOCK_BANK_ACCOUNT。

## 查看结果与去重

接口记录中筛选「动账通知」或搜索 saveZhbdzt。记录包含请求体、响应体、HTTP 状态与处理状态：

- SUCC：HTTP 2xx，JSON code=0，且 data 不是 false，表示保存接口已受理；不代表后续异步记账已完成。
- FAIL：HTTP/业务明确失败，或本地参数检查未通过。
- UNKNOWN：超时、网络异常、非 JSON、缺少业务返回码等，无法确认接收端是否已经保存。

发送前持久化占位，按企业、日期、交易码、原业务流水去重。**批量改为按包去重：企业、日期、交易码加批次标识（原请求 FileName，缺省用批次号），整个批次一条流水一条占位**，避免标准报文重复上传时挡板新生成批次号造成重复动账。清空普通接口日志不清除去重，重启不会自动重发在途、成功或失败请求。⚠ 升级提示：去重键由明细维度改为批次维度，若环境中已存在明细级历史流水，对历史批次再次触发动账会新增一条包级流水并与历史流水并存，因此**不要对历史批次重新触发动账同步**。

本功能不自动重试。**推送口径（2026-09-22 固化）：只有未推送的「未生成 / 待推送」与「失败」可以推送**；「已受理」「发送中」「历史保护」一律拒绝，「结果不明」只允许在流水详情里核对结算接收结果后单笔补推（批量入口拒绝，因为它意味着可能已经推送）。数据库版将占位和结果保存到 YHT_MOCK_MOVEMENT；普通日志清理和全部历史清理均保留去重状态，不允许通过清历史重放通知。

## 资金流水与手工补操作

所有功能改为顶部标签页，一次只显示一个模块。切换保留已录入表单，支持浏览器前进后退和刷新锚点，标签可用左右箭头切换。

1. 打开「资金流水」，可按业务日期、中心银行、中心账号、流水/批次/请求标识、收付方向、通知状态筛选并分页查询；**通知状态支持多选，并预置「可推送（未推送 / 失败）」「未推送（未生成 / 待推送）」两个筛选项**，便于一次筛出可补推流水后批量处理。金额使用精确文本显示。这里是挡板成功交易的模拟流水，不是实际银行查询接口。
2. 新成功交易和批量成功明细即使自动通知关闭也登记流水；失败和处理中交易不会伪造成资金变动。处理在既有工作队列中完成，繁忙时稍后刷新。
3. 升级前的交易可点「同步已有成功交易」，根据保存的原始 CAPS 请求核验企业来源，只登记流水、不发通知。缺少原始请求时跳过；检查数量不是新生成数量，重复同步不重复登记。普通历史清理前先同步需要保留的成功交易。
4. 列表每行的「通知状态」下方直接写出该行能否推送及原因；勾选列用于批量处理，表头勾选框全选本页并显示半选态。**每次查询只反映当前页，勾选可跨页累积，批量执行后清空。**
5. 选择「详情 / 补操作」会在页面中央弹出**模态弹窗**（不再是页面底部内联面板，条目多时无需滚到底），ESC 或「关闭」按钮均可关闭。弹窗内填写操作原因；状态「未生成」时点击「补动账通知（仅生成）」，按中心银行配置生成报文快照，进入「待推送」，没有外部请求。
6. 预览报文与当前目标地址后点击「推送到结算」，二次确认后才发送。自动通知开关关闭不妨碍明确的人工操作，仍必须配置有效接口地址和鉴权环境变量。
7. 状态「失败」时，先核对结算端未接收，勾选确认并说明原因，再点击「补推到结算」；状态「结果不明」同样需勾选确认，且只能在弹窗里单笔补推。保留原报文、金额、对手账户和银行流水，不因配置变更重建报文；推送地址与鉴权取当前配置，并记录实际目标和结果。
8. **批量补生成并推送**：勾选多条（或全选本页）→ 填写批量推送原因 → 如选中含「失败」需勾选核对确认 → 点击「批量补生成并推送」。服务端逐条判定并返回每条处理结果：未生成先补生成通知再推送，待推送直接推送，失败在确认后补推；已受理 / 发送中 / 历史保护 / 结果不明逐条拒绝并给出原因，不会重复动账。单次最多 50 条，超出直接拒绝。**服务端是唯一裁判**：即使页面状态过期，服务端仍按库中真实状态拒绝。
9. 「已受理」禁止重推；「发送中」禁止并行发送。浏览器旧版本按钮、连续点击以及多实例并发通过数据库控制锁和流水版本校验拒绝重复占用。HTTP 成功只表示接收接口受理，不表示异步记账完成。
10. 若服务中断遗留「发送中」，先停止原发送节点并重启（多实例必须由运维核实原节点已停止），核对结算接收结果后勾选专门确认，点击「恢复中断发送为结果不明」。恢复不发送；确认结算未收到后才能另行补推。当前进程拥有的发送不允许释放；系统不凭时间超期自动释放，也无法替代运维核实另一节点是否已停机。每次发送带尝试标识和版本，失效尝试不能覆盖新结果。
11. 「历史保护」表示旧版本已有发送占位但没有完整通知快照，不能根据当前配置伪造快照重推。旧版本已成功的通知保持「已受理」并禁止重发。
12. 生成、推送与中断恢复记录保存在独立表，记录原因、目标、请求、响应和时间；不保存 Authorization 值。清除普通接口记录及历史数据不会删除资金流水、操作记录或去重信息。
13. 批量推送相关接口：POST /yht-mock/api/movements/batch-push（ids / reason / confirmedNotReceived）。流水查询的 status 参数支持逗号分隔多值。

Schema3 新表：YHT_MOCK_FLOW、YHT_MOCK_FLOW_ATTEMPT。升级见 doc/数据库脚本/一户通挡板达梦/04-upgrade-v2-to-v3.sql。

## 验证边界

本次使用 H2 Oracle 模式、本机 HTTP 接收器及 Edge 无头浏览器模拟 API 验证。已覆盖银行配置保存、编辑、停用、删除、失败提示和刷新，以及单笔收付与批量中心银行选择。没有连接真实达梦、调用真实结算服务或发布服务；H2 升级 DDL 回归不验证 DIsql 命令及匿名块。真实环境仍需验证数据库升级、网关鉴权、动账字典、账号有效性及后续事件处理。
